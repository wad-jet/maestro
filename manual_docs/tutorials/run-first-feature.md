# Запуск первой фичи

[Назад к оглавлению](../index.md)

Это обучающий материал: проводим вас за руку по полному циклу
feature-маршрута скилла `maestro` (шаги 0→18). Пример использует вымышленную
фичу для иллюстрации pipeline.

## 🎯 Что вы изучите

- Как пройти HITL-гейты на каждом шаге.
- Когда включается spec/Spec Review.
- Как устроена реализация (SDD) и ревью.

## 📖 Пошаговый проход

### Шаг 0: Project Context

Агент читает `docs/project-context.md`. Если файла нет — проводит HITL-диалог
по 14 категориям (включая секцию Commands). Если есть — запрашивает
подтверждение актуальности.

> **Варианты:** `(a)` загрузить и подтвердить · `(b)` создать/обновить ·
> `(c)` пропустить · `(d)` отмена.

### Шаг 1: Маршрут

Выберите `(f) feature`.

### Шаг 1.5: Режим

`(a) efficient` — агент молчит между гейтами · `(b) interactive` — комментирует
находки по ходу.

### Шаг 2: Подтверждение старта (pre-flight)

`(a) да` — pre-flight (диагностика состояния working tree, ветка, worktree,
baseline-тесты) и начало работы · `(b) отмена`. Pre-flight — последняя точка
отмены до создания ветки.

### Шаги 3–6: Изоляция

После диагностики агент предлагает сценарий (worktree / простая ветка). Выберите
вариант и создайте ветку `feature/<kebab-case>`.

### Шаг 7: Категория фичи

Оркестратор применяет матрицу сигналов и предлагает категорию.

- `(a) Сложная/Архитектурная` → полный pipeline со spec (шаги 8–10).
- `(b) Простая` → сразу к плану (шаг 11).
- При `(a)`, если в `docs/superpowers/specs/` есть готовый spec —
  `(d)` использовать его (fast-track) · `(e)` создать заново. В fast-track
  валидная подпись ревью/санизации в spec пропускает соответствующие гейты.

### Шаги 8–10: Spec и Spec Review (для сложных/архитектурных)

- Шаг 8 — диспатч сабагента `design` (trusted): brainstorming → spec. `design`
  пишет spec файл и возвращает summary + открытые вопросы. В fast-track шаг
  пропускается — используется внешний spec.
- Шаг 9 — оркестратор **обязан** предложить Spec Review (для архитектурных —
  обязателен). Диспатч `opus`-субагента (untrusted, независимый ревьюер).
- Шаг 10 — spec-гейт: `(a) Approve` → к плану · `(b) Revise` · `(c) Reject`.

### Шаги 11–12: План

- Шаг 11 — `writing-plans` создаёт план задач + секцию Project Context Changes
  (при необходимости) + регрессионные сценарии.
- Шаг 12 — `(a) Approve`: коммит spec+plan+regression-entry, переход к SDD.

### Шаг 13: Реализация (SDD)

Задачи выполняются субагентами (haiku/sonnet по сложности), каждая проходит
обязательный task-review. Регрессионные сценарии сверяются с кодом.

### Шаги 14–16: Документация и проверки

- Шаг 14 — обновление пользовательской документации.
- Шаги 15/15a — тесты, coverage, lint, build.
- Шаг 16 — финальное ревью ветки.

### Шаги 17–18: Завершение

- Шаг 17 — pre-PR: `(a) Approve merge` · `(b) Fix` · `(c) Отмена`.
- Шаг 18 — merge в base-ветку (fast-forward или --no-ff).

## 💡 Советы

- Каждый гейт — отдельный вопрос; «continue» не подтверждает следующий.
- Для простой фичи spec/Spec Review пропускаются — не пугайтесь отсутствия шагов 8–10.
- Путь быстрого старта: `0 → 6 → 7(b) → 11 → 13 → 16 → 18`.

## ⚠️ Известные ограничения

- Trivial fix (1–2 строки) — maestro не нужен, используйте `@haiku`.
- Refакторинг без изменения поведения — `subagent-driven-development` напрямую.
