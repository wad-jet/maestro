# Бэкап и восстановление памяти maestro

[Назад к оглавлению](../index.md)

## 🎯 Назначение

Пошагово: создать **бэкап данных memory layer** и восстановить их — штатно
(команда + tool в opencode) и аварийно (CLI без opencode, в т.ч. с другой
машины). v1 — только бэкенд `sqlite` (qdrant/pgvector → понятный отказ).
Справочник (формат, ключи `memory.backup.*`, fail-closed-валидация) — в
[Память maestro (reference)](../reference/memory.md) (разделы
`memory_backup`, «Аварийный CLI», «Ключи»); модель безопасности (C3) — в
[`SECURITY.md`](../../SECURITY.md) §5a.

## ✅ Штатный бэкап (`@maestro-memory-backup`)

1. В opencode запустите команду:

   ```
   @maestro-memory-backup
   ```

   Если tool `memory_backup` недоступен (память не включена) — команда
   сообщит об этом и завершится (см. [Как включить память](enable-memory.md)).

2. Команда вызывает `memory_backup` с `action: "list"` и показывает список
   существующих бэкапов (файл, `ts`, размер, статус jsonl/манифеста).

3. Ответьте на HITL-вопрос: (a) backup — (b) restore — (c) restore --replace —
   (d) отмена. Для бэкапа выберите **(a) backup**.

4. Tool пишет пару `backup-<key>-<ts>.jsonl` + `backup-<key>-<ts>.manifest.json`
   в каталог `memory.backup.path` (default `.maestro/memory/backup`): все
   записи активного `key`, повторно замаскированные по **текущему**
   confidential-набору (double-masking), + манифест (`model_id`, `dim`,
   `schema_fields`, `sha256` тела и др.). Вывод — число записей.

5. После успешной записи работает **retention**: старые пары этого проекта
   сверх `memory.backup.retention` (default `3`) удаляются (строго по
   паттерну `backup-<key>-*`, чужие файлы не трогаются).

> Бэкап с 0 записей не создаётся (tool: «нет записей для бэкапа»).
>
> Если каталог бэкапа **не** в `.gitignore` (например, после override пути) —
> в выводе каждого бэкапа будет WARN: «каталог бэкапа НЕ в .gitignore
> (бэкапы могут попасть в git)». См. «Бэкапы — только в приватные репо».

## ✅ Восстановление (merge — дефолт)

1. `@maestro-memory-backup` → листинг → выберите **(b) restore** и файл из
   списка (проверьте `ts` и статус манифеста `ok`).

2. Restore в режиме **merge** (дефолт): upsert по `session_id`, повторное
   маскирование (`maskEntry`) перед записью. Конфликт по ключу — **wins
   restore**: версия из файла бэкапа перезаписывает более свежую (без
   сравнения `time_last` — осознанная перезапись). Записи, отсутствующие в
   файле, не трогаются.

3. Прочитайте счёт в выводе: **N перезаписано / M добавлено**.
   `перезаписано > 0` — свежие записи (созданные после бэкапа) откатаны в
   состояние бэкапа (см. «Устаревший бэкап и merge»).

## 🚨 Аварийное восстановление (replace)

Replace — **деструктивная** операция: будет удалена **вся** память проекта
(активный `key`), затем восстановлена из файла бэкапа.

1. `@maestro-memory-backup` → листинг → выберите **(c) restore --replace**.
2. **Двойное подтверждение:**
   - HITL команды — явное предупреждение «будет удалена ВСЯ память проекта,
     затем восстановлена из <файл>» + **отдельное** подтверждение;
   - нативный `permission: ask` tool `memory_backup` сработает дополнительно.
3. Удаление выполняется **только после** успешной валидации бэкапа (sha256,
   манифест, все строки) — при порче/подмене файла память не пострадает.
4. Вывод — счёт (перезаписано/добавлено) и режим `replace`.

Используйте для **disaster recovery** (потеря/повреждение БД), не для
рутины: replace вернёт состояние **ровно** бэкапа, а merge оставит записи,
созданные после бэкапа (но откатит изменённые — см. ниже).

## 🛠️ CLI без opencode (аварийный канал)

Когда opencode недоступен (зависание, повреждённая БД), backup/restore
выполняется вручную из терминала:

```bash
node <путь-к-плагину>/memory/backup-cli.js list
node <путь-к-плагину>/memory/backup-cli.js backup
node <путь-к-плагину>/memory/backup-cli.js restore --file <путь> [--replace]
```

- `<путь-к-плагину>` — каталог установленного плагина `maestro-bootstrap`,
  где **рядом с `memory/` лежит `core.js`**: в целевом приложении —
  package-кэш OpenCode (путь пакета — из регистрации плагина в
  `.opencode/opencode.json` / глобальном конфиге); при разработке — каталог
  репо плагина. **Не `module_dir`**: там копия `memory/` без `core.js`, CLI
  оттуда не работает.
- Запуск — из корня (или подкаталога) git-репозитория проекта с
  `maestro.json`, где включена память (`storage.type: sqlite` — v1).
- sqlite-драйвер загружается из `module_dir` — там должен быть выполнен
  `npm install` (онбординг ниже).
- `--replace` — только из **интерактивного терминала** (TTY): CLI попросит
  ввести namespace; не-tty (скрипт/CI) → отказ.
- Тот же конфиг (`memory.backup.*`), те же данные (`memory.db` в
  `<data-dir>`) и те же confidential-наборы, что у плагина. Аудит —
  bootstrap-лог `.maestro/logs/maestro-bootstrap-<дата>.log`.
- Restore принимает файл **только из каталога бэкапов** (`memory.backup.path`)
  — файл снаружи будет отклонён.

### С другой машины (bootstrap-последовательность)

1. Установите плагин штатно: agpack или
   `git+https://github.com/wad-jet/maestro.git` в `.opencode/opencode.json` /
   глобальном конфиге; в `maestro.json` — секция `memory` (`enabled`,
   `namespace`, `storage.type: sqlite`).
2. Первый запуск opencode — плагин выполнит **self-provisioning**: создаст
   `module_dir`, запишет `package.json`, скопирует исходники модуля.
3. `npm install` в `module_dir` (default
   `<data-dir>/maestro/memory/module/`; первая установка может занять
   больше 5 минут — при обрыве просто повторите).
4. Запустите CLI (см. выше) — например, `restore --file <путь>`.

> Файлы бэкапа должны быть на машине: если бэкапы коммитятся в приватное
> репо — приходят вместе с репо; если нет — скопируйте пару
> (`*.jsonl` + `*.manifest.json`) вручную **в каталог `memory.backup.path`**
> (restore не читает файлы вне него).

## 🔒 Бэкапы — только в приватные репо (C3)

Записи памяти замаскированы, но это всё ещё знание о проекте (архитектура,
решения, git-метаданные). Модель: **коммит бэкапа = осознанная настройка**.

- **Дефолт:** `.maestro/memory/backup` — под `.maestro/`, который в
  `.gitignore`: бэкапы **не коммитятся**, они machine-local (эфемерные —
  см. «Дефолтный путь бэкапов — эфемерный»).
- **Коммит** — только осознанно: override `memory.backup.path` в отслеживаемое
  место (или gitignore-исключение) **и только приватное репо**. Пока каталог
  не gitignored, tool выводит **WARN при каждом бэкапе** (детерминированная
  проверка `git check-ignore`, не LLM-оценка).
- **Публичные репо — нет:** даже маскированные данные не публикуются (C3).

## ⚠️ Операционные заметки

### Restore при закрытом opencode (SQLITE_BUSY)

`memory.db` удерживает запущенный opencode (WAL, busy_timeout 5000). Если
restore возвращает busy-ошибку — **закройте opencode и повторите** (CLI —
вообще только при закрытом opencode). Документированное ограничение
(не enforcement): плагин не блокирует БД за вас.

### Устаревший бэкап и merge: свежие записи откатываются

Merge — **wins restore**: записи, чей `session_id` есть в файле бэкапа,
перезаписываются версией из файла — **включая более свежие**, созданные
после бэкапа. Восстановление устаревшего бэкапа в merge-режиме откатывает
изменённые записи в состояние бэкапа (счёт `перезаписано` показывает
масштаб отката); записи, добавленные после бэкапа (с нового `session_id`),
выживают. Если нужна **ровно** состояние бэкапа (disaster recovery) —
**replace**.

### sha256 — детекция порчи, не защита от подделки

`sha256` в манифесте — контрольная сумма JSONL-тела: детектирует порчу
файла (биты, обрезка, случайная правка) — при несовпадении restore
отказывается (fail-closed). Манифест **не подписан**: злоумышленник,
заменивший файл бэкапа, заменит и манифест — checksum от намеренной подмены
не защищает. Защита от недоверенного restore-файла — fail-closed-валидация
(схема v3, `model_id`/`dim`, `key`, `schema_fields`), **повторное
маскирование** каждой записи (`maskEntry`) перед записью и двойной гейт
`replace` (см. [`SECURITY.md`](../../SECURITY.md) §5a).

### Escape-hatch: отказ restore из-за смены `schema_fields`

Restore **отказывается** от бэкапа, чьи `schema_fields` не совпадают с
текущей схемой (fail-closed — без partial restore). Если после апгрейда
плагина старый бэкап не восстанавливается:

1. **Закрепите (pin) версию плагина, создавшую бэкап** (версия из манифеста,
   поле `plugin_version`): точная версия пакета `maestro` в
   `.opencode/opencode.json` / глобальном конфиге (или tag репо) → перезапуск
   opencode.
2. Выполните restore (merge или replace) на старой версии.
3. Апгрейдните плагин до текущей версии; при следующем бэкапе создастся файл
   с актуальной схемой (сверьте `schema_fields` в манифесте).

### Дефолтный путь бэкапов — эфемерный

`.maestro/memory/backup` — **machine-local**: `.maestro/` gitignored, бэкапы
теряются при потере машины/диска и недоступны на другой машине.
**Долговечность** (DR, команда) — только осознанным override
`memory.backup.path` (отслеживаемое место в **приватном** репо) + коммит
(см. «Бэкапы — только в приватные репо»).
