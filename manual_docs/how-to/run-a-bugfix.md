# Запуск багфикса

[Назад к оглавлению](../index.md)

## 🎯 Назначение

Как запустить багфикс через скилл `maestro`. Маршрут багфикса идёт через
debug sub-pipeline (шаги D1–D7), затем план → SDD → проверки → завершение.

## 📖 Пошаговая инструкция

### Шаг 1: Выберите маршрут (шаг 1)

В ответ на вопрос агента выберите `(b) bugfix`.

### Шаг 2: Подтверждение старта + pre-flight (шаги 2–6)

Подтвердите старт, пройдите диагностику и создайте ветку `fix/<kebab-case>`.

### Шаг 3: Debug sub-pipeline

**D1 — Ресеч и гипотезы.** Агент читает логи, воспроизводит проблему, формирует
гипотезу (`systematic-debugging`).

**D2 — Гейт гипотезы.** `(a) да` — начать probe · `(b) новая гипотеза` → к D1.

**D3 — Probe-фаза.** Агент вносит временные изменения и записывает каждую правку
в `.probe-changes.md`.

**D4 — Проверка гипотезы.** Запуск, тесты, логи — гипотеза подтвердилась?

**D5 — Откат probe.** Агент всегда откатывает probe-код (независимо от результата).

**D6 — Гейт.** `(a) да` — гипотеза подтверждена · `(b) нет` → к D1.

**D7 — Гейт перехода к фиксу.** `(a) да` → к плану (шаг 11).

### Шаг 4: План, реализация, проверки, завершение

Дальше — стандартный маршрут: план (шаги 11–12), реализация (шаг 13),
документация и проверки (шаги 14–16), завершение (шаги 17–18).

## 💡 Пример

```
Проблема: "500 при активации узла с дублирующимся reference"

D1: Гипотеза — reference UNIQUE constraint бросает 500, нет проверки перед insert
D2: (a) да
D3: add try-catch вокруг eventStore.append(), логирует reference
D4: curl POST /nodes/test/activate → в логе 'ref: dup-ref-123' → подтверждено
D5: откат try-catch → git status показывает чистый diff фикса
D6: (a) да
D7: (a) да → план → SDD → проверки → merge
```

## ⚠️ Известные ограничения

- Для тривиального багфикса (1–2 строки) maestro не используется —
  redirect на `@haiku` с TDD.
- `git stash` в manual-проверках оркестратора запрещён (может применить чужой stash).
