# Спека: версионирование в project-context.md (правило + pipeline-hook)

- **Дата:** 2026-09-21
- **Ветка:** `feature/versioning-in-project-context`
- **Категория:** Простая фича (Bounded), формализация по конвенции AGENTS.md
- **Источник:** боль пользователя: при каждой фиче/фиксе приходится напоминать
  про bump версии; правило версионирования нигде не зафиксировано

## 1. Проблема

Проектный контекст (`docs/project-context.md`) хранит **текущую** версию
дистрибутива, но не хранит **правило** версионирования: есть ли версионирование,
какая схема (semver), где живёт версия, какой тип изменения какой уровень даёт,
что делать при релизе (changelog, синхронизация ссылок на версию). Из-за этого
при каждой фиче/фиксе/доработке агент не знает, нужен ли bump и какого уровня —
пользователь вынужден напоминать (прецедент: вопрос «А bump версии минорной
выполнен?» после мержа 4.3.0).

## 2. Решение

### 2.1. Поле «Версионирование» в project-context.md (категория 3)

В категории 3 («Стек технологий») фиксируется блок:

- **Есть ли версионирование:** да / нет (для проектов без версии дистрибутива —
  «нет», pipeline-хук не срабатывает).
- **Схема** (напр. semver: MAJOR.MINOR.PATCH).
- **Где живёт версия** (напр. корневой `package.json → version`).
- **Маппинг типа изменения → уровень** (напр. новая фича/процессное правило —
  minor; багфикс/патч — patch; beta-модули — отдельное правило, напр.
  «memory layer в beta — дистрибутивная версия не бампается»).
- **Действия при релизе:** changelog-секция `## [YYYY-MM-DD]` + строка
  «Версия X.Y.Z»; синхронизация всех файлов, ссылающихся на текущую версию
  (package.json, project-context.md, README — по факту наличия); bump —
  отдельный коммит `chore: bump version to X.Y.Z — <содержание> (changelog/version)`.

### 2.2. Pipeline-hook (SKILL.md maestro)

- **Шаг 0 (Load Project Context):** из проектного контекста извлекаются
  **правила версионирования** (если поле есть) — в переменную сессии
  PROJECT_CONTEXT наравне с командами секции 14.
- **Гейт 17 (pre-PR):** если версионирование есть — оркестратор ПОКАЗЫВАЕТ на
  гейте предлагаемую версию: `Версия: X.Y.Z → A.B.C (правило: <маппинг>)`.
  Версионирования нет / правила нет — строка не показывается, шаг не меняется.
- **Шаг 18 (finishing, после merge):** если на гейте 17 была строка версии —
  оркестратор выполняет bump по правилам контекста: новая версия, changelog-
  секция, синхронизация ссылок, отдельный bump-коммит (по прецеденту репо —
  после merge, на base-ветке, до push, если push ещё не выполнен).

### 2.3. Шаблон контекста (maestro-setup)

`skills/maestro-setup/init-context.md`, категория 3 — дополнительная строка:
«Версионирование: да/нет + схема, где живёт версия, маппинг типа изменения →
уровень, действия при релизе (changelog, синхронизация версий)».

## 3. Охват изменений

| Файл | Изменение |
|---|---|
| `docs/project-context.md` | §3 — блок «Версионирование» для этого репо (semver, package.json, маппинг, релиз-действия, memory-beta исключение) |
| `skills/maestro-setup/init-context.md` | категория 3 — строка-шаблон «Версионирование» |
| `skills/maestro/SKILL.md` | шаг 0 — извлечение правил версионирования; гейт 17 — строка «Версия: …»; шаг 18 — выполнение bump |
| `manual_docs/explanation/project-context.md` | категория 3 — «версионирование» в описании обязательной секции |
| `manual_docs/overview/changelog.md` | запись в `[Unreleased]` |

## 4. Критерии приёмки

1. Блок «Версионирование» существует в `docs/project-context.md` §3 и содержит
   все 5 полей 2.1.
2. SKILL.md: шаг 0 упоминает извлечение правил версионирования; гейт 17 —
   пропозицию версии (условно: «если версионирование есть»); шаг 18 —
   выполнение bump по правилам.
3. `init-context.md` категория 3 содержит строку-шаблон.
4. manual_docs синхронизированы (project-context.md + changelog).
5. Язык — русский.
6. **Догфудинг:** при мерже этой фичи выполняется bump 4.3.0 → 4.4.0 (minor,
   новая фича) по новому же правилу — доказательство, что правило сработало
   без напоминания.

## 5. Чего НЕ делаем

- Не вводим авто-bump в плагин/скриптах — bump выполняет оркестратор по
  правилам контекста (документационная фича).
- Не меняем существующие версии/конвенции релиза — формализуем уже живущую
  практику (прецеденты 3.1.0, 3.2.1, 4.2.3, 4.2.4, 4.3.0).
- Не трогаем beta-правило memory layer — формализуем как часть маппинга.
