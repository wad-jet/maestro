## Дизайн-решения

### D1. Scope реформата — топовые 7 не-reference страниц (HITL)

Реформатируются ровно 7 файлов (user-facing: tutorials/how-to/explanation):
1. `manual_docs/explanation/agents-and-trust.md` (8 стен, max 8.9k)
2. `manual_docs/how-to/enable-memory.md` (11 стен)
3. `manual_docs/tutorials/setup-project.md` (4 стены)
4. `manual_docs/explanation/pipeline-overview.md` (3 стены, max 3.9k)
5. `manual_docs/how-to/choose-models.md` (3 стены)
6. `manual_docs/how-to/keep-docs-up-to-date.md` (3 стены)
7. `manual_docs/how-to/choose-embedding-model.md` (3 стены) — how-to, не
   reference (исправление по Spec Review I2: в первоначальном scope ошибочно
   отнесён к reference/).

`reference/` (memory.md — 35 стен, config.md — 13, hitl-gates.md — 6,
model-selection.md — 6, commands.md — 5) — **FU** отдельным пасом (справочник
плотный по природе; правила применяются, но реформат — отдельная фича).

### D2. Правила читабельности — новая секция в `skills/manual-docs/SKILL.md` (HITL)

Новая секция **«Читабельность»** (между «Правила» и «Роль в maestro»),
5–7 правил с одним before/after-примером. **Бюджет секции: ≤ ~50 строк,
пример ≤ ~25 строк** (скилл грузится на шаге 14 пайплайна целевых
приложений — бюджет контекста). Пример — «иллюстрация из доков самого
maestro» (пометка обязательна; **без версионных строк** — дрейф-тест D1c
не сканирует skills/**), источник фрагмента — реальный блок
`agents-and-trust.md`:

- **R1 Лид.** В начале документа и каждого крупного раздела — 1–2 предложения-
  лид: что даёт раздел и кому.
- **R2 Короткие абзацы.** Абзац — не длиннее 2–3 предложений; «стена текста»
  (> ~600 знаков) запрещается — делить.
- **R3 Структура вместо монотона.** ≥3 однородных объекта (агента, шага,
  ключа, случая) — таблица или список, не абзац.
- **R4 Аббревиатуры.** При первом вхождении (в документе) — раскрытие
  («HITL — human-in-the-loop (ручное подтверждение)»); далее — сокращение
  допустимо. Вставка раскрытия — добавление без перестройки предложения
  (граница с D3). Для reference/ (FU1) — рассмотреть per-раздел (non-linear
  чтение: читатель входит с середины).
- **R5 Акценты.** Ключевые термины/предупреждения — жирным или `>`-блок;
  не более 2–3 акцентов на экран.
- **R6 Пример.** Для неочевидного правила/поведения — короткий конкретный
  пример (команда, фрагмент конфига, ситуация).

Документ-пример для before/after берётся из реального блока `agents-and-trust.md`
(худшая стена 8.9k — до/после, ~15 строк).

Плюс: в «Правило 3: Рецензия документации» — пункт «Читабельность по секции
«Читабельность» (лиды, стены, таблицы)».

### D3. Глубина правки — структура, без переписывания смысла (HITL)

Правки: деление абзацев на списки/таблицы/подзаголовки, лиды, лёгкое
разбиение длинных предложений, аббревиатуры при первом вхождении, акценты.
**Не делаем:** переписывание формулировок на «простой язык», смена порядка
содержимого (кроме выделения лидов), удаление фактов, изменение терминов/
путей/команд/ключей/версий, **переименование/удаление существующих
заголовков** (в manual_docs есть anchor-ссылки на заголовки — не ломать).
Факты «до» и «после» — идентичны (это проверяет ревью: сверка фактов по
diff — inline-code spans, пути, semver, команды — без удалений/замен, не
только стиля).

### D4. Критерии приёмки

1. На 7 страницах D1: **0 прозаических абзацев > 600 знаков**. Методика
   измерения (детерминированная, унаследует FU2):
   - **fenced code blocks (``` … ```) исключаются**;
   - **списки и таблицы меряются построчно/по-элементу** (после очистки
     префиксов «- », «1. », «|») — длинный bullet или строка таблицы > 600
     знаков тоже «стена»;
   - **абзац = прозаический блок** между `\n\n+` без markdown-префиксов.
2. Все факты сохранены: версии, ключи конфигурации, пути, команды, имена
   агентов/команд — идентичны до/после (git diff + сверка ревью).
3. Секция «Читабельность» в `skills/manual-docs/SKILL.md` с R1–R6 + пример
   (в бюджете D2); пункт в «Правило 3».
4. npm test зелёный (полный прогон, без новых красных); drift-тест зелёный
   (пути/имена в доках не менялись).
