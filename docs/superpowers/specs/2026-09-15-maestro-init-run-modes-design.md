# Спека: режимы запуска `@maestro-init` (manual / auto-answer / auto-ai)

- **Дата:** 2026-09-15
- **Ветка:** `feature/maestro-run-modes`
- **Категория:** Сложная фича (полный pipeline), реализация в 2 фазы
- **Источник:** TODO п.77 (lite/pro, P3) + боль пользователя: типовые доработки дают
  одни и те же HITL-ответы каждый прогон (отчёт `report-ses_f6e30d9d2ffe4mBUm6L4SVx5KS-2026-09-14.md`)

## 1. Проблема

Стандартная, проработанная доработка проходит пайплайн с одними и теми же
рутинными ответами на каждом гейте (подтвердить контекст, категорию, план,
прогнать Spec Review). Это когнитивная нагрузка без пользы. При этом HITL
нельзя убирать тотально: PR, финальное ревью спеки, чувствительные контракты и
правила бизнес-логики требуют явного решения человека.

## 2. Режимы запуска

`@maestro-init` получает **три режима**, различающихся философией автоматизации.
Режим — per-run флаг, не персистится в `maestro.json`.

| Режим | Флаг | Цель | Механика |
|---|---|---|---|
| **manual** | *(без флага)* / `--no-auto` | полный контроль человека | текущее поведение без изменений |
| **auto-answer** | `--auto-answer` / `-aa` | **полнота процесса** без поштучных подтверждений | все шаги/проверки/ревью выполняются полностью; авто-принимаются только рекомендации на рутинных гейтах |
| **auto-ai** | `--auto-ai` / `-ai` | **максимальная лёгкость и эффективность** (срезание углов) | ИИ сам принимает решения с доп. анализом; механика — ralph loop |

### Философия

- **manual** — человек подтверждает каждый шаг.
- **auto-answer** — *не облегчает работу, убирает только подтверждения.* Все шаги
  pipeline, pre-flight, baseline-тесты, Spec Review, task-review, docs, финальные
  проверки выполняются в полном объёме. Авто-принимается лишь ответ на рутинный
  вопрос «подтверждаете рекомендацию?». Любое сокращение процесса — это auto-ai,
  а не auto-answer. Каждое авто-принятие выводится одной строкой в чат
  (`[auto-answer] шаг N: принята рекомендация (a) X — обоснование`), не молча.
- **auto-ai** — ИИ сам решает, что можно упростить/пропустить: маршрут
  (фича/баг/спайк), пересборка vs обновление project-context, контентные
  вопросы — с доп. анализом. Жёсткий пол (никогда не пропускается): TDD,
  task-review, SEC-3, шаг 15 (тесты для гейта 17), security-гейты, инварианты
  ⚑1–4. Цикл ведётся механикой ralph loop.

## 3. Инварианты автоматизации (действуют во всех режимах, включая auto-ai)

| # | Инвариант | Механика в пайплайне |
|---|---|---|
| ⚑1 | PR/мерж — только человек (лично или явное поручение) | гейт 17 всегда HITL; шаг 18 — только после явного ответа |
| ⚑2 | Финальное ревью спеки — только разработчик; ИИ-ревью (opus) вспомогательное | гейт 10 всегда HITL; **принятие спеки — только явная команда** («спека принята» / буква варианта); **«продолжай»/«ок»/молчание ≠ принятие; шаги 11+ (план, реализация) не начинаются до явного принятия** |
| ⚑3 | Тесты, написанные ИИ, — не полностью доверенные | результаты показываются человеку на гейте 17; ни одно авто-решение не опирается на «ИИ-тесты зелёные» как доказательство корректности |
| ⚑4 | Внешние API-контракты интеграций и основополагающие правила бизнес-логики — только явное HITL-решение | sensitivity guard на гейте 12 (см. §5) |

## 4. Матрица гейтов по режимам

Легенда: **HITL** — всегда ручной ответ; **авто** — авто-принятие рекомендации
(в auto-answer — с уведомлением; в auto-ai — ИИ решает сам с доп. анализом);
условие-источник рекомендации не выполнено → HITL в любом режиме (P1.3).

| Гейт | manual | auto-answer | auto-ai |
|---|---|---|---|
| 0 — контекст | HITL | авто (a) загрузить, если файл есть; нет → HITL | авто (ИИ решает пересборка/обновление/пропуск) |
| 1 — маршрут | HITL | авто из текста задачи, если однозначно; иначе HITL | авто (ИИ решает фича/баг/спайк) |
| 1.5 — режим | HITL | авто (a) efficient | не спрашивается (режим фиксирован) |
| 2 — pre-flight | HITL | авто (a) да (P1.3) | авто |
| 7 — категория | HITL | авто по матрице сигналов (P1.3) | авто |
| 7d — внешний spec | HITL | авто (d), если однозначное соответствие; иначе HITL | авто |
| 9 — предложение Spec Review | HITL (обязан предложить) | авто (b) прогнать (сложные); архитектурные — обязателен | авто (ИИ решает прогнать/пропустить по анализу) |
| 10 — spec gate | **HITL (⚑2): явная команда** | **HITL (⚑2): явная команда** | **HITL (⚑2): явная команда** |
| 12 — plan gate | HITL | авто (a), если quality-проверки пройдены **и** нет чувствительных изменений (⚑4); иначе HITL | авто; чувствительные изменения → HITL (⚑4) |
| 17 — pre-PR/merge | **HITL** (⚑1) | **HITL** | **HITL** (⚑1) |
| Контентные вопросы (brainstorm Q/A, custodian-сходимость, имя ветки, D2/D6/D7, spike) | HITL | HITL (никогда не авто) | авто (ИИ решает с доп. анализом) |
| Security-гейты (8.6 FINDINGS, Точка 2, File access, гейт плагина P5) | HITL | HITL | **гибрид**: безопасный дефолт ИИ применяет сам (вычистить и продолжить); принятие риска / стоп — HITL |
| Чувствительные изменения (внешние API-контракты, основополагающая бизнес-логика) ⚑4 | HITL | HITL | HITL (⚑4) |
| Tier 3 / упавшие команды (15/15a), docs-расхождения (14), reconciliation (13f) | HITL | HITL | HITL (окружающая неоднозначность не авто-решается) |
| Прозрачность | вопрос на каждом гейте | уведомление `[auto-answer] шаг N: …` | журнал решений + паузы на гейтах 10/17 |

## 5. auto-answer: перечень авто-гейтов и условия

Авто-принимаются (по рекомендации P1.3/источнику):

| Гейт | Авто-ответ | Условие-источник |
|---|---|---|
| 0 | (a) загрузить | `docs/project-context.md` существует; нет → HITL |
| 1 | маршрут из текста задачи | однозначно; иначе HITL |
| 1.5 | (a) efficient | сам флаг выражает предпочтение |
| 2 | (a) да | P1.3 (маршрут и режим только что выбраны) |
| 7 | категория по матрице | P1.3 |
| 7d | (d) использовать внешний spec | однозначное соответствие задаче; иначе HITL |
| 9 | (b) прогнать Spec Review | сложные фичи (рекомендован); архитектурные — обязателен |
| 12 | (a) Approve | P1.3 (quality-проверки пройдены) **+ sensitivity guard** |

### Sensitivity guard (гейт 12, ⚑4)

Авто-принятие (a) Approve на гейте 12 применяется только если план **и** spec
**не затрагивают** внешние API-контракты интеграций (public API, межсервисные
контракты, breaking changes) и основополагающие правила бизнес-логики. Если
затрагивают — гейт 12 остаётся HITL даже в auto-answer (рекомендация
показывается по P1.3, подтверждает человек). Классификация (гейт 7) под guard
не подпадает: сигналы «Public API / breaking» в матрице ведут только в более
строгий путь (обязательный Spec Review + гейт 10).

### Никогда не авто (auto-answer)

- Гейты 10 (⚑2), 17 (⚑1)
- Контентные вопросы фичи: brainstorm Q/A, custodian-сходимость, имя ветки при
  неоднозначности, D2/D6/D7, spike-гейты
- Security-гейты: 8.6 при `FINDINGS_FOUND` (включая HITL-заверение «sanitize
  пропустить» — P7), Точка 2, File access control, гейт плагина (P5)
- Плато и особый случай Revise (шаг 10)
- Tier 3 и упавшие команды (15/15a), docs-расхождения (14), reconciliation (13f)
- Чувствительные изменения (⚑4)

### P1.3 и ранние гейты

Дефолты P1.3 (шаги 2, 7, 10, 12, 17) без флага — не меняются: дефолт
предлагается, подтверждается вручную. auto-answer добавляет рекомендации на
гейты 0/1/1.5/9 (только при флаге) и превращает рекомендации в авто-принятие
на 2/7/12. Правило «условие-источник не выполнено → HITL» сохраняется.

## 6. auto-ai: семантика (Phase 2)

- **ИИ решает сам** (с доп. анализом): маршрут (фича/баг/спайк), project-context
  (пересборка vs обновление), контентные вопросы (brainstorm Q/A, custodian-
  сходимость, имя ветки, D2/D6/D7), Spec Review offer (прогнать/пропустить по
  анализу), docs-шаг.
- **Жёсткий пол** (никогда не пропускается): TDD, task-review, SEC-3, шаг 15
  (тесты — для гейта 17 и ⚑3), security-гейты, инварианты ⚑1–4.
- **Security-гейты — гибрид:** при находках sanitizer ИИ применяет безопасный
  дефолт «вычистить и продолжить» (не риск-принятие); принятие риска и стоп —
  только HITL.
- **Правило направления:** автоматизируются только **risk-reducing** действия
  (вычистить, замаскировать, запретить доступ, остановиться) — их ошибка стоит
  эффективности (восстановимо). **Risk-accepting** действия (продолжить как есть,
  разрешить доступ, пропустить sanitize, довериться источнику) — всегда HITL:
  их ошибка стоит конфиденциальности (невосстановимо). Принцип уже действует для
  Ур.1 маскирования плагина (авто, без HITL) — гибрид расширяет его на обработку
  находок Ур.2, не вводя новый класс авто-security-решений.
- **Механический пол не снимается:** Ур.1 маскирование task-промптов, read-блоки
  access_policy и confidential-deny исполняются плагином безусловно — авто-режимы
  их не отключают; worst case «непослушного» оркестратора покрыт механикой.
  Гибрид 8.6/Точка 2 — инструкционный уровень (статус как у P5/P7).
- **R1 Прозрачность:** каждое security-авто-действие (вычистить / deny) —
  в журнал решений + строка в сводке на следующем инвариантном гейте (10/17);
  человек видит, что сделано с безопасностью, до принятия спеки/мержа.
- **R2 Анти-тупик:** отказ в доступе (deny) не ретраится в ralph loop (>1 попытки)
  — оркестратор передаёт нужный контекст через санизированный промпт либо
  фиксирует деградацию в журнал.
- **R3 Тревожная плотность:** аномально высокое число findings за прогон
  (эвристика оркестратора) → пауза с HITL даже для безопасного направления —
  признак системной проблемы, не рутины.
- **R4 P5 — предпосылка режима:** без работающего плагина авто-режимы не стартуют
  (жёсткий стоп, fail-closed) — это не «гибрид», а условие существования режима.
- **Паузы на инвариантных гейтах:** гейты 10 (⚑2) и 17 (⚑1) — жёсткие стопы,
  ИИ ждёт человека, затем продолжает. Принятие спеки на гейте 10 — только явной
  командой; ralph loop не начинает шаги 11+ (план, SDD) до неё.
- **Механика:** ralph loop (state-файл `.opencode/ralph-loop.local.md`,
  idle-детект продолжения, `<promise>DONE</promise>` по завершении,
  max-итерации, `/cancel-ralph`). Итерации не форсируют проход инвариантных
  гейтов 10/17.
- **Fallback неоднозначности:** если доп. анализ неоднозначен — консервативный
  выбор (более полный путь), как рекомендации auto-answer; не гадать в пользу
  срезания углов.

### Модель принятия решений (кто решает)

Решение принимает либо оркестратор сам (механические случаи), либо
диспатч субагента по tier-сложности (сужденческие). Диспатч — через `task`
с `subagent_type=sonnet|opus` (OpenCode выбирает агента, модель привязана в
merge-конфиге `agent.{sonnet,opus}.model`); перед untrusted-диспатчем —
sanitize (Точка 2); decision-агент read-only, возвращает структурированное
решение (выбор + обоснование + confidence), применяет оркестратор; каждая
запись — в журнал решений.

| Уровень | Решения | Исполнитель |
|---|---|---|
| **Механический** (без диспатча) | авто-принятия набора auto-answer (0/1/1.5/2/7/7d/9/12 — источник-условие P1.3/matrix/guard), security-дефолт «вычистить и продолжить» | оркестратор сам |
| **Средний** → `sonnet` | маршрут при неоднозначности, имя ветки, Spec Review offer, docs-шаг, project-context обновление/пересборка, D6/D7, custodian-сходимость | диспатч **батчами** (несколько вопросов — один диспатч) |
| **Сложный** → `opus` | контентные вопросы brainstorm (архитектура/design), D2 (гипотеза багфикса), spec-уровневые вопросы | диспатч |
| Confidential-зависимые | trusted `custodian` (Q/A-агрегат, без значений) | существующий паттерн шага 8 |
| **Эскалация** | sonnet вернулся неуверенным (низкий confidence) → повторный диспатч `opus` | аналог fix-loop эскалации |
| **Fallback** | opus тоже неуверен → консервативный выбор (более полный путь) | оркестратор применяет, фиксирует в журнале |

Батчинг: контентные вопросы brainstorm/сходимости собираются и отправляются
одним диспатчем (пакет ответов), а не по одному — экономит время/токены
(5–15 вопросов фичи ≠ 5–15 диспатчей). Механические авто-принятия диспатч НЕ
требуют: решение уже обосновано внешним источником-условием.

## 8. Фазы

- **Phase 1:** manual + auto-answer (полная реализация) + семантика auto-ai
  зафиксирована в этом спеце. Реализация файлов 1–8 (+9 опц.).
- **Phase 2:** auto-ai (ralph loop интеграция, гибридные security-гейты, правила
  доп. анализа) — доработка SKILL.md и доков.

## 9. Out of scope

- Персистенция режима в `maestro.json` (режим — per-run флаг).
- Изменения плагина/кода (чистый markdown-контент; плагин не затрагивается).
- Алиасы сверх `-aa`/`-ai` (YAGNI).
- auto-ai полная реализация — Phase 2.

## 10. Верификация

- Перечни гейтов идентичны в SKILL.md ↔ hitl-gates.md ↔ commands.md (grep-сверка).
- Инварианты ⚑1–4 и security-гейты перечислены как never-auto во всех трёх местах.
- Нет остаточных имён (`--solo`, `--autopilot`, `--manual` как флага).
- Diff-сверка: каждое изменение поведения покрыто в `manual_docs/`.
