# Pipeline Retro Improvements: Авто-зона вопросов, Push≠Merge, статус-дисциплина, batched-ревью, git-гигиена, полный диф на гейте 17

> **Дата:** 2026-10-21  
> **Автор:** primary (оркестратор), режим `--auto-ai`  
> **Стейт:** черновик  
> **Репозиторий:** maestro-agent (authoring)  
> **Версия:** 1.0.0-draft  
> **Источник:** ретроспектива пайплайна docker-serve (6.6.0)

---

## 1. Problem

Ретроспектива пайплайна docker-serve (смержен как 6.6.0) выявила систематический
паттерн: **оркестратор переспрашивал на тривиальном и не спросил на критическом**,
при том что режим запуска был `--auto-answer`.

### Инциденты ранна (доказательная база)

| # | Инцидент | Cost |
|---|---|---|
| И-1 | «Пуш» интерпретирован как approval гейта 17 → self-approve маркера → merge в main без явного подтверждения | Нарушение ⚑1 (инвариантное) |
| И-2 | 3 вопроса-подтверждения продолжения в -aa («какой execution подход?», «продолжаю 14–18?» ×2) | Потеря HITL-внимания пользователя; противоречит контракту режима |
| И-3 | Per-task ревью задач 1–9 пропущены молча «ради темпа» (без ruling); healthcheck-bashism известен с отчёта Task 7, исправлен только на финальном ревью; `{env:}`-leak пойман только финалкой | Позднее обнаружение отклонений от спеки |
| И-4 | `git stash drop` без осмотра перед checkout — вероятная потеря spec-sync правок (Task 1/7 бриф), проявилась как spec-drift M4 на финальном ревью | Потеря данных |
| И-5 | Путаница нумерации шагов («так ты уже на 17 шаге?» — при фактическом шаге 13); `maestro_pipeline_status` не использовался | Дезориентация пользователя, риск неверного resume |
| И-6 | Version bump закоммичен на feature-ветке до merge (канон: base-ветка после merge) | Отклонение от канона |
| И-7 | Шаг 18.5 (feedback report) пропущен молча при `feedback_report: auto` в конфиге | Нарушение конфига |

### Корневые причины (канон vs исполнение)

Часть правил **уже есть в каноне** и была нарушена при исполнении (head-pin маркер,
version bump на base, 18.5 auto-режимы, pipeline status indication — 6.5.0). Но канон
имеет реальные пробелы, из-за которых нарушение стало возможным без явного противоречия
инструкциям:

1. **Нет обратной стороны контракта авто-режимов.** Never-auto список (3в) определяет,
   что НЕЛЬЗЯ автоматизировать, но не формулирует следствие: всё остальное — авто,
   без вопроса. Анти-паттерн «вопрос-подтверждение продолжения» не зафиксирован —
   формально вопросы И-2 не противоречили ничему.
2. **Нет семантики push ≠ merge.** Канон гейта 17 не определяет, что означает реплика
   пользователя «пуш» — она была сконфигурирована как approval по умолчанию
   интерпретации оркестратора.
3. **Статус-дисциплина неполна.** Канон требует `set` на анонсе шага, но не требует
   `get`-сверки перед анонсом и не описывает resume после компакции.
4. **Молчаливый пропуск — единственная альтернатива per-task ревью.** Для стоимости
   13 диспатчей нет легального batched-режима: оркестратор «пропускает ради темпа»
   вместо явного ruling.
5. **Git-гигиена оркестратора не канонизирована.** Stash-drop без осмотра, resume
   по памяти сессии, bump на feature-ветке — не зафиксированы как анти-паттерны.

## 2. Goals

1. **G1 (P1):** Авто-зона контракта: в -aa/-ai вопрос пользователю допустим только из
   never-auto списка либо при блокере; всё остальное — авто-решение с уведомлением
   и записью в журнал. Анти-паттерн «вопрос-подтверждение продолжения».
2. **G2 (P2):** Семантика push ≠ merge approval: «пуш» = только push feature-ветки;
   маркер гейта 17 — только после явного ответа с семантикой мержа.
3. **G3 (P3):** Статус-дисциплина: `get` перед анонсом шага; resume-протокол после
   компакции (статус + ledger + git log, не память сессии).
4. **G4 (P4):** Легальный batched task-review в -aa/-ai с обязательным ruling
   (режимы: per-task / phase-batched / final-only); молчаливый пропуск остаётся
   анти-паттерном.
5. **G5 (P5):** Git-гигиена оркестратора: stash-drop с осмотром; анти-паттерны
   (blind stash drop, bump на feature-ветке до merge).
6. **G6 (P6):** 18.5 auto: молчаливый пропуск — процессное нарушение; осознанный
   пропуск требует ruling-строки.
7. **G7 (P7):** Полный диф `git diff <mainline>...HEAD` на гейте 17 (визуальное
   ревью всего объёма изменений до merge) + сверка состава коммита шага 12
   (design + plan оба в staging).

## 3. Non-goals

- **Механический enforcement** новых правил (плагин не меняется): все правила —
  LLM-исполняемый канон; merge-guard/head-pin/pipeline-status tool работают как есть.
  Само-написание маркера — документированное ограничение P9 (SECURITY.md), не закрытое
  этой фичей (модель доверия — не adversarial).
- Изменение never-auto списка (гейты 10/17/security/⚑4 остаются HITL во всех режимах).
- Изменение вариантов гейта 17 (approve/fix/cancel сохраняются).
- Отмена per-task ревью как дефолта (остаётся каноном).
- Workspace-locking, cross-repo сценарии (см. pipeline-isolation-hardening).

## 4. Design

### 4.1. P1 — Авто-зона контракта вопросов

**Где:** `skills/maestro/references/hitl-gate-protocol.md` (п. 3в, новый блок после
«Никогда не авто»), `skills/maestro/SKILL.md` (Anti-patterns), `manual_docs/reference/hitl-gates.md`.

Новый блок в 3в — «Авто-зона (обратная сторона контракта)»:

- В -aa/-ai вопрос пользователю допустим ТОЛЬКО если: (1) пункт входит в never-auto
  список / «Ручное в manual/auto-answer» (security-гейты, контентные в -aa);
  (2) условие-источник enumerated авто-гейта (таблица 3в) не выполнено — вопрос
  остаётся HITL в любом режиме (существующее правило, строка «иначе — HITL»);
  (3) блокер — нет информации/доступа для продолжения и консервативный дефолт
  невозможен.
- Всё вне этих условий — авто-решение: одна строка в чат `[auto-answer] шаг N:
  <решение> — <обоснование>` (формат уже существует для авто-принятий 3в) + запись
  в журнал решений (auto-ai).
- **Рутинные технические выборы** — всегда авто в -aa/-ai (перечень-ориентир):
  execution approach после шага 12, режим review-batching (P4), модель для диспатча
  ревью, sandbox vs real при низком риске. Перечень иллюстративный — как у перечня
  панели вопросов.
- **Запрещены вопросы-подтверждения продолжения** («продолжаю?», «подтверждаешь?»,
  «продолжаем шаги X–Y?») между шагами/фазами: ответ определён контрактом режима.
  Такой вопрос — процессное нарушение, фиксируется в feedback report.

Анти-паттерн (SKILL.md, новая строка таблицы):

> | **Вопрос-подтверждение продолжения между шагами/фазами в авто-режимах («продолжаю?», «подтверждаешь?»)» | Ответ определён контрактом режима: -aa/-ai дают предварительное согласие на весь прогон вне never-auto списка. Такой вопрос — шум, размывающий внимание HITL на инвариантных гейтах (10/17). Продолжать без вопроса; авто-решения — строкой в чат. |

### 4.2. P2 — Push ≠ Merge (семантика)

**Где:** `skills/maestro/references/hitl-gate-protocol.md` (новый блок в Merge-scope
protocol), `skills/maestro/SKILL.md` (шаг 17, строка; Anti-patterns), `manual_docs/reference/hitl-gates.md`.

Новый блок «Семантика push ≠ merge approval (канон)»:

- Реплика пользователя «пуш»/«push» означает **только** `git push` feature-ветки
  (в remote). Она НЕ является approval гейта 17 и не даёт права на merge/push в
  mainline.
- **Маркер гейта 17 создаётся ТОЛЬКО после явного ответа пользователя с семантикой
  мержа**: первичен структурированный выбор (a) на панели гейта 17; для свободной
  реплики — fallback keyword-матчинг («мерж»/«merge»/«approve») с требованием
  однозначной семантики (вложенные/отрицательные вхождения — «не мержи, просто
  пушни» — НЕ approval; при неоднозначности → HITL-гейт). Вывод approval из
  «пуш»/контекста/молчания — нарушение ⚑1 (process-level; mechanical-контур —
  merge-guard P9, head-pin).
- Если feature-ветка уже запушена — гейт 17 всё равно исполняется полностью:
  push ветки не сокращает и не подменяет гейт.
- `head` в маркере — снимок HEAD на момент подтверждения, ПОСЛЕ ответа
  (head-pin v2, 6.5.0 — уточнение порядка: ответ → head-снимок → маркер).

Анти-паттерн (SKILL.md):

> | **Интерпретировать «пуш»/контекст как approval гейта 17** | ⚑1: merge — только явный ответ с семантикой мержа. «Пуш» = push feature-ветки, не более. Self-approve маркера (создание до явного ответа) — процессное нарушение даже при формально валидном маркере. |

### 4.3. P3 — Статус-дисциплина pipeline

**Где:** `skills/maestro/SKILL.md` (секция «Pipeline status indication»), `manual_docs/reference/pipeline-status.md`.

Дополнение существующего канона (6.5.0):

- **`get` перед анонсом шага:** оркестратор сверяет фактический статус перед
  объявлением следующего шага — исключает рассинхрон нумерации (И-5: анонс «шаги
  14–18» при фактическом шаге 13).
- **Resume-протокол после компакции/обрыва:** восстановление положения — через
  `maestro_pipeline_status(action: "get")` + ledger (план/SDD) + `git log`, не по
  памяти сессии. Загружаемый скилл определяется фактическим состоянием по
  однострочному правилу: `step < 13` → возобновление с шага `step` по канону
  (скилл загрузится точкой использования); `step 13` при неполном ledger →
  executing-plans/subagent-driven по признаку «есть живые task-строки без DONE»;
  `step > 13` → финализация (никаких execution-скиллов) (класс ошибок И-5/ложная
  загрузка executing-plans).
- Строка в чат при step_jump-warning уже обязательна (существующий канон) — не меняется.

Анти-паттерн (SKILL.md):

> | **Resume после компакции по памяти сессии (без get/ledger/git log)** | Память сессии ненадёжна после компакции: пропущенные пункты плана, ложный скилл, неверная нумерация шагов. Восстанавливать положение инструментально: pipeline status `get` + ledger + git log. |

### 4.4. P4 — Batched task-review с ruling

**Где:** `skills/maestro/SKILL.md` (шаг 13; Anti-patterns «Пропускать task-review» —
усиление; -ai баннер и hard-floor формулировки), `skills/maestro/references/hitl-gate-protocol.md`
(3в: hard floor «task-review»), `manual_docs/reference/hitl-gates.md`.

Режимы task-review (шаг 13):

| Режим | Условие | Решение |
|---|---|---|
| **per-task** (канон, default) | все планы; fallback, если условия ниже не выполнены | без вопроса |
| **phase-batched** | план с 5+ задачами, задачи группируются в фазы | -aa/-ai — авто-выбор с ruling; manual — HITL-предложение |
| **final-only** | план с ≤3 задачами | -aa/-ai — авто-выбор с ruling; manual — HITL-предложение |

**Согласование с контрактом авто-режимов (обязательные правки, иначе противоречие):**

- **«Принцип полноты» auto-answer (3в, строки «сама работа (… task-review …)
  выполняется в полном объёме. Любое сокращение процесса — вне auto-answer»)** —
  дополняется: task-review исполняется в полном объёме **по покрытию** (каждый task
  покрыт ревью до гейта 16 — инвариант без исключений); batching меняет
  **гранулярность** (per-task → батч), не факт покрытия — это не «сокращение
  процесса» в смысле принципа, а легальный режим с ruling.
- **-aa-баннер (SKILL.md шаг 1, строки 386–389)** — аналогичная оговорка не
  требуется в самом баннере (баннер ссылается на перечень 3в, не дублирует);
  правится только формулировка принципа полноты в 3в.
- **auto-ai hard floor («task-review»)** — обновляется формулировка: «task-review
  (per-task или batched с ruling — см. шаг 13; молчаливый пропуск — нет)».

**Требования к ruling** (обязательные поля, запись в ledger/журнал решений):

1. Выбранный режим + причина (cost: N диспатчей vs M).
2. Состав батча (какие задачи покрываются одним ревью).
3. Принятый риск: отклонения от спеки обнаруживаются позже → дороже ревью-фиксы
   (пример-прецедент: docker-serve И-3).

Ruling включается в сводку журнала решений на гейте 17 (auto-ai). Молчаливый пропуск
ревью — анти-паттерн (существующая строка усиливается: «...в т.ч. "ради темпа" без
ruling — единственный легальный путь отклонения от per-task это явный ruling»).

**Hard-floor формулировка обновляется:** «task-review» → «task-review (per-task или
batched с ruling — см. шаг 13; молчаливый пропуск — нет)» — в 3в (auto-ai hard floor)
и -ai баннере. Инвариант сохраняется: каждый task покрыт ревью до гейта 16; batching
меняет гранулярность, не факт покрытия.

### 4.5. P5 — Git-гигиена оркестратора

**Где:** `skills/maestro/SKILL.md` (Pre-flight/Обработка сбоев — новый блок
«Git-гигиена оркестратора»; Anti-patterns).

Новый блок:

- **Stash-drop с осмотром:** `git stash` для разблокировки checkout — только с
  предварительным `git stash show -p` и явным решением «что в стэше». Содержимое,
  соответствующее брифу задачи (напр., предписанные spec-sync правки), —
  **незавершённая задача**: вернуть (`stash pop`) и завершить (commit), не
  выбрасывать. Выбрасывание допустимо только для однозначного мусора с фиксацией
  решения строкой в чат.
- **Version bump — только на base-ветке после merge** (существующий канон, шаг 18) —
  дополняется анти-паттерном (дубль-фиксация: И-6).

Анти-паттерны (SKILL.md, новые строки):

> | **Blind stash drop (без `git stash show -p` и явного решения)** | В стэше могут быть незакоммиченные правки по брифу задачи (spec-sync и т.п.) — потеря данных. Осмотр обязателен; правки по брифу = незавершённая задача. |
> | **Version bump на feature-ветке до merge** | Канон (шаг 18): bump — отдельный коммит на base-ветке после merge, до push base. Bump на feature-ветке создаёт ложный merge-scope и нарушает воспроизводимость релиза. |

### 4.6. P6 — 18.5 auto: запрет молчаливого пропуска

**Где:** `skills/maestro/SKILL.md` (шаг 18.5, режим `auto`).

Дополнение режима `auto` (существующий канон покрывает сбои fail-soft строкой):

- Молчаливый пропуск 18.5 в режиме `auto` (без строки «Отчёт не сгенерирован: <причина>»)
  — процессное нарушение, фиксируется в следующем feedback report.
- Осознанный пропуск (не сбой) требует ruling-строки в чат с причиной — по аналогии
  с авто-решениями P1.

User-facing изменений нет (режимы `feedback_report` уже документированы) —
manual_docs не затрагивается.

### 4.7. P7 — Визуальное ревью полного дифа на гейте 17 + сверка коммита шага 12

**Источник:** HITL-фидбек от пользователя в ходе этой фичи (2026-10-21): «рассмотреть
вариант не коммитить в ветку до решения гейта 17, чтобы визуально посмотреть
отличия до коммитов». Анализ: полный диф до merge достижим показом
`git diff <mainline>...HEAD` на гейте (three-dot — конвенция merge-scope, диф
HEAD от merge-base); отказ от per-task коммитов противоречит SDD
(task-review по дифам задач) и создаёт риск И-4-класса (незакоммиченная работа
теряется — прецедент stash-drop). Решение — достичь цели (полное визуальное ревью
до merge) без отказа от инкрементальных коммитов:

**Где:** `skills/maestro/SKILL.md` (шаг 17 — блок «Оркестратор ПОКАЗЫВАЕТ»;
шаг 12 — сверка состава коммита), `skills/maestro/references/hitl-gate-protocol.md`
(Merge-scope protocol), `manual_docs/reference/hitl-gates.md`.

1. **Полный диф на гейте 17.** К existing-показу (`git log --oneline` + тесты +
   issues + версия) добавляется полный `git diff <mainline>...HEAD`:
   - до ~300 строк дифа — полностью в чате;
   - больше — по файлам/секциям с заголовками (и/или выгрузка в файл с путём
     в чате), с предложением «показать конкретные файлы по запросу».
   - Обоснование: гейт 17 — единственная точка approval merge; человек видит
     весь объём изменений до того, как они попадут в main (сейчас — только
     `--stat` в merge-scope протоколе).
2. **Сверка состава коммита шага 12.** Перед коммитом `docs: design + plan for
   <feature-name>` оркестратор проверяет staging: оба файла (spec и plan) в
   `git diff --cached --stat`; каноническое имя коммита. Прецедент: docker-serve
   (6.6.0) — план не закоммичен (файл остался untracked в main-checkout, коммит
   содержал только spec; имя отклонилось от конвенции).
3. Anti-pattern (SKILL.md): «Коммит шага 12 без сверки состава (plan/spec не в
   staging, неканоническое имя)» — пропущенный артефакт пайплайна выпадает из
   merge-scope и истории.

**Отклонено (журнал решений):** «не коммитить до гейта 17» — незакоммиченная
работа хрупка (И-4), task-review требует per-task дифов, диф визуально идентичен;
цель достигается п.1.
