# Design: memory_search — гибридный recall и прозрачность

**Дата:** 2026-09-11
**Статус:** draft
**Категория:** сложная фича (memory layer, плагин `maestro-bootstrap`)
**Ветка:** `feature/memory-search-hybrid`
**Конвенция кодовых ссылок:** ссылки на `memory/index.js` даются по
структурному якорю (обработчик/комментарий/тест) — номера строк не
приводятся (дрейфуют); sqlite.js/recall.js — по проверенным номерам.

## 1. Проблема

Живое тестирование `memory_search` на текущих данных (9 записей, sqlite,
`namespace ai.opencode.maestro`) выявило четыре дефекта качества поиска:

1. **Recall gap.** Запрос «отчёт память» не возвращал запись «Preview-сервер для
   @maestro-memory-report» — тематически релевантную и в пределах date-диапазона.
   Причина подтверждена экспериментом на живой БД:
   - sqlite FTS строит матчинг с **неявным AND** (`storage/sqlite.js:567`,
     `tokens.join(" ")`): `"отчёт"* "память"*` матчит 2 записи; `OR`-матчинг — 6
     записей, включая потерянные «Preview-сервер» и «Обогащение графа
     HTML-отчёта памяти»;
   - русская морфология ломает префикс-матчинг: `память*` ≠ `памяти`, при этом
     `отчёт*` матчит `отчёта/отчёту`;
   - векторная близость «отчёт память» ↔ «Preview-сервер» ниже `min_score` 0.35,
     поэтому без FTS-ноги запись не всплывает.
2. **Parity-разрыв.** Auto-recall (`memory/recall.js`) — чисто векторный
   (`_searchOpts` не несёт `query`, FTS-нога не используется), тогда как
   `memory_search` и `memory_recall_preview` — гибридные. Комментарий в
   `memory/index.js` у формирования search-вызова `memory_recall_preview`
   («тот же путь, что у recall: embed → search (включая FTS-запрос)»)
   фактически неверен.
3. **Empty-filter footgun.** `memory/index.js`, обработчик `memory_search`
   (блок фильтров перед вызовом `search`) применяет их при
   `args.X !== undefined`: пустая строка в аргументе `author` и `date_to=0`
   становятся жёсткими SQL-фильтрами (равенство `author` пустому,
   `time_last <= 0`) → тихое «Ничего не найдено».
   Зафиксировано вживую: `memory_search` с пустым `author` возвращал пусто на
   непустом бакете.
4. **Непрозрачность результата.** В выводе `memory_search`/`memory_recall_preview`
   нет порога `min_score`, scope и контекста пустого результата — пользователь
   не может оценить полноту выдачи.

## 2. Цели / Non-goals

**Цели:**
- Восстановить recall sqlite-гибрида на много-токенных запросах (фикс 1).
- Единый гибридный путь поиска в auto-recall / `memory_search` /
  `memory_recall_preview` (фикс 2).
- Пустые/нулевые фильтры не должны отсекать выдачу (фикс 3).
- Прозрачная шапка результата (фикс 4).

**Non-goals (отдельные задачи при необходимости):**
- Счётчик «N из M» (требует API-change `storage.search` во всех 3 бэкендах).
- Аннотация near-dup хитов, `time_first` в выводе.
- `plainto_tsquery` (неявный AND) в pgvector — русский стемминг (`russian` config)
  уже смягчает морфологию; при желании — отдельная задача.
- Egress raw-запроса в `memory_search` на централизованных бэкендах —
  существующее решение Task 6 (комментарий у передачи `searchOpts.query`
  в `memory/index.js`), не меняется.
- **Не-цель (follow-up):** тот же класс empty-filter footgun в `memory_forget`
  — пустой `author` и `before=0` приводят к `deleteByFilter` с пустыми фильтрами
  (`memory/index.js`, обработчик `memory_forget`). Деструктивного вреда сегодня
  нет; зеркалирование guard — отдельный follow-up.

## 3. Изменения

### 3.1 FTS: AND → OR (sqlite)

`plugins/maestro-bootstrap/memory/storage/sqlite.js:567`:

```js
const match = tokens.map((t) => `"${t.replace(/"/g, '""')}"*`).join(" OR ");
```

- bm25 естественно ранжирует многословные совпадения выше (больше совпавших
  термов → меньшее bm25) — качество AND-совпадений сохраняется, recall растёт.
- FTS-only хиты идут через `fuseRrf` с display-score 0.5. **Единый порог после
  слияния:** к fused-результату применяется пост-фильтр — хиты с display-score
  ниже `min_score` отбрасываются; правило общее для всех трёх путей вызова
  (auto-recall, `memory_search`, `memory_recall_preview`) и применяется в общем
  коде поиска после `fuseRrf`, до возврата вызывающему. Следствие: при
  `min_score > 0.5` FTS-only хиты (display 0.5) не попадают в выдачу;
  существующий фильтр vectorHits по `min_score` в `storage/sqlite.js`
  сохраняется, но перестаёт быть единственной точкой применения порога
  (ранее FTS-only хиты проходили в выдачу независимо от `min_score`).
- `ftsHits.slice(0, top_k)` по bm25 — без изменений; шум от OR компенсируется
  ранжированием.
- Одинарный токен — идентично прежнему.
- FTS5 parse error → существующий try/catch (vector-only fallback) без изменений.
- Только sqlite-бэкенд: pgvector — `plainto_tsquery` + стемминг, qdrant —
  full-text payload; оба не трогаются.

### 3.2 Гибридный auto-recall

`plugins/maestro-bootstrap/memory/recall.js`, `onChatMessage` — все три вызова
`storage.search` (строки ~87, ~93, ~101) получают `query: masked` (результат
`maskTranscript`, уже вычисленный для embed на строке ~58).

- **Очистка FTS-текста от плейсхолдеров (recall.js).** Маскированные строки
  коллапсируют в литерал-плейсхолдер (mask.js); его unicode61-токен присутствует
  в FTS-индексе каждой замаскированной записи (записи маскируются при записи на
  всех бэкендах). После AND→OR (§3.1) плейсхолдер в auto-recall-запросе
  становится OR-термом, матчащим все замаскированные записи, — каждый
  частично замаскированный запрос порождал бы систематический FTS-only шум
  (display 0.5). Поэтому в recall.js перед вызовом `search()` из текста
  FTS-ноги (`searchOpts.query`) вырезаются строки-плейсхолдеры; вход эмбеддера
  не меняется — в `embed()` уходит полный masked query. Если после вырезания
  FTS-текст пуст — FTS-нога не выполняется (поиск деградирует до векторного,
  существующий fallback).

**Security (инвариант SECURITY.md «raw не уходит на сервер»):**
- На sqlite (локальный) FTS исполняется локально; masked идентичен raw лишь для
  текста без конфиденциальных вхождений и без фрагментов, похожих на секреты
  (паттерн «ключ-равно-значение» маскируется в том числе при пустом списке
  confidential-паттернов). Кроме того, записи маскируются при записи на всех
  бэкендах, поэтому «сырой» запрос и так не совпал бы с текстом записей в FTS.
  Вывод не меняется: единая маскировка безопасна для egress и практически не
  теряет качество sqlite-FTS.
- На централизованных бэкендах (pgvector/qdrant) текстовый запрос уходит на
  сервер → передаётся ТОЛЬКО замаскированный текст. Полностью замаскированный
  запрос (однострочный → `[confidential]`) → существующий short-circuit
  (строка ~59) срабатывает до поиска.
- Неиспользуемое ветвление по типу бэкенда не вводится: маска — uniform-правило.

### 3.3 Guard пустых фильтров

`plugins/maestro-bootstrap/memory/index.js`, обработчик `memory_search`
(блок фильтров перед вызовом `search`):

- `author`: фильтр применяется только если аргумент — строка, непустая после
  trim (ровное сравнение в SQL без изменений).
- `date_from`/`date_to`: фильтр применяется только если значение — конечное
  число `> 0` (epoch 0 / отрицательные / NaN / не-числа — «не заданы»).

### 3.4 Шапка результата

`plugins/maestro-bootstrap/memory/index.js` (обработчик `memory_search` —
ветки вывода после фильтрации; `memory_recall_preview` — ветка пустого
результата и ветка вывода):

- **Единое правило для обоих инструментов.** X = `config.min_score`.
  Y — эффективный scope (результат применения membership, а не запрошенный
  дефолт): branch-membership применено → `branch`; поиск плоский (mainline не
  разрешён либо явно запрошен `project`) → `project`. Значение `branch_context`
  задаёт только запрашиваемый scope; при неразрешённом mainline печать
  `branch` вводила бы в заблуждение. N = `filtered.length` — число записей
  после scope/membership-фильтров (post-membership count).
- `memory_search`:
  - пустой результат: `Ничего не найдено в памяти (порог min_score X, scope Y).`
  - непустой: второй строкой (после disclaimer) —
    `Найдено: N (порог min_score X, scope Y)`.
- `memory_recall_preview`:
  - пустой: `Ничего не найдено.` → `Ничего не найдено (порог min_score X, scope Y).`
  - непустой: `Найдено: N (порог min_score X, scope Y)`.
- Заголовок «порог min_score X» соответствует фактическому поведению:
  благодаря единому пост-фильтру (§3.1) в выдаче не бывает хитов с
  display-score ниже `min_score`; при `min_score > 0.5` FTS-only хиты не
  показываются вовсе.
- Short-circuit полностью замаскированного запроса (`Ничего не найдено.`)
  остаётся без изменений — поиск не выполнялся, порог не применим.

## 4. Тесты (TDD: RED → GREEN)

- `plugins/maestro-bootstrap/memory/storage/sqlite.test.js`:
  - запись с частичным совпадением токенов (1 из 2) находится по 2-токенному
    запросу (ранее — нет);
  - запись с полным совпадением ранжируется выше частичного.
- `plugins/maestro-bootstrap/memory/recall.test.js`:
  - auto-recall передаёт masked query (с вырезанными плейсхолдерами — см. §3.2):
    FTS-only хит (вектор ниже min_score, текст матчит) попадает в буфер /
    `systemBlock` только при display-score ≥ min_score;
  - явный захват аргументов: `embed()` вызван с полным masked query;
    `opts.query` в `search()` равен masked query без строк-плейсхолдеров
    (токен плейсхолдера отсутствует в FTS-тексте) — без захвата утверждение
    «передаёт masked query» не защищено тестом;
  - полностью замаскированный запрос → short-circuit (буфер пуст) — существующий
    тест сохраняется.
- `plugins/maestro-bootstrap/memory/index.test.js`:
  - пустой `author` и `date_to=0` не применяют фильтр (запись находится);
    guard-варианты: `date_from=0`, отрицательные даты, `author` — строка из
    одних пробелов → фильтр не применяется;
  - формат шапки: непустой результат содержит `Найдено: N`; пустой — строку с
    порогом и scope (обновить существующие формат-ассерты: тест M-4 по имени
    и др.).
- Branch-scope × FTS interop: FTS-only хит записи вне branch-context (head не
  входит в membership-набор) → отброшен; FTS-only хит merged sibling (входит в
  membership) → сохранён.
- Единый порог: при `min_score > 0.5` FTS-only хиты (display 0.5) отсутствуют в
  выдаче на всех трёх путях (auto-recall, `memory_search`,
  `memory_recall_preview`); при `min_score ≤ 0.5` — присутствуют.
- Порядок fusion: хит, присутствующий в обеих ногах (вектор + текст),
  ранжируется выше text-only хита.
- Регресс: `node --test plugins/maestro-bootstrap/index.test.js` (176) и
  `npm run test:memory` (478) зелёные.

## 6. Риски и откат

- OR-матчинг увеличивает число FTS-only хитов → компенсируется bm25-ранжированием
  и top_k-капом RRF; риск шума оценён как низкий (локальный бэкенд, top_k ≤ limit).
  Ограничение: OR-нога без stopword-фильтрации матчит частые токены полных
  сообщений — текстовая нога почти всегда непуста, а text-only хит №1
  (1/61) в RRF тяжелее векторного хита №2 (1/62); митигация — тесты §4 и
  единый порог (§3.1).
- **Ожидания по эффекту:** практический выигрыш §3.1/§3.2 — sqlite-центричен.
  На централизованных бэкендах текстовая нога для длинных сообщений часто пуста
  (pgvector: `plainto_tsquery` — неявный AND; qdrant: `full_text_match` по
  всему тексту запроса). Паритет, обеспечиваемый спеком, — структурный
  (единый код-путь и единая маскировка), а не паритет ранжирования результатов
  между бэкендами.
- Гибридный auto-recall меняет состав автоинжект-контекста (FTS-only хиты с
  score 0.5 могут попадать в `systemBlock`) — риск умеренный, покрывается
  тестами recall и QA-чеклистом `docs/testing/maestro-sandbox-checklist.md`.
- Откат: 4 независимых изменения в 3 файлах — частичный revert по патчам
  без пересборки схемы (схема БД не меняется).
