# Спека: дефолты в HITL-гейтах (P1.3)

- **Дата:** 2026-09-03
- **Ветка:** `feature/hitl-gate-defaults`
- **Категория:** Сложная фича (полный pipeline)
- **Источник:** TODO п.77 (maestro должен вести пользователя «за руку», предлагая очевидные решения, а не ждать указаний) — реализуемая инкрементальная часть, без структурного lite-режима (P3).

## 1. Проблема

Каждый HITL-гейт задаёт открытый вопрос «что делаем?» с вариантами (a)/(b)/(c).
В большинстве случаев у оркестратора есть доказательная рекомендация (вердикт
ревью, состояние тестов, категория по матрице, открытые issues). Пользователь
вынужден обдумывать с нуля вместо быстрого подтверждения очевидного. Это —
когнитивная нагрузка на HITL на подтверждаемых шагах и подготовка почвы для
будущего lite-режима (P3).

## 2. Зафиксированные решения (сессия 2026-09-03)

| # | Решение |
|---|---|
| 1 | Новый пункт протокола HITL: каждый question **decision gate** (шаги 2, 7, 10, 12, 17) сопровождается рекомендуемым вариантом по умолчанию с кратким обоснованием; HITL подтверждает одной буквой или меняет выбор |
| 2 | Формат предложения: «рекомендую (a) X, потому что Y — подтвердите или выберите иное» (не открытый вопрос) |
| 3 | Структурированные варианты (a)/(b)/(c) сохраняются — дефолт лишь помечает рекомендованный вариант, не отменяет меню |
| 4 | Не затрагиваются (перечень закрыт на Revise-цикле): гейты 1 (маршрут) и 1.5 (режим) — предпочтения пользователя, «правильного» ответа нет; гейты D2/D6/D7 (багфикс-гипотезы) — контентные решения; плато и особый случай confidential на шаге 10 — контекстные решения; security-гейты (8.6, Security Review Точка 2, File access control) — решения об уровне риска; дефолт неприменим |
| 5 | Дефолты специфицируются для каждого decision gate (таблица ниже); обоснование ссылается на фактическое состояние пайплайна |
| 6 | P1.4 (эвристика «диф одним предложением» + проектная матрица) — ОТДЕЛЬНЫЙ цикл; здесь дефолт гейта 7 = категория по матрице сигналов |

## 3. Источники дефолтов по гейтам

| Гейт | Дефолт | Источник обоснования |
|---|---|---|
| 2 (старт) | (a) да | маршрут (шаг 1) и режим (шаг 1.5) только что выбраны пользователем — продолжение согласовано с предыдущими выборами |
| 7 (категория) | (a) или (b) по матрице | категория из матрицы сигналов (после P1.4 — + эвристика, в этом цикле — только матрица) |
| 10 (spec-гейт) | (a) Approve | вердикт ревью approve / fast-path (P1.2) |
| 12 (plan-гейт) | (a) Approve | quality-проверки плана (шаг 11) пройдены |
| 17 (pre-PR) | (a) Approve merge | только follow-up issues («не блокирует»), тесты зелёные, secret-scan (SEC-3) — 0 находок |

Правила применения дефолтов:

1. **Отрицательные случаи (общее правило).** Дефолт предлагается только при
   выполнении условия-источника из таблицы. Если условие НЕ выполнено — дефолт
   НЕ предлагается, вопрос остаётся открытым, без рекомендации. Примеры: шаг 10 —
   вердикт ревью revise/reject или открытые Critical/Important; шаг 17 — открытые
   блокирующие issues, красные тесты или находки secret-scan (SEC-3).
2. **Закрытый перечень.** Дефолты применяются ТОЛЬКО к пяти перечисленным вопросам
   decision gates (2, 7, 10, 12, 17). Все прочие HITL-вопросы — гейты 1/1.5
   (предпочтения), D2/D6/D7 (контентные), плато и особый случай confidential на
   шаге 10, security-гейты (8.6, Security Review Точка 2, File access control) —
   дефолтов НЕ имеют.
3. **Гейт 2.** На момент гейта известно лишь то, что маршрут (шаг 1) и режим
   (шаг 1.5) только что выбраны; baseline-состояние неизвестно — pre-flight
   запускается на шаге 3, ПОСЛЕ ответа «(a) да». Дефолт (a) сохранён ради
   единообразия набора decision gates и задела под lite-режим (P3), хотя
   обоснование близко к тавтологии (последняя точка отмены до изоляции).

## 4. Изменения по файлам

### 4.1. `skills/maestro/SKILL.md` — секция «HITL Gate Protocol»

В протоколе добавить пункт **3а** — сразу после пункта 3 («Дождаться ответа»),
до пункта 4 («После ответа»); нумерация существующих пунктов 0–4 НЕ меняется:

> **Дефолты в decision gates (P1.3).** Для decision gates (шаги 2, 7, 10, 12, 17)
> оркестратор сопровождает вопрос рекомендуемым вариантом по умолчанию с кратким
> обоснованием: «рекомендую (a) X, потому что Y — подтвердите или выберите иное».
> HITL подтверждает дефолт ТОЛЬКО явной буквой варианта (или явно выбирает иное);
> «continue»/«давай»/«ок» дефолт НЕ подтверждают (см. пункт 3). Структурированные
> варианты (a)/(b)/(c) сохраняются — дефолт помечает рекомендованный вариант, не
> заменяет меню. Дефолт предлагается ТОЛЬКО на этих пяти вопросах; все прочие
> HITL-вопросы — гейты 1/1.5 (предпочтения пользователя), D2/D6/D7 (контентные
> решения по гипотезе), плато и особый случай confidential на шаге 10,
> security-гейты (8.6, Security Review Точка 2, File access control) — дефолтов
> НЕ имеют. Если условие-источник дефолта НЕ выполнено — дефолт НЕ предлагается,
> вопрос остаётся открытым, без рекомендации. Источники дефолтов: шаг 2 — маршрут
> и режим только что выбраны (шаги 1/1.5); шаг 7 — категория по матрице сигналов;
> шаг 10 — вердикт ревью approve / fast-path (P1.2); шаг 12 — quality-проверки
> плана (шаг 11) пройдены; шаг 17 — только follow-up issues («не блокирует»),
> тесты зелёные, secret-scan (SEC-3) — 0 находок.

Дополнительно заменить заголовочную строку секции «HITL Gate Protocol» — термин
«decision gates» унифицируется (расширяется с 10/12/17 до 2/7/10/12/17):

- Было: «Decision gates (шаги 10, 12, 17) — явный вопрос с вариантами (a)/(b)/(c).
  Остальные gates в pipeline (шаги 1, 2, 7, D2, D6, D7) следуют тому же
  протоколу, но с вариантами, специфичными для каждого gate (см. inline-описание
  в pipeline).»
- Стало: «Decision gates (шаги 2, 7, 10, 12, 17) — явный вопрос с вариантами
  (a)/(b)/(c), сопровождаемый рекомендуемым дефолтом (п. 3а). Остальные gates в
  pipeline (шаги 0, 1, 1.5, D2, D6, D7, а также плато и особый случай на шаге 10
  и security-гейты 8.6 / Security Review Точка 2 / File access control) следуют
  тому же протоколу, но без дефолтов и с вариантами, специфичными для каждого
