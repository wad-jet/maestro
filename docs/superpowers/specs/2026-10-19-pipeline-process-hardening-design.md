# Spec: Укрепление процесса пайплайна (late-entry, режим-контракт, guards, дисциплины)

**Дата:** 2026-10-19
**Статус:** черновик (до Spec Review)
**Категория:** Сложная фича (по матрице: 10+ файлов; без DB/public API/breaking/новых модулей)
**Версия:** 6.1.0 → **6.2.0** (minor: новые процессные правила скилла + функциональность плагина; маппинг §3 project-context)

## 1. Контекст и проблема (инцидент)

В сессии 2026-10-19 (`/maestro-init -aa`) были пропущены шаги пайплайна 0–13, 16, 18–18.5:
оркестратор вошёл в пайплайн **после** того, как реализация была выполнена в сессии, и
перескочил к шагу 14 («работа уже сделана»). Коммит лёг **прямо в main** без ветки и гейта 17
(⚑1), bump версии не выполнен (changelog `[Unreleased]` пуст), финальное ревью и feedback
report пропущены. Повторный «исправленный» проход тоже имел отклонения: гейт 7b не задан,
ревью выполнено `general`-сабагентом без доступа к файлам (ревью по самоописанию), строка
версии на гейте 17 не показана, маркер гейта 17 создан без полей `gate`/`decision` из канона.

Корневые причины (разбор от 2026-10-19):
1. **Нет протокола позднего входа** — пайплайн предполагает вход до начала работы; ситуация
   «реализация уже существует» не описана ни в SKILL.md, ни в hitl-gate-protocol.md.
2. **`-aa` истолкован как «пропускать шаги»** — канон говорит обратное («полнота процесса»),
   но контракт режима не surfaced-ится при старте прогона.
3. **Merge-guard не ловит прямой `git commit` в mainline** — гард только `git merge` /
   `git push`; коммит на main проходит свободно.
4. **`maestro_pipeline_status` — только индикатор** — прыжок 0→14 принимается молча.
5. **Рассинхрон канона и кода по маркеру гейта 17** — SKILL.md требует
   `{"sessionID","ts","gate":17,"decision":"a"}`, merge-guard валидирует только
   `{sessionID, ts}`.

## 2. Цели

- **R1** — протокол позднего входа: при старте пайплайна, если изменения задачи уже
  существуют, оркестратор обязан остановиться и получить HITL-решение (полный проход с
  ретро-дизайном / откат и заново / явный отказ от пайплайна). Пропуск шагов молча
  недопустим.
- **R2** — баннер-контракт режима: при старте с `-aa`/`-ai` оркестратор обязан вывести
  контракт режима (что выполняется полностью, какие гейты авто, что всегда HITL).
  Молчаливое расхождение с контрактом = процессное нарушение.
- **R3** — guard прогрессии `maestro_pipeline_status`: forward-прыжок через канонические
  шаги → warning в ответе тула + log (non-blocking).
- **R4** — guard прямых коммитов в mainline (`git commit` при текущей ветке main/master
  без маркера гейта 17) + валидация полей `gate`/`decision` маркера. Конфиг
  `merge_guard.commit_guard`: `warn` (default) / `deny` / `off`.
- **R5** — дисциплина финального ревью (шаг 16): ревью выполняет реальный `reviewer`-
  сабагент с доступом к фактическому дифу; «ревью по описанию без чтения файлов» —
  anti-pattern, вердикт недействителен.
- **R6** — дисциплина версии: на гейте 17 строка версии обязательна при
  `Версионирование: да` (включая решение «без bump» с обоснованием); шаг 18 исполняет
  решение гейта, молчаливый пропуск bump — нарушение.

## 3. Non-goals

- Per-session pipeline status (текущее состояние — глобальный singleton; мульти-сессии —
  отдельная фича, follow-up).
- Защита от `git commit` в подкомандах (`&&`-цепочках с `git merge` уже покрыта
  субстринг-детекцией merge-ветки; коммит в цепочках с merge/push дополнительно
  блокируется существующим гардом).
- Remote-side enforcement (server hooks, CI) — вне scope.
- Изменение механики ralph loop, авто-режимов (перечень 3в не расширяется).
- Изменение инвариантов ⚑1–4 (усиливается только исполнение ⚑1).

## 4. Ограничения

- Инварианты ⚑1–4 не ослабляются (invariants.md); фича усиливает исполнение ⚑1.
- Все хуки плагина — `try/catch`-guarded, глобальные (не scoped к maestro-сессиям).
- Merge-guard — fail-closed: любая аномалия проверки → deny (для deny-механик).
- Без новых npm-зависимостей (чистый Node ESM; git — через `child_process`).
- Russian — рабочий язык доков и сообщений.
- Docs-drift (`maestro-install/docs-drift.test.mjs`, в `npm test`) — должен остаться зелёным;
  bump версии синхронизирует все ссылки (package.json, project-context §3, AGENTS.md, доки).
- Канон маркера гейта 17 (SKILL.md) — источник правды для схемы маркера.

## 5. Дизайн

### R1. Протокол позднего входа (SKILL.md)

**Точка вставки:** детекция — шаг 0 (Load Project Context), подпункт **«Late-entry
check»** (read-only: только `git status`/`git log`). Действует для всех маршрутов
(feature/bugfix/spike). **Момент вопроса:** auto-режимы — вопрос сразу после
авто-определения маршрута на шаге 1 (без пакета; маршрут уже известен и route-adapted
вариант (a) сформирован); manual — late-entry-вопрос **пакетом** с вопросом маршрута
на шаге 1 (один вызов question tool; протокол «пакетов» — hitl-gate-protocol.md),
текст варианта (a) финализируется после выбора маршрута.

**Механика:**
1. Триггер детекта — **любой** из сигналов:
   - (a) `git status --short` не пуст (uncommitted изменения, потенциально относящиеся
     к задаче);
   - (b) текущая ветка содержит коммиты вне базового mainline: `git log --oneline
     <mainline>..HEAD` не пуст (mainline — main/master);
   - (c) **саморефлексия оркестратора по контексту сессии:** реализация по задаче
     (правки/коммиты) выполнялась в этой сессии **до** входа в пайплайн (сигнал
     процессный, не git-механический; покрывает сценарий «коммит прямо в main,
     working tree чист»).
2. Если сигналов нет — ничего не происходит (основной поток).
3. Если есть — **обязательный HITL-вопрос** (контентный вопрос). Вариант (a)
   адаптирован под маршрут шага 1:
   > Обнаружены уже выполненные изменения по задаче (N файлов / M коммитов до старта
   > пайплайна). Пайплайн выполняется полностью; как поступить с готовой реализацией?
   > **feature:** (a) Полный проход с ретро-дизайном — классификация (шаг 7),
   >     дизайн/спека по факту, SDD = верификация существующей реализации (diff
   >     сверяется с дизайном), шаги 14–18.5 как обычно
   > **bugfix:** (a) Полный проход с ретро-анализом — D1–D7 (гипотеза/probe по факту
   >     фикса), план, SDD = верификация, шаги 14–18.5 как обычно
   > **spike:** (a) Завершить spike-проход с выводом-рекомендацией по факту
   >     (throwaway-код не коммитится; мержа нет)
   > (b) Откатить изменения (reset/checkout) и пройти пайплайн с чистого листа
   > (c) Явно продолжить без пайплайна — оркестратор фиксирует отказ в чате;
   >     последующая работа — вне pipeline (без артефактов pipeline)
4. **Режимы:** в manual и auto-answer — всегда HITL (контентный вопрос). В auto-ai —
   консервативный дефолт **(a)** (более полный путь) с фиксацией в журнал решений;
   варианты (b)/(c) — только HITL.

**Anti-pattern** (новая строка в таблице Anti-patterns):
- **«Вход в пайплайн post-factum с готовой реализацией и перескок к шагу 14»** —
  Late-entry check (шаг 0) обязателен; готовая реализация не отменяет шаги 0–13:
  классификация, дизайн/спека по факту, SDD-верификация. Молчаливый перескок —
  нарушение полноты процесса во всех режимах.

**Производные места:** `references/hitl-gate-protocol.md` — в §3в (режимы запуска)
примечание: late-entry-вопрос — контентный, не входит в авто-список (auto-ai —
консервативный дефолт (a)); `manual_docs/reference/hitl-gates.md` — секция
«Поздний вход в пайплайн».

### R2. Баннер-контракт режима (SKILL.md + hitl-gate-protocol.md)

**Точка:** шаг 1 (выбор маршрута) — сразу после определения маршрута, если установлен
флаг `-aa`/`-ai`.

**Формат (обязательная строка в чат; per-mode, т.к. семантики режимов разные):**

`-aa` (auto-answer):
> `[auto-answer] Контракт режима: все шаги выполняются полностью;
> авто-принятие — только гейты из перечня 3в (с условием-источником);
> всегда HITL — по перечню 3в «Никогда не авто» (+ 7b: аппрув короткого
> дизайна, контентный вопрос). Любое сокращение процесса — вне режима.`

`-ai` (auto-ai):
> `[auto-ai] Контракт режима: все шаги выполняются полностью; ИИ решает
> маршрутные/контентные решения с доп. анализом (журнал решений, сводка на
> гейтах 10/17); жёсткий пол: TDD, task-review, SEC-3, тесты (шаг 15),
> security-гейты, ⚑1–4; всегда HITL — по перечню 3в «Никогда не авто»
> (+ late-entry варианты (b)/(c) — только HITL). Консервативный fallback —
> более полный путь. Любое сокращение процесса — вне режима.`

Оба баннера ссылаются на канонический never-auto-список 3в, **не дублируют** его
текстом (полнота списка — в каноне; баннер не устаревает при расширении списка).

**Канон:** `hitl-gate-protocol.md` §3в — новый подпункт: баннер обязателен при старте
с авто-флагом; отсутствие баннера = фиксация нарушения в feedback report. Список
авто-гейтов в баннере — из таблицы 3в (не дублировать текстом: «по перечню 3в»).

**Производные места:** `manual_docs/reference/hitl-gates.md` (секция режимов).

### R3. Guard прогрессии `maestro_pipeline_status` (pipeline-status.js)

**Семантика:** non-blocking warning. Модуль ведёт каноническую последовательность шагов
и сравнивает переходы.

**Каноническая последовательность** (константа модуля):
`-1, 0, 1, 1.5, 2, 3, 4, 5, 6, 7, 7b, 7d, 8, 8.5, 8.6, 9, 10, 10b, 11, 12, 12a, 13, 13f, 14, 15, 15a, 16, 17, 18, 18.5`
(подшаги 7b/7d/10b/12a маппятся на родительские: 7, 7, 10, 12 — только для сравнения
позиций; 13f/15a — полноценные элементы последовательности). Шаг, **отсутствующий**
в последовательности (например, новый подшаг в будущем) → без warning + `log.info`
(неизвестный шаг не блокирует видимость; трекер фиксирует его позицию как есть).

**Правила:**
1. `set` с шагом **впереди** последнего зафиксированного: если между ними в канонической
   последовательности есть ≥1 промежуточный шаг → ответ тула содержит
   `{"ok":true,"warning":"step_jump","skipped":[...]}` + `log.info("pipeline_status:step_jump", ...)`;
   без промежуточных → `{"ok":true}`. Нотация `skipped` — **полная каноническая**
   (включая подшаги 7b/7d/10b/12a/15a как отдельные элементы; маппинг на родителей
   используется только для сравнения позиций, не для вывода).
2. `set` **назад** (fix-loop, re-review, 10b→9) или повтор того же шага — без warning
   (легальные циклы).
3. `clear` — сброс трекера (следующий `set` — без warning, «первый после clear»).
4. Впервые установленный шаг (после clear/старта) — без warning.
5. Warning не блокирует и не меняет состояние (шаг фиксируется как есть).
6. **Обязанность оркестратора:** на `warning: step_jump` — ответить **одной строкой
   в чат** (обоснование: легальный skip-path по канону / ошибка → откат к пропущенному
   шагу). Строка канонизируется в блоке «Pipeline status indication» SKILL.md
   (~стр. 215) и в description тула `maestro_pipeline_status`.

**Исключения (легальные прыжки):** warning выдаётся **для всех** forward-прыжков —
в т.ч. для задокументированных skip-путей (Bounded 7→13, bugfix 6→11, fast-track).
Обоснование: warning — это механизм **видимости** (оркестратор видит прыжок и
объясняет его в чат одной строкой, например `[auto-answer] Bounded: шаги 8–10
пропущены (категория на шаге 7) — нормальный skip-path`). Неинформативного
исключения не делаем (YAGNI): оркестратор обязан отреагировать на warning строкой в чат.

**Производные места:** `manual_docs/reference/pipeline-status.md` — секция
«Progression warning»; тесты `pipeline-status.test.js`.

**Известное ограничение (follow-up, не в scope):** состояние глобальное
(модуль-level), не per-session — две параллельные primary-сессии разделяют трекер;
warning может быть ложным для второй сессии. Фиксируется в spec/доках.

### R4. Commit guard + валидация маркера (merge-guard.js, core.js)

#### R4a. Детекция `git commit`

- Новый экспорт `detectCommitCommand(command)`: `true` при `/git\s+commit(\s|$)/`
  (не матчит `git commit-graph`/`git commit-tree`), с тем же исключением (команда,
  начинающаяся с `echo` → `false`). Отдельная функция (не расширение
  `detectGuardCommand`) — commit-ветка требует git-запроса (текущая ветка),
  который не нужен для merge/push.
- **Substring-детекция переключения на mainline (конвенция merge-ветки):** если
  команда **также** содержит `git\s+(checkout|switch)\s+...main|master` (например,
  `git checkout main && git commit -am "…"`) → эффективная ветка = mainline:
  git-запрос текущей ветки **не отменяется**, а дополняется (истинная ветка может
  быть иной до выполнения; effective = max(текущая, переключаемая)).
- **Workdir:** git-запрос выполняется в `event.input.workdir` (если задан), иначе `root`.
  Это покрывает worktree: `git -C <workdir> branch --show-current`.
- **Ограничения детекции (документируются):** false-negative — `git switch -c main`
  (создание ветки, не переключение) и переключение без commit в одной команде;
  false-positive — `git checkout main -- path` (восстановление файла с main) в
  сочетании с `git commit` → эффективная ветка считается mainline. По аналогии
  с задокументированным ограничением bare `git push` push-гарда.

#### R4b. Проверка ветки и маркера

- Новый экспорт `checkCommitGuard(command, workdir, root, sessionID, nowMs, conf, mode)`:
  1. Эффективная ветка: substring-детекция переключения (R4a) → mainline; иначе
     `git -C <workdir> branch --show-current` (execFileSync, timeout 3 c, try/catch).
     Разграничение исходов git-запроса (fail-closed-совместно с §4):
     - exit 0 + **пустой** вывод (detached HEAD) → `{allow:true, reason:"branch_unknown"}`
       (детерминированное состояние; задокументированное ограничение);
     - **исключение/таймаут** → deny-режим: `{allow:false, reason:"guard_error"}`
       (fail-closed, как merge-guard); warn-режим: `{allow:true, reason:"guard_error"}`
       + log (не блокируем легитимные коммиты при сбое детекта).
  2. Ветка ∈ {main, master} (mainline-набор совпадает с push-гардом) →
     `checkMergeMarker(root, sessionID, nowMs, conf)` (переход к R4c).
  3. Иная ветка → `{allow:true, reason:"not_mainline"}`.
- Интеграция в `core.js` (execute.before, shell): после merge-ветки гарда —
  `if (commitGuardMode !== "off" && detectCommitCommand(...))` → `checkCommitGuard`;
  результат `allow:false`:
  - mode `deny` → throw `[commit-guard:deny]` (аналог merge-guard);
  - mode `warn` → **не** блокируем: `log.warn("commit_guard", {action:"warn", ...})`
    + **system-notice в сессию** (паттерн fail-loud memory-модуля: per-session context-hook
    с текстом-напоминанием про гейт 17; один notice на сессию — Set warned sessions).

#### R4c. Усиление валидации маркера (R4-маркер)

- `checkMergeMarker`: после проверки `sessionID`/`ts` — новые проверки:
  `data.gate !== 17` или `data.decision !== "a"` → `{allow:false, reason:"marker_incomplete"}`.
- Канон (SKILL.md шаг 17) уже требует `{"sessionID","ts","gate":17,"decision":"a"}` —
  код доводится до канона. Старые неполные маркеры → deny (оркестратор пересоздаёт —
  одна команда, TTL не истечёт).

#### R4d. Конфиг

- `merge_guard.commit_guard`: `"warn" | "deny" | "off"`, **default `"warn"`**
  (согласовано с пользователем 2026-10-19: не ломать легитимные коммиты вне maestro,
  видимость — через notice). Не-валидное → soft-fallback `"warn"` + пометка в log.
- `resolveMergeGuardConf` расширяется: `{enabled, ttlSec, commitGuard}`.

**Производные места:** `manual_docs/reference/config.md` (ключ), `manual_docs/how-to/install-maestro.md`
(если там описан merge-guard) — сверить; тесты `merge-guard.test.js`, `index.test.js`.

### R5. Дисциплина финального ревью (SKILL.md, шаг 16)

- Шаг 16: новый подпункт — **«Достоверность ревью»:** финальное ревью выполняется
  реальный `reviewer`-сабагент (а также `sonnet` при параллельном) **с фактическим
  доступом к дифу и файлам ветки** (промпт диспатча содержит base..HEAD; сабагент
  читает diff/файлы сам). Ревью по описанию оркестратора без чтения фактического дифа
  **не является ревью**: вердикт недействителен, требуется re-dispatch.
- **Anti-pattern** (новая строка): **«Ревью по описанию: диспатч ревью-промпта без
  доступа сабагента к фактическому дифу/файлам (или с запретом читать файлы)»** —
  вердикт такого ревью не принимается на гейте 17 (issue: «review невалиден»).

### R6. Дисциплина версии (SKILL.md, гейт 17 + шаг 18)

- **Гейт 17:** новый обязательный подпункт — **«Строка версии (обязательная при
  §3 `Версионирование: да` **и наличии правил версионирования в контексте**)»:**
  - формат: `Версия: <текущая> → <предлагаемая> (правило: <тип изменения → уровень>)`
    — как сейчас (строки 1059–1062), НО теперь: отсутствие строки при включённом
    версионировании с правилами = **неполный гейт** (оркестратор возвращает подготовку
    гейта); при `Версионирование: да` **без** правил в контексте — строка
    `Версия: <текущая> → без bump (обоснование: нет правил версионирования

## 7. Риски

- **R4a ложные срабатывания:** `git commit` внутри коммит-хуков/скриптов (например,
  `git commit` в `maestro-install.sh`-подобных сценариях) — в warn-режиме (default)
  это лишь notice; deny-режим — opt-in осознанно.
- **R4b detached HEAD:** `branch --show-current` пуст → guard не срабатывает
  (задокументированное ограничение; коммит в detached HEAD — редкий сценарий,
  mainline-коммит обычно в named-ветке).
- **R3 ложные warning** при параллельных сессиях (глобальный трекер) — follow-up,
  задокументировано.
- **R4c строгость маркера:** после деплоя старые неполные маркеры (TTL 600 c) →
  короткий период deny до пересоздания — приемлемо (маркер создаётся одной командой).
- **TTL маркера vs deny-режим (шаг 18):** если между (a) на гейте 17 и bump-коммитом
  на main (шаг 18) пройдёт >TTL (600 c, ручная пауза), commit-guard в deny-режиме
  заблокирует легитимный bump-коммит. Корректное поведение — пересоздание маркера
  **только** по новому явному (a) на гейте 17 (автоматическое пересоздание без HITL =
  дрейф ⚑1). Зафиксировано; warn-режим (default) не блокирует.
