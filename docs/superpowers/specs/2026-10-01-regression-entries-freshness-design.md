# Спека: актуальность regression-entries при прогоне пайплайна (#103, 4.19.0)

Дата: 2026-10-01. Автор: primary (brainstorm + HITL-решения). Статус: draft.

## Контекст

TODO:23 / роадмап #103 (Волна 3): «актуальность regression-entries. M6:
обновление entries при прогоне пайплайна (на шаге ревью), а не отдельной
рутиной».

Данные (аудит 2026-10-01, репо maestro-agent): entry
`regression/entries/2026-09-18-subagent-resilience.md` (фича от 2026-09-18)
устарел после 6 следующих фич (4.14.0 → 4.18.0):

1. сценарий `run: node --test plugins/maestro-bootstrap/index.test.js → 171 pass`
   — тестов сейчас 266 (их добавляли docs-drift, benchmark, memory-фичи);
   `@regression full` даст false-fail (не регрессия, а старое ожидание);
2. сценарий `run: grep -in "3 попыток" skills/maestro/SKILL.md → 0` — 4.14.0
   вынесла детали SKILL.md в `references/*.md`; проверка проходит «важно»
   (текст перенесли), а не потому, что anti-loop работает.

Сегодня чужие (не текущей фичи) entries обновляются **никогда**: шаги 11/12a/13f
работают только с entry текущей фичи; `@regression` — standalone, выполняет
сценарии, но не обновляет entry.

## Дизайн-решения

### D1. Механика — расширение шагов 11 + 13f (HITL, вариант (a))

Не новый шаг, не новая команда, не новый механизм (M5/M6): расширяются
существующие regression-хуки пайплайна.

**Шаг 11 (анализ, план):** оркестратор дополнительно определяет
**«под угрозой» entries (cross-entry selection)** — механически:

- источник: `regression/entries/` (только `status: active` — мутации,
  см. D5; `verified` — read-only чек, см. D5), entry текущей фичи
  исключается;
- **цель сценария** (C1-фикс) — каскад извлечения, repo-relative:
  1. поле `path` сценария (файл-часть, без `:line`);
  2. если `path` нет — аргумент команды `run:`, резолвящийся в
     существующий файл/каталог (для `grep`/`sed` — **последний**
     file-аргумент, не паттерн; `node --test <file>` — файл;
     `npm run <script>` — путь к манифесту сервиса/корня);
  3. если ни `path`, ни file-аргумент `run:` — сценарий **не
     выбирается** (known limitation: prose-сценарии без машинных
     целей; см. D6). Module-хинты вида «`(SKILL.md):`» не матчатся
     (не полные пути).
- пересечение: цели сценариев entry ∩ file-set плана (файлы задач плана
  + `## Project Context Changes` + **path-резолвящиеся** цели
  risk-анализа; допустимы каталог-префиксы, напр.
  `plugins/maestro-bootstrap/`); имена модулей без path-резолва в
  file-set не входят;
- пересечения нет → хук no-op (ни в 11, ни в 13f);
- cap: **≤ 5 entries** за прогон; порядок выбора — по числу пересекающихся
  сценариев (desc), тир — по `added` (desc). Остаток — фиксируется в
  выводе 13f + progress-логе (feedback-report подхватит из сессии) —
  не блокирует.

Результат (список «под угрозой» + пересекающиеся сценарии) фиксируется
**в плане** (секция `## Cross-Entry Reconciliation`, коммитится на 12a,
видна на гейте 12) и передаётся в 13f.

**Шаг 13f (reconciliation, после реализации):** существующая сверка entry
текущей фичи (без изменений) + **cross-entry reconciliation**: 13f
**пересчитывает** пересечение по фактическому диффу (`git diff <base>...`)
и берёт **union** (список плана ∩ фактический дифф) — защита от
недовыборки при дрейфе имплементации от плана (M8). Механика сверки и
HITL — в главе `references/regression-registry.md`, «Cross-entry
reconciliation (13f)» (указатель добавляется в скелет 13f).

### D2. Что сверяется (факты, без HITL)

Два класса проверок (по выбранному entry, D5):

- **Existence — по ВСЕМ automated-сценариям** выбранного entry:
  1. **Цель существует** (`test -f`) — `path`/file-аргумент `run:`
     удалён/переименован → расхождение **категории A** (локус/цель
     отсутствует).
- **Diff-условные — по ПЕРЕСЕКАЮЩИМСЯ** сценариям (файл цели в
  фактическом диффе):
  2. **`path:line`** — содержимое строки больше не соответствует
     описанию сценария (дрейф локации) → категория A. (Суждение
     оркестратора по тексту строки vs описанию — не механика;
     помечено как LLM-суждение.)
  3. **Числовое ожидание** (паттерн `→ N pass` / `→ N fail` / `→ 0`) →
     расхождение **категории B** (stale-подозрение).

Исполнение: **0 запусков чужих тестов** (граница M6), кроме одного
bounded-исключения в D3(a).

### D3. Расхождения — HITL (семантика 13f)

Факт (расхождение найдено) — без HITL. Решение по каждому расходящемуся
сценарию — HITL (manual/auto-answer — гейт; auto-ai — решение ИИ с
журналом, **при неуверенности — fallback (a) с обязательной записью в
журнал**):

- (a) **обновить entry** — локацию (`path:line`) перегенерировать
  **чтением файла** (найти новую строку по описанию сценария);
  **числовое ожидание** (категория B) — **один bounded-запуск** этого
  конкретного `run:`-сценария (carve-out из D6: запуск одного
  сценария в рамках принятия (a), не прогон всех) → фактическое число;
  `run:`-команду — перегенерировать по новой локации;
- (b) **пометить `[Manual]`** — сценарий не автоматизируется;
- (c) **удалить сценарий** из entry.

Гейт — один на все «под угрозой» entries (список: entry → сценарий →
расхождение (категория A/B) → выбор a/b/c), не по одному на сценарий.
Если entry после обновлений не содержит ни одного сценария → HITL
отдельно: (a) перенести в `released/` со `status: cancelled` (формат
отмены — `cancelled-features.md`, как гейт отмены) — **пустой
active-entry запрещён** (vacuous-verified: `full` на entry без
automated-сценариев проходит вакуумно → verified без проверок).

### D4. Границы mутации entry (что НЕ меняется)

Обновляются **только** локации/команды/ожидания сценариев. Не трогаются:
`status`, `last_full_pass`, `released`, `added`, `risk` (риск-матрица —
атрибут фичи entry, не текущего диффа), `version`, `feature`. Новых полей
нет (YAGNI). **Carve-out (I3):** единственный статус-переход —
empty-entry → `cancelled` (D3, через HITL). Авто-коммит — паттерн
`@regression` (только конкретный путь entry, не `git add -A`; коммит
`chore(regression): <feature> entry reconciled by <текущая-фича>`).
**Шардинг (I4):** коммит чужого entry из ветки текущей фичи делает
«конфликт параллельных pipeline невозможен по построению» (канон)
маловероятным, а не невозможным — канон-формулировка уточняется (D7.2):
при merge-конфликте entry — повторная reconciliation после мержа.

### D5. `active` — мутации; `verified` — read-only чек

Cross-entry reconciliation **с мутациями (D3/D4)** — только entries со
`status: active`. `verified` — **read-only**: те же existence/diff-
проверки (D2), расхождения — в вывод 13f (отчёт), **без HITL и без
мутаций** (инварианты «`full` — единственный авторитет для `verified`»
и «статус-мутации — только `@regression`» не нарушаются). Обновление
`verified`-entry — штатно: `@regression full` → (fail → демоция на
`active` → следующий прогон пайплайна) или ручная правка entry.
Best-effort: гарантированного момента обновления verified нет — честно
зафиксировано.

### D6. Non-goals / known limitations

- Исполнение чужих сценариев/тестов в пайплайне (это — `@regression`
  standalone; M6: «не отдельная рутина» в пайплайне). Единственный
  carve-out — bounded-запуск одного сценария в рамках D3(a).
- Prose-сценарии без машинных целей (ни `path`, ни file-аргумент `run:`)
  — не выбираются хуком (known limitation: семантическое устаревание
  таких сценарий не покрывается механически).
- Новый шаг/команда/поле формата entry; plugin-изменения.
- `released/` entries (архив — не живётся).
- Семантическое устаревание формулировок (grep-проверка проходит «важно»
  после переноса текста) — покрывается только через дрейф-локации
  (D2.2, LLM-суждение по строке) и числовые ожидания (D2.3);
  качественное устаревание без изменения файла цели — не покрывается
  механически.

### D7. Синхронизация (поверхности)

1. `skills/maestro/SKILL.md` — компактные правки скелета (≤ ~20 строк
   суммарно): шаг 11 — подпункт «Cross-entry selection» (короткое правило
   + указатель на главу); шаг 13f — пункт cross-entry reconciliation
   (указатель на главу, «см. references/regression-registry.md,
   «Cross-entry reconciliation (13f)»»); существующее предложение «Если
   entry не создана (не было risk-сценариев на шаге 11) — шаг
   пропускается» **ограничить own-entry частью** (cross-entry — свой
   no-op при пустом списке D1, шаг не «пропускается» целиком).
   Механики D1–D3 — **в главе** (скелет — указатели, паттерн канона).
2. `skills/maestro/references/regression-registry.md` — новая секция
   «Cross-entry reconciliation (13f)» (механики D1–D5: каскад целей,
   existence/diff-проверки, категории A/B, HITL, границы мутации,
   verified read-only, шардинг-уточнение I4) + правка «Жизненный цикл»
   (cross-entry-обновления: active — сценарии только, carve-out
   empty→cancelled; verified — read-only, мутации только через
   `@regression`) + **уточнение инварианта шардинга** (D4/I4: «конфликт
   маловероятен; при merge-конфликте — повторная reconciliation после
   мержа») + **guard vacuous-full** (I3: `full` на entry без
   automated-сценариев не верифицирует — статус не меняется;
   синхронно в `commands/regression.md`) + **fix битой ссылки** (M7:
   строка «Дизайн: `docs/regression-flow.md` (источник истины)» — файл
   не существует; заменить на «канон — эта глава» + fix той же ссылки в
   `commands/regression.md:8`).
3. `manual_docs/how-to/use-regression-registry.md` — раздел об актуальности
   entries (как entries поддерживаются пайплайном: 11-выбор + 13f-сверка,
   verified read-only).
4. `manual_docs/explanation/pipeline-overview.md` — шаг 13f в таблице —
   уточнить (cross-entry).
5. Changelog 4.19.0, roadmap #103, regression entry фичи, TODO:23.
