обновление entries при прогоне пайплайна (на шаге ревью), а не отдельной
рутиной».

Данные (аудит 2026-10-01, репо maestro-agent): entry
`regression/entries/2026-09-18-subagent-resilience.md` (фича от 2026-09-18)
устарел после 6 следующих фич (4.14.0 → 4.18.0):

1. сценарий `run: node --test plugins/maestro-bootstrap/index.test.js → 171 pass`
   — тестов сейчас 266 (их добавляли docs-drift, benchmark, memory-фичи);

2. сценарий `run: grep -in "3 попыток" skills/maestro/SKILL.md → 0` — 4.14.0

Сегодня чужие (не текущей фичи) entries обновляются **никогда**: шаги 11/12a/13f
работают только с entry текущей фичи; `@regression` — standalone, выполняет
сценарии, но не обновляет entry.

## Дизайн-решения

### D1. Механика — расширение шагов 11 + 13f (HITL, вариант (a))

Не новый шаг, не новая команда, не новый механизм (M5/M6): расширяются
существующие regression-хуки пайплайна.

**Шаг 11 (анализ, план):** оркестратор дополнительно определяет
**«под угрозой» entries (cross-entry selection)** — механически:

- источник: `regression/entries/` (только `status: active`, см. D5),
  entry текущей фичи исключается;
- пересечение: файл-часть `path` сценариев entry (без `:line`) ∩
  набор файлов/каталогов, которые затронет план (файлы задач плана +
  `## Project Context Changes` + модули risk-анализа; допустимы
  каталог-префиксы, напр. `plugins/maestro-bootstrap/`);
- пересечения нет → хук no-op (ни в 11, ни в 13f);
- cap: **≤ 5 entries** за прогон; порядок выбора — по числу пересекающихся
  сценариев (desc), тир — по `added` (desc). Остаток — в отчёт
  (feedback-report, «не покрыты прогоном») — не блокирует.

Результат (список «под угрозой» + пересекающиеся сценарии) фиксируется
в плане/прогресс-логе и передаётся в 13f.

**Шаг 13f (reconciliation, после реализации):** существующая сверка entry
текущей фичи (без изменений) + **cross-entry reconciliation** по списку из D1:
сверка фактов по каждому пересекающемуся сценарию (без исполнения сценариев —
см. D6).

### D2. Что сверяется (факты, без HITL)

Для каждого пересекающегося сценария «под угрозой» entry:

1. **`path` существует** (`test -f`) — файл сценария удалён/переименован →
   расхождение.
2. **`path:line`** — если файл изменён текущим диффом: содержимое строки
   больше не соответствует описанию сценария (дрейф локации) → расхождение.
3. **Цель `run:`** — механически: путь/файл, на который указывает команда
   (первый path-аргумент: `node --test <file>`, `grep … <file>`,
   `npm run <script>` — скрипт в манифесте) существует → иначе расхождение.
4. **Числовое ожидание** (паттерн `→ N pass` / `→ N fail` / `→ 0`):
   если файл, к которому относится ожидание, изменён текущим диффом →
   «stale-подозрение» (расхождение категории B — см. D3).

Не исполняется ничего (0 запусков чужих тестов) — это граница M6.

### D3. Расхождения — HITL (семантика 13f)

Факт (расхождение найдено) — без HITL. Решение по каждому расходящемуся
сценарию — HITL (manual/auto-answer — гейт; auto-ai — решение ИИ с журналом,
fallback (a)):

- (a) **обновить entry** — перегенерировать `path:line`/`run:`/ожидание
  по факту (оркестратор читает файл, находит новую локацию/число);
- (b) **пометить `[Manual]`** — сценарий не автоматизируется;
- (c) **удалить сценарий** из entry.

Гейт — один на все «под угрозой» entries (список: entry → сценарий →
расхождение → выбор a/b/c), не по одному на сценарий. Если entry после
обновления не содержит ни одного сценария → HITL отдельно: (a) оставить
entry без сценариев — (b) перенести в `released/` со `status: cancelled`
(формат отмены — `cancelled-features.md`, как гейт отмены).

### D4. Границы mутации entry (что НЕ меняется)

Обновляются **только** локации/команды/ожидания сценариев. Не трогаются:
`status`, `last_full_pass`, `released`, `added`, `risk` (риск-матрица —
атрибут фичи entry, не текущего диффа), `version`, `feature`. Новых полей
нет (YAGNI). Авто-коммит — паттерн `@regression` (только конкретный путь
entry, не `git add -A`; коммит `chore(regression): <feature> entry
reconciled by <текущая-фича>`).

### D5. Только `status: active` entries

Cross-entry reconciliation — **только** для entries со `status: active`.
`verified` — вне хука: инвариант канона «`full` — единственный авторитет для
`verified`» и «статус-мутации — только `@regression`» не нарушаются.
Устаревший `verified`-entry обновляется штатно: `@regression full` →
демоция на `active` → следующий прогон пайплайна обновит (D1–D4).

### D6. Non-goals

- Исполнение чужих сценариев/тестов в пайплайне (это — `@regression`
  standalone; M6: «не отдельная рутина» в пайплайне).
- Новый шаг/команда/поле формата entry; plugin-изменения.
- `released/` entries (архив — не живётся).
- Семантическое устаревание («важное прохождение» grep-проверки — D2.4
  ловит только числовые ожидания; качественное устаревание формулировок —
  known limitation, не покрывается механически).

### D7. Синхронизация (поверхности)

1. `skills/maestro/SKILL.md` — шаг 11: подпункт «Cross-entry selection (D1)»;
   шаг 13f: расширение пункта (cross-entry reconciliation + гейт D3).
   Бюджет: ≤ ~40 строк суммарно (скелет 1171 строка).
2. `skills/maestro/references/regression-registry.md` — раздел «Жизненный
   цикл»: абзац «Cross-entry-обновления (13f): active-only, сценарии
   только, статусы не меняются; verified — через `@regression full`».
3. `manual_docs/how-to/use-regression-registry.md` — раздел об актуальности
   entries (как entries поддерживаются пайплайном).
4. `manual_docs/explanation/pipeline-overview.md` — шаг 13f в таблице —
   уточнить (cross-entry).
5. Changelog 4.19.0, roadmap #103, regression entry фичи, TODO:23.
