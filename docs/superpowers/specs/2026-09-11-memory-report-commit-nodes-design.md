# Design: commit-узлы в графе отчёта памяти (memory report commit nodes)

**Дата:** 2026-09-11
**Фича:** `feature/memory-report-commit-nodes`
**Статус:** spec (после brainstorm primary, шаг 8 maestro)

## 1. Цель

Сделать граф похожести в HTML-отчёте `@maestro-memory-report` более информативным:
узел графа должен идентифицировать **изменение** (commit / `head`), а не opencode-сессию.
Узел дополняется агрегатными метаданными: короткий хеш `head`, ветка, число сессий,
ссылающихся на commit, и тир (merged/experience/unknown/dead).

Мотивация: `session_id` — ключ записи в хранилище, но идентичность записи в memory layer
v3+ — по коммиту (`head`): matching/промоция/commit-scoped recall работают по `head`
(см. AGENTS.md). Несколько сессий могут ссылаться на один `head` (re-summarize, несколько
сессий на одной ветке без нового коммита) — сегодня такие записи отображаются как
отдельные узлы одного и того же изменения.

## 2. Требования

1. Узел графа — commit (`head`); сессии одного `head` группируются в один узел.
2. Метаданные узла: короткий хеш `head`, ветка, число сессий, тир.
3. Вес ребра между commit-узлами — косинус между **центроидами** эмбеддингов групп
   (нормализованное среднее эмбеддингов сессий группы).
4. Записи без `head` (`head=''`) — отдельные узлы (unattributed), ключ по `session_id`.
5. Совместимость с `@maestro-memory`: заголовки `Граф (рёбер: N):` и `Кластеры:`
   (session-based, темы) сохраняются; `@maestro-memory` читает только счётчики и секции
   Тиры/По веткам — не меняется.
6. SEC-4b: в HTML и в tool-выводе только агрегаты (хеши, ветки, счётчики, тиры,
   session_id). Заголовки/summary/decisions записей не выводятся.
7. Кластеры тем остаются по сессиям (семантика тематической агрегации, не изменений).

## 3. Текущее поведение (baseline)

`memory_stats_detail` (plugins/maestro-bootstrap/memory/index.js, ~стр. 1150–1273):
- scan: `session_id, title, embedding, author, time_last, origin_project_hash, branch, head, merged`;
- `clusterEntries(usable, threshold)` — кластеры по сессиям (темы);
- `buildGraph(usable, threshold, 500)` — попарный косинус эмбеддингов сессий, рёбра выше
  порога, cap 500;
- вывод: `Граф (рёбер: N):` + строки `  <sid> <-> <sid>: <score>`;
- тиры: `applyBranchScope(rows, sets)` → merged/experience/unknown/dead per session;
- `@maestro-memory` агрегирует только количества (кластеры, связи) и секции
  Тиры/По веткам — ID узлов не парсит.

## 4. Дизайн

### 4.1 Группировка узлов

В `memory_stats_detail` после загрузки `usable` (строки с валидным embedding):

1. Сгруппировать по `head` **по всем строкам scan** (не только по `usable`):
   - `head !== ''` → узел с ключом `head:<full-hex>`;
   - `head === ''` → узел с ключом `ses:<session_id>` (unattributed), `branch=''`
     (инвариант записи: write-gate indexer'а разрешает запись только при
     резолвнутом `head`; ветка резолвится вместе с `head` — записи `head=''`
     возможны только через импорт/легаси, для них `branch=''`).
2. Поля узла:
   - `head` — полный хеш; для unattributed-узлов вместо поля `head=` выводится
     поле `ses=<session_id>` (в строке узла ровно одно из `head=` / `ses=`);
   - `branch` — ветка последней (по `time_last`) сессии группы; для unattributed
     при `head=''` — ветка записи (по инварианту `''`); legacy-случай
     `head=''` c `branch≠''` — выводится фактическая ветка записи;
   - `sessions` — число сессий в группе (по всем строкам, с учётом сессий
     без embedding);
   - `tier` — приоритет по членам группы: `dead` > `unknown` > `experience` > `merged`;
     в fail-soft режиме (revList недоступен): `merged`, если все члены группы
     `merged=1`, иначе `unknown`;
   - `session_ids` — список `session_id` группы, разделитель `, `.
3. Эмбеддинг узла — центроид **по подмножеству строк группы с валидным embedding**:
   среднее арифметическое эмбеддингов, нормализация к единичной норме (все
   эмбеддинги уже нормализованы; среднее нормализуется повторно).
4. Узел, у которого ни одна сессия не имеет валидного embedding, — **изолированный**:
   присутствует в секции `Узлы графа` (метаданные полные), но не участвует в рёбрах.
5. Рёбра: `buildGraph` по узлам с центроидами, тот же `similarity_threshold`
   (default 0.7) и cap 500.

### 4.2 Формат вывода `memory_stats_detail` (additive)

Секция `Узлы графа (<M>):` — одна строка на узел:

```
Узлы графа (6):
  head=5ac737cda7bdf8cf5538729435b3e344547433c0 | branch=feature/memory-branch-lifecycle | sessions=3 | tier=merged | session_ids=ses_f74811f10ffeUng5TXq5bGFCph, ses_f78e8bc29ffe4LriglmvBENwZ3, ses_f794f5416ffeUB6X79yiJaPbas
  ses=ses_f794e4e9bfferR0aO4KCjtbrpd | branch= | sessions=1 | tier=unknown | session_ids=ses_f794e4e9bfferR0aO4KCjtbrpd
```

Секция `Граф (рёбер: N):` — рёбра по компактным ключам:

```
Граф (рёбер: 15):
  h:5ac737cda7 <-> h:84ba0fb7c7: 0.87
  h:5ac737cda7 <-> s:ses_f794e4e9: 0.71
```

Компактные ключи: `h:<первые 12 hex>` для commit-узлов, `s:<первые 12 символа
session_id>` для unattributed-узлов. Полные значения — в секции `Узлы графа`.
Коллизия компактных ключей маловероятна (12 hex / 12 символов) и влияет только на
отображение; документируется как принятый риск.
Парсинг строк узла — по префиксам `key=` в фиксированном порядке
(`head=`/`ses=`, `branch=`, `sessions=`, `tier=`, `session_ids=`): значение поля
ограничено следующим маркером ` | key=`, `session_ids=` — до конца строки
(сплит по ` | ` как разделителю не используется: `|` допустим в именах
git-веток, напр. `branch=fix|login`; `git check-ref-format` запрещает пробелы в
имени ветки, поэтому маркер ` | key=` внутри значения не встретится).
Секция узлов ограничена первыми 500 узлами (по убыванию `sessions`); при
превышении — строка-многоточие `…(+N узлов ещё)`.

Заголовки `Кластеры:` и кластерные строки (по сессиям, с темами) — без изменений.
Секции Key/Бэкенд/Модель/Каталог/Записей/По авторам/По датам/Тиры/По веткам/
Диагностики — без изменений.

### 4.3 Команда `@maestro-memory-report`

**Шаг 3.5 переписывается:** рендер графа — по commit-узлам (секции `Узлы графа`
+ `Граф`); сессионный вариант рендера (по session_id) удаляется.

1. Спарсить секции `Узлы графа (M):` и `Граф (рёбер: N):`.
2. Рендер SVG-графа:
   - узел — круг; подпись — компактный ключ (`h:5ac737cda7` / `s:ses_f794e4e9`);
   - под узлом — ветка (если есть) и бейдж `×N` (число сессий);
   - цвет по тиру: merged `#22c55e`, experience `#3b82f6`, unknown `#f59e0b`,
     dead `#ef4444`; unattributed — серый контур;
   - ребро — линия с opacity, пропорциональной весу (как сейчас).
3. Легенда тиров + таблица узлов: полный `head` (или `ses:<session_id>` для
   unattributed), ветка, sessions, tier, session_ids.
4. **Обновить whitelist разрешённых агрегатов в шаге 3.6 команды:** + head-хеши,
   имена веток, тиры. Обоснование: это git-метаданные, уже присутствующие в
   tool-выводе (секция «По веткам»), а не текст записей; заголовки/summary/decisions
   по-прежнему запрещены.
5. SEC-4b: всё перечисленное — агрегаты; заголовки/summary/decisions не выводятся.

Остальные секции отчёта (summary, гистограмма, кластеры, авторы) — без изменений.

### 4.4 Совместимость

- `@maestro-memory`: читает `Граф (рёбер: N)` (счётчик), `Кластеры:` (счётчик),
  Тиры/По веткам — все сохраняются. Изменений не требуется.
- Формат секций `Узлы графа:` — новый, additive; старые секции не переименовываются.
- Описание tool `memory_stats_detail` не меняется (семантика «граф похожести»
  сохраняется).

## 5. Безопасность (SEC-4b, SECURITY.md)

- В выводе `memory_stats_detail` и в HTML — только агрегаты: хеши commit, имена веток,
  счётчики, тиры, session_id. Это разрешённые категории (см. SEC-4b команды
  `@maestro-memory-report`).
- `include_text: false` (default) — по-прежнему без заголовков/summary/decisions.
- Commit-subject из `git log` в отчёт НЕ включается (текстовый контент, по духу SEC-4b).
- Confidential-контур не затрагивается (фича работает на агрегатах).

## 6. Тестирование (TDD, шаг 13 SDD)

В `plugins/maestro-bootstrap/memory/index.test.js` (блок Task 8, секция
`memory_stats_detail`), прогон: `npm run test:memory` (и полный контур плагина —
`node --test plugins/maestro-bootstrap/index.test.js`, 176 тестов зелёные):

1. Группировка по head: 2 записи с одним `head` → один узел, `sessions=2`,
   `branch` от последней сессии.
2. Центроид: 2 сессии одного head, ортогональные эмбеддинги к третьей сессии другого
   head → ребро между commit-узлами есть (порог преодолён за счёт центроида) И/ИЛИ
   вес соответствует центроиду.
3. Unattributed fallback: запись с `head=''` → узел `ses:<session_id>`, `branch=''`,
   `sessions=1`.
4. Рёбра: в секции `Граф` ключи вида `h:<hex>` / `s:<prefix>`; счётчик рёбер N
   совпадает с числом строк; порог по умолчанию 0.7.
5. Тир узла: обязательный тест по полной цепочке приоритета
   `dead` > `unknown` > `experience` > `merged` (сессии одной группы с разными
   тирами → тир узла = приоритетный).
6. Узел без embedding у всех сессий — присутствует в `Узлы графа`, рёбер нет.
7. Регрессия: существующие тесты `memory_stats_detail` (граф по сессиям, кластеры,
   тиры, fail-soft) — без поломок; при необходимости обновить ожидания формата строк.

## 7. Документация (шаг 14)

- `manual_docs/reference/memory.md`: описать секции `Узлы графа:` / `Граф` (commit-узлы,
  центроидная агрегация, unattributed, компактные ключи); зафиксировать, что
  `similarity_threshold` применяется к **центроидной** похожести (распределение весов
  отличается от попарно-сессионного) и что для `@maestro-memory` «количество связей»
  теперь означает число **commit-рёбер**.
- `manual_docs/reference/commands.md`: если описывает `@maestro-memory-report` — обновить
  раздел графа (commit-узлы, легенда тиров) и whitelist агрегатов шага 3.6 (head-хеши,
  ветки, тиры — разрешены; titles/summary/decisions — запрещены).

## 8. Вне scope

- Кластеры тем по commit (остаются по сессиям).
- Изменение `@maestro-memory` (не требуется).
- Новый tool / structured-вывод (отклонён — подход A).
- Include commit-subject / других текстов в отчёт (SEC-4b).
