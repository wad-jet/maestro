# Design: Ужесточение обработки подписей spec (внешний fast-track)

## Проблема

TODO-утверждение «Maestro НЕ берёт в работу неподписанные спецификации (подпись
`maestro:sanitize`/`maestro:review`)» — **неточно**. Подписи spec не являются
условием входа в работу: они лишь **skip-буклетчинг** для повторного входа
(re-entry / fast-track, шаг 7d) — чтобы пропустить уже пройденные шаги 8.6/9.
Их отсутствие означает «шаг выполняется», а не «шаг блокируется».

Две рисковые слабости текущего дизайна:

1. **Подпись подделываема и самодостаточна.** SKILL сам фиксирует forgeability:
   блок вставляется вручную; hash sha256 доказывает лишь соответствие подписи
   содержимому, НЕ факт прохождения sanitize/review в нашем контуре.
2. **Внешний spec (шаг 7d) доверяет подписи автоматически.** Валидная `CLEAN` →
   skip 8.6, валидная review-подпись → skip 9/10 **без HITL**. Внешний spec
   приходит в обход in-pipeline brainstorm + custodian Q/A данного контура; опора
   на чужую/подделанную подпись для авто-пропуска sanitize — прямой вектор утечки
   чувствительных данных к untrusted-агентам (opus на 9, implementer на 13) и
   пропуска архитектурного ревью.

## Цель

- Закрыть внешний fast-track-путь: не полагаться на подпись как на основание
  **автоматического** пропуска 8.6/9 для внешних spec.
- Явно зафиксировать семантику подписи: **skip-маркер, а не гейт допуска**.
- Уточнить, что планы подписями не маркируются (их гейт — HITL-аппрув шага 12).

## Решения

### Р1 (П.2). Fast-track (шаг 7d): подпись — только рекомендация

**Определение.** «Внешний spec» = **любой** spec, входящий через шаг 7d
(fast-track), **включая re-entry spec'ов этого контура из прошлых сессий** (новая
сессия всегда встречает spec через 7d). Механизма различения происхождения не
существует (и он отложен в Р5) — поэтому правило применяется ко **всем** 7d-входам
единообразно.

Для всех 7d-входов перестать автоматически пропускать 8.6/9 по валидной подписи.
Подпись считается **советующей** (provenance), а не авторитетной.

- **8.6 (sanitize)** выполняется **всегда**, даже при валидной `CLEAN`-подписи.
  Исключение — только явное HITL-заверение доверия к источнику (вариант
  «доверяю источнику, sanitize пропустить»). **Ограничение:** заверение
  допустимо только при валидной (не stale) подписи `status: CLEAN`;
  `FINDINGS_ACCEPTED` → 8.6 выполняется всегда (правило 4 «Подписи spec-файла»
  сохраняется, rubber-stamp не перекрывает его).
- **9 (Spec Review)** **не пропускается авто** по review-подписи; предлагается
  всегда через HITL: (a) пропустить / (b) прогнать (шаги 9+10).

Мотив: для всех 7d-входов история подписи недоверенна (подпись подделываема и
доказывает лишь соответствие hash'а, не факт прохождения процесса). Легитимный
in-contour re-entry покрывается явным HITL-заверением (8.6) и HITL-выбором (a)
для 9 — не авто-skip'ом.

### Р2 (П.1). Подпись — provenance-рекомендация, не гейт допуска

В разделе «Подписи spec-файла» явно зафиксировать единое пост-измененческое
определение подписи:
- Отсутствие подписи НЕ блокирует вхождение spec/плана в работу.
- Подпись — **provenance-рекомендация для HITL-решений**; авто-пропуска
  повторных шагов она НЕ даёт никогда (см. Р1).
- Действительный контроль — процесс (шаг 8.6/9), а не файл-подпись.

### Р3 (П.4). Планы не маркируются подписями

У плана (шаг 11) нет и не должно быть подписи: вход в реализацию уже жёстко
гейтится обязательным HITL-аппрувом (шаг 12: Approve/Revise/Отмена). Ввести
`
` — избыточно.

### Р4. SECURITY.md — зафиксировать принцип

Добавить требование ИБ в §3: для внешних spec подпись не является основанием
авто-пропуска sanitize/review; подпись подделываема и доказывает лишь соответствие
hash'а содержимому, не факт прохождения процесса в контуре. Контрмеры §4 —
обновить под этот принцип.

## НЕ входит (scope-out)

- **Р5 (П.3) — гейт по трейсу процесса** (аудит-событие `sanitize.completed` +
  инвариант «8.6 отработал до untrusted-диспатча», регистр санизации в `.maestro/`).
  Это более крупный дизайн, затрагивающий плагин (`plugins/maestro-bootstrap/core.js`),
  состояние сессии и audit-лог. **Отдельная follow-up задача.** Обоснование см.
  в анализе (П.3 в предварительном разборе).

## Критерии приёмки

1. В SKILL.md **не остаётся авто-skip правил по подписи для 7d-входов** (проверка
   по всем секциям: 7d, 8.6, 9, Security Review Точка 1): 8.6 выполняется всегда
   (кроме HITL-заверения при валидной `CLEAN`), 9 предлагается всегда
   (не авто-skip по подписи).
2. «Подписи spec-файла»: явно сказано, что отсутствие подписи не блокирует вход,
   что подпись — provenance-рекомендация (без авто-пропуска) и что план подписями
   не маркируется.
3. SECURITY.md содержит принцип про 7d-входы.
4. `docs/testing/maestro-sandbox-checklist.md` (C13) обновлён под новое поведение.
5. manual_docs синхронизированы: hitl-gates, run-first-feature, changelog, **и
   `agents-and-trust.md`** (обязательный синк SECURITY.md → manual_docs по правилу
   AGENTS.md). Плагин/тесты не затронуты; `npm test` зелёный (регресс).
