# Spec: параллельное первое ревью + переформулировка задачи ревью (#95)

Дата: 2026-09-25. Маршрут: feature (Сложная). Режим: auto-answer.
Основание: роадмап Волна 2 `docs/roadmap.md` — «#95 — сокращение повторных ревью:
переформулировка/расширение трактовки задачи ревью + параллельное первое ревью на
2 агентов (sonnet + opus, только при разных моделях). M3: определить tie-breaker
при расхождении вердиктов». Продолжение линии P1.1+P1.2 (2026-09-03,
`2026-09-03-review-minor-noise-design.md`) после #109/#115 (4.10.0 — метрики
пайплайна, включая `reviewDispatches`, для измерения эффекта; условие I1
выполнено).

## Проблема

После P1.1+P1.2 (Minor не обосновывает blocking-вердикт; fast-path Approve при
только-Minor) повторные раунды ревью всё равно случаются («ревью → правки →
повторное ревью»). Две оставшиеся причины:

1. **Трактовка задачи ревью.** Промпт финального ревью не разделяет явно
   «что искать / что уже проверено / что считать настоящей находкой». Ревьюер
   может переосмысливать локальные детали задач (уже покрытые task-ревью),
   а пропускать то, что реально дорого — кросс-тасковые проблемы и
   несоответствие спеке.
2. **Один ревьюер = одна слепая зона.** Финальное ревью (шаг 16) — одиночный
   диспатч (opus-тир, `code-reviewer`). Второе мнение ловит то, что первый
   пропустил → первый раунд становится «толще» → меньше циклов «почини —
   перепроверь».

## Решение

Два комплементарных механизма на **финальном ревью (шаг 16)**. Два других
контюра — (a) Spec Review (шаг 9) и (b) SDD task-reviewer (шаг 13) — НЕ
меняются (non-goal, §4).

### 1. Параллельное первое ревью (шаг 16)

Вместо одного диспатча — **два независимых параллельных диспатча**:
`code-reviewer` (opus-тир) + `sonnet`. Оба ревьюют диф ветки независимо, в
одном формате (бакеты + `Approved|Needs fixes|Reject`). Параллельно —
wall-clock время не удваивается; прирост стоимости — один sonnet-прогон.

- **Sanitize:** диспатч sonnet проходит стандартный trust-путь без
  изменений — Level 1, авто-санитизация промпта плагином для untrusted
  диспатчей (как любой диспатч sonnet в пайплайне); отдельной механики не
  вводится.
- **Диспатч-обёртка sonnet:** явное «не мутируй код и файлы — верни только
  отчёт ревью» (асимметрия пермишенов `sonnet: edit: allow` vs
  `code-reviewer: edit: deny` принята осознанно — см. Риски 5).

**Правило активации** (решает оркестратор, механически, до диспатча; НЕ
HITL-вопрос; анонс одной строкой в чат: «Параллельное ревью: да/нет —
причина: <…>»):

| Конфиг `review.parallel` | Поведение |
|---|---|
| `auto` (дефолт, ключ отсутствует) | параллельно, если ЛЮБОЕ из условий активации (ниже); иначе одиночное |
| `always` | параллельно всегда (кроме guard ниже) |
| `off` | всегда одиночное (как в 4.11.0) |

**Условия активации** (только для `auto`; оркестратор определяет механически
по дифу ветки, `git diff --name-only` против базы):

1. категория фичи ∈ {Сложная, Архитектурная} (назначена на шаге 7; в
   bugfix-маршруте (D-flow) шага 7 нет → условие = false, работают только
   условия 2–3);
2. диф ≥ 3 изменённых **source-файлов**: source-файл = любой трекаемый файл
   вне исключений; исключения — spec/plan-артефакты (brainstorm),
   `docs/**` (project-context, roadmap), changelog, `regression/**`,
   `manual_docs/**`; для docs-репо (как этот) source = `skills/**`,
   `agents/**`, `commands/**`, `plugins/**`;
3. **cross-layer диф**: изменённые source-файлы затрагивают ≥ 2 слоёв из
   стек-профиля проекта (`docs/project-context.md`, §3 «Стек технологий»);
   если профиль слоёв не выделяет или классификация файла неоднозначна →
   условие = false (пересечение с условием 1 допустимо: сигнал оставлен как
   независимый триггер по A2, проверка дешёвая).

**Guard «одна модель»** (действует при `auto` и `always`): срабатывает, если
идентичность моделей **доказуема** — второе чтение той же модели бессмысленно
→ одиночное ревью (анонс с причиной). Процедура резолва (оркестратор на шаге
16 перед диспатчем; только чтение конфигов, плагин не меняется):

1. **Источник значений:** каждый из ключей `agent.sonnet.model` /
   `agent.code-reviewer.model` читается из локального
   `.opencode/opencode.json` (если файл существует), при отсутствии ключа
   локально — из global `~/.config/opencode/opencode.json` (пути — как в
   таблице сабагентов SKILL.md). Нечитаемый источник = ключ не резолвнут.
2. **Сравнение:** строгое строковое равенство резолвнутых значений (разные
   строки могут означать одну и ту же модель — консервативно в сторону
   параллельного ревью; худший случай — один лишний sonnet-прогон).
3. **Guard срабатывает (одиночное ревью), если:** (a) оба ключа резолвнуты и
   строки равны (анонс: «модели идентичны») — ИЛИ (b) оба ключа не
   резолвнуты: оба агента наследуют модель сессии → идентичны (анонс:
   «модели не заданы — обе от сессии»).
4. **Guard не срабатывает (параллельное ревью), если:** строки различаются —
   ИЛИ резолвнут ровно один ключ: модель второго не определена,
   идентичность недоказуема (анонс помечает: «модель <агент> не задана»).

**Конфиг-ключ:** `maestro.json → review.parallel: auto | always | off`
(дефолт `auto`; ключ отсутствует → `auto`). Чтец — оркестратор на шаге 0
(тул `maestro_config`, кэш в переменной сессии, паттерн PROJECT_CONTEXT).
Невалидное значение → soft fallback в `auto` + пометка в анонсе шага 16
(паттерн `review:config_fallback`, как `communication:config_fallback` /
`feedback_report:config_fallback`). **Плагин не меняется** — ключ
потребляется skill-логикой (инструкциями SKILL.md), не кодом
maestro-bootstrap.

**Объединение вердиктов:**

- **Совпало** (`Approved`+`Approved` / `Needs fixes`+`Needs fixes` /
  `Reject`+`Reject`) → union находок обоих ревьюеров → fix-loop
  (union, дедупликация и контрольные раунды — см. ниже).
- **Расхождение** (возможно только `Approved` vs `Needs fixes`; `Reject` —
  см. ниже). По P1.1 вердикт `Needs fixes` обязан опираться на открытые
  Critical/Important. Два случая:
  - **Случай A — зеркальный: `code-reviewer` (opus) `Needs fixes` + `sonnet`
    `Approved`.** Арбитраж не нужен: по A3 решение старшего по рангу стоит →
    действует `Needs fixes`, fix-loop по C/I-находкам code-reviewer.
    `Approved` sonnet ничего не отменяет; Minor-находки sonnet (если есть) —
    в follow-up-список, не молчаливо.
  - **Случай B — `code-reviewer` (opus) `Approved` + `sonnet` `Needs
    fixes`:**
    - **Пре-фильтр P1.1:** C/I-находки sonnet на самом деле пусты (только
      Minor) → вердикт sonnet невалиден по P1.1, **арбитраж не
      запускается** — действует `Approved`; Minor-находки sonnet — в
      follow-up-список, не молчаливо.
    - **Арбитраж (M3):** sonnet имеет открытые C/I → короткий арбитражный
      диспатч `code-reviewer` (opus): по каждой C/I-находке sonnet —
      **заново** проверить соответствующий код по дифу (явная инструкция в
      арбитражном промпте: «проверяй каждую находку по дифу, цитируй hunk в
      заключении; не опирайся на первое чтение») и заключение «находка
      валидна / невалидна». Финальный вердикт — по итогам арбитража:
      **хотя бы одна находка валидна → `Needs fixes` + fix-loop по валидным;
      все невалидны → `Approved`** (находки sonnet — в follow-up-список, не
      молчаливо).
  - Арбитраж — третий диспатч, только в случае B при непустых C/I у sonnet
    (редкость), не каждый запуск.
- `Reject` любого ревьюера (совпал ли вердикт или нет) → эскалация к
  пользователю (как сейчас: пересмотр требований или отмена).

**Union, дедупликация и контрольные раунды fix-loop:**

- **Union + дедупликация:** находки обоих ревьюеров объединяются в один
  список; совпадающие по файлу и сути — одна запись с пометкой источника
  (`code-reviewer` / `sonnet` / `оба`).
- **Контрольный раунд — один диспатч `code-reviewer` (opus)** по
  union-списку с per-finding трекингом (fixed / open (blocking) /
  follow-up — словарь текущего fix-loop). Sonnet в контрольных раундах не
  участвует: его роль — только первое чтение (расширение слепой зоны);
  контроль закрытия находок — за старшим tier'ом.
- **Закрытие sonnet-only находок:** sonnet-находки, вошедшие в union
  (валидированные арбитражем в случае B, либо при совпавшем вердикте
  `Needs fixes`+`Needs fixes`), проверяются контрольным диспатчем наравне с
  находками code-reviewer; невалидные и Minor — уходят в follow-up до
  fix-loop и контрольного раунда не требуют.
- Цикл «правки → контрольный раунд» повторяется по правилам текущего
  fix-loop (эскалация rounds 4–5 — без изменений).

### 2. Переформулировка задачи ревью (промпт)

Единственный канон инструкции финального ревью — `agents/code-reviewer.md`
(самодостаточный файл; диспатч sonnet получает тот же канон в текст
промпта — self-contained, паттерн implementer-prompt). Структура
переформулировки:

- **Блок «что уже проверено»** (контекст, не для переоценки): task-ревью
  пройдены (spec compliance + code quality на задачу — локальные детали
  задач не переосмысливать); спека утверждена на гейте 10; secret-scan в
  scope (SEC-3 — без изменений); тесты прогнаны на шаге 15 (результаты
  передаются в промпт).
- **Явный фокус** (по порядку): кросс-тасковые проблемы (взаимодействие
  изменённых модулей — то, что (b) по определению не видит); соответствие
  требований спеке; архитектура/целостность; риск регрессии.
- **Порог блокировки:** только открытые C/I обосновывают `Needs fixes`
  (P1.1 — уже инвариант, формулировка усиливается в связке с фокусом).
- **SCOPE NOTE** (вспомогательные коммиты вне скоупа) — сохраняется.

## Риски

1. **Рост стоимости ревью** (sonnet-прогон + редкий арбитраж opus).
   Митигация: правило активации (`auto` — только на сложном/большом дифе),
   guard «одна модель», `off` как полный откат.
2. **Арбитражный bias** (opus подтверждает собственное первое чтение).
   Митигация: арбитражный промпт — перепроверка каждой находки по дифу с
   цитированием hunk в заключении; пре-фильтр P1.1 (Minor не доходит до
   арбитража).
3. **Дрейф двух промптов** (канон code-reviewer vs диспатч sonnet).
   Митигация: единый канон в `agents/code-reviewer.md`, диспатч sonnet
   копирует канон в промпт (self-contained); пометка в SKILL.md.
4. **Частота расхождений неизвестна** — эффект #95 неочевиден до базовой
   статистики. Митигация: метрики 4.10.0 уже собирают `reviewDispatches`/
   циклы; dogfooding этой фичи — первый замер.
5. **Асимметрия пермишенов sonnet** (`edit: allow`, в отличие от
   `code-reviewer` — `edit: deny`): ревью-диспатч sonnet теоретически может
   мутировать код. Митигация: явный запрет в диспатч-обёртке («только отчёт
   ревью, без мутаций»); риск принят осознанно (менять пермишены агента
   глобально нельзя — sonnet используется и как имплементер).
