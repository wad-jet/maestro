# Manual Docs

## Обзор

Навык ведения пользовательской документации платформы по методологии
**Diátaxis** (tutorials / how-to / reference / explanation). Документация живёт в
`manual_docs/` отдельно от технической документации разработчика в `docs/`.

**Базовый принцип:** документация — это код. Она ревьюится в том же PR, что и
код, и попадает в него в рамках обязательного шага 14 пайплайна maestro
(diff-сверка кода с `manual_docs/`). При наличии в проекте coverage-команды
(`DOCS_COVERAGE_COMMAND`) актуальность дополнительно проверяется на шаге 15.
Устаревшая или отсутствующая документация блокирует merge так же, как падающий
юнит-тест.

## Когда применять

Применять **обязательно** при:

- Добавлении или изменении пользовательского поведения (бизнес-флоу, статусы, конфигурация)
- Добавлении или переименовании модуля/подсистемы (`src/<module>/`, сервис, пакет)
- Добавлении или изменении публичного API-эндпоинта (в контроллере/роуте)
- Изменении конфигурации, переменных окружения, docker-compose
- Завершении спринта (критерии приёмки документируются)
- Добавлении примеров кода, команд, схем

## Когда НЕ применять

- Правки внутренней технической документации в `docs/` (спринт-планы, ADR, guideline)
- Комментарии в коде, JSDoc
- Изменения только в `test/` без пользовательского эффекта

## Структура `manual_docs/` (Diátaxis)

```
manual_docs/
  index.md                  # Оглавление + навигация
  tutorials/                # Обучение (learning-oriented): проводим за руку
    connect-first-node.md
    first-transaction.md
  how-to/                   # Инструкции (task-oriented): решаем задачу
    create-adapter.md
    configure-currency.md
    deploy-with-docker.md
  reference/                # Справочник (information-oriented): ищем факт
    api-authentication.md
    system-accounts.md
    configuration.md        # Ключи/параметры конфигурации (пример, не API-центрично)
  explanation/              # Пояснения (understanding-oriented): почему так
    architecture.md
    double-entry.md
    hash-chain.md
  images/                   # Схемы и скриншоты
  examples/                 # Готовые примеры конфигов/скриптов
  .coverage-exemptions.json # Список исключений для теста покрытия
```

### Разделение `manual_docs/` и `docs/`

| Папка | Аудитория | Содержание |
|-------|-----------|------------|
| `manual_docs/` | Пользователи, интеграторы, девопс | Руководства, API-reference, how-to, объяснения |
| `docs/` | Разработчики проекта | Спецификация, спринт-планы, ADR, guideline, security |

`manual_docs/` ссылается на `docs/` для глубоких технических деталей — без
дублирования. Например, `explanation/architecture.md` кратко описывает слои и
ссылается на `docs/spec.md` §2 для полной схемы.

## Правила

### Правило 1: Документация → Код (Docs-as-Code TDD)

- **В пайплайне maestro** дока обновляется на шаге 14 — после реализации, до
  финальных проверок (шаг 15). Обновление `manual_docs/` — обязательная часть
  PR, проверяется diff-сверкой.
- Для крупных изменений документация может утверждаться на ревью до написания
  кода (на уровне спецификации) — «документация → код» для отдельных крупных фич.

### Правило 2: Один PR — одна документация

Любое изменение кода сопровождается обновлением документации в **том же PR**.
В PR проверяется:

- Обновлён ли `CHANGELOG.md` в разделе `Unreleased`.
- Обновлена ли пользовательская документация в `manual_docs/`.
- Добавлены ли примеры для новых функций.
- Для нового/изменённого эндпоинта — отражение в справочнике (например,
  `reference/configuration.md` или api-reference) — иначе PR блокируется
  (coverage-гейт на шаге 15 или diff-сверка на шаге 14).

### Правило 3: Рецензия документации

Документация рецензируется наравне с кодом. Проверяется:

- Грамматика и стиль (русский язык).
- Точность технической информации.
- Работоспособность примеров (curl-команды, JSON, код).
- Понятность для конечного пользователя.
- Читабельность по секции «Читабельность» (лиды, стены >600 знаков, таблицы при ≥3 однородных объектов).

### Правило 4: Версионирование

- Каждый релиз фиксируется в `CHANGELOG.md` с указанием даты.
- Документация для старых версий сохраняется в ветках или тегах.

### Правило 5: Синхронизация скилла

Скилл живёт в `skills/manual-docs/SKILL.md` (source of truth, под git). Доставка в целевое
приложение — штатным механизмом (вручную из удалённого репозитория или через `agpack`);
отдельное `.opencode/`-зеркалирование не требуется (см. AGENTS.md → «Скиллы»).

## Читабельность

Дока читается глазами: монотонный текст с нераскрытыми аббревиатурами — главная
причина, по которой пользователь не дочитывает. Правила R1–R6 обязательны для
новых и изменяемых страниц `manual_docs/`.

- **R1 Лид.** В начале документа и каждого крупного раздела — 1–2 предложения:
  что даёт раздел и кому.
- **R2 Короткие абзацы.** Абзац — не длиннее 2–3 предложений; «стена текста»
  (> ~600 знаков) запрещается — делить.
- **R3 Структура вместо монотона.** ≥3 однородных объекта (агентов, шагов,
  ключей, случаев) — таблица или список, не абзац.
- **R4 Аббревиатуры.** При первом вхождении в документ — раскрытие
  («HITL — human-in-the-loop (ручное подтверждение)»); далее — сокращение
  допустимо. Вставка раскрытия — добавление без перестройки предложения.
  Для справочника (reference/) — per-раздел: читатель входит с середины.
- **R5 Акценты.** Ключевые термины/предупреждения — жирным или `>`-блок;
  не более 2–3 акцентов на экран.
- **R6 Пример.** Для неочевидного правила/поведения — короткий конкретный
  пример (команда, фрагмент конфига, ситуация).

### Пример: «было → стало»

Было — «стена» (цитата из `manual_docs/explanation/agents-and-trust.md`):

```
- **Локальность (default) / внешний embedder (opt-in).** Эмбеддинги — в процессе,
  БД — на диске, кэш модели — локальный. Единственный сетевой вызов — однократная
  загрузка модели эмбеддингов (offline-режим с предзагрузкой). Опциональный
  `memory.embedding.provider: "openai"` — внешний OpenAI-совместимый API:
  контент записей маскируется до эмбеддинга (жёсткий инвариант выше),
  **recall-запросы маскируются всегда** (best-effort, line-level по
  `confidential.paths`), ключ — только через `api_key_env`, запросы/контент
  покидают машину — **осознанный opt-in** (trust-модель не меняется). При
  непустых `confidential.paths` — init-warn
  `external_embedder_unmasked_queries`. Проверка работоспособности модели на
  старте (probe) не влияет на модель доверия. `memory.db` вне git (глобальный
  каталог). Секреты не логируются.
```

Стало — лид + список (те же факты):

```
- **Локальность (default) / внешний embedder (opt-in).** Эмбеддинги —
  в процессе, БД — на диске, кэш модели — локальный; единственный сетевой
  вызов — однократная загрузка модели эмбеддингов (offline-режим
  с предзагрузкой).
  - **Внешний embedder (opt-in):** опциональный
    `memory.embedding.provider: "openai"` — внешний OpenAI-совместимый
    API — контент записей маскируется
    до эмбеддинга (жёсткий инвариант выше), **recall-запросы маскируются
    всегда** (best-effort, line-level по `confidential.paths`), ключ —
    только через `api_key_env`, запросы/контент покидают машину —
    **осознанный opt-in** (trust-модель не меняется); при непустых
    `confidential.paths` — init-warn `external_embedder_unmasked_queries`.
  - **Прочее:** проверка работоспособности модели на старте (probe) не
    влияет на модель доверия; `memory.db` вне git (глобальный каталог);
    секреты не логируются.
```

Иллюстрация из доков самого maestro; при изменении исходного блока пример обновить.

## Роль в maestro

`manual-docs` — **generic user-docs скилл для целевого приложения**. В пайплайне
maestro он загружается оркестратором на **шаге 14** через skill-инструмент
(не субагент; `step_to_tier` не затрагивается), чтобы обеспечить отражение
пользовательских изменений в `manual_docs/` целевого приложения.

Это **отдельно** от правила синхронизации `manual_docs/` самого maestro — т.е. от
документации скилла maestro (см. `manual_docs/how-to/keep-docs-up-to-date.md`).
`manual_docs/` maestro описывает сам скилл; скилл `manual-docs` описывает, как
вести пользовательскую доку целевого приложения.

## Тест покрытия документации (опционально)

В maestro актуальность `manual_docs/` обеспечивается двумя механизмами:

1. **Diff-сверка (всегда, шаг 14)** — оркестратор сверяет diff кода с
   изменениями в `manual_docs/` и требует отражения пользовательских изменений
   в документации. HITL поднимается только при расхождении.
2. **Coverage-гейт (опционально, шаг 15)** — если в проекте задан
   `DOCS_COVERAGE_COMMAND` (например, `docs.coverage.spec.ts`) и он не `none`,
   maestro выполняет его в финальных проверках. Пример такого теста
   (зеркалит `observability.coverage.spec.ts`):

   - **Пользовательские сущности/эндпоинты:** сканирует декларации в коде
     (например, `src/**/*.controller.ts` для REST) и требует, чтобы каждая
     пользовательская поверхность была отражена в `manual_docs/reference/`.
   - **Оглавление:** проверяет существование `manual_docs/index.md`.
   - **Ссылки:** проверяет, что относительные markdown-ссылки из `index.md` резолвятся.
   - **Исключения:** `manual_docs/.coverage-exemptions.json` для инфраструктурных
     сущностей, не требующих user-facing доки.

   При падении тест называет точный файл и сущность, которую нужно задокументировать.

> Если `DOCS_COVERAGE_COMMAND` не задана — coverage-гейт заменяется diff-сверкой
> на шаге 14 (fallback, работает в любом проекте без coverage-теста).

## Шаблоны документов

### Шаблон README.md (обязательные разделы)

```markdown
# <Название проекта>

## 📖 Описание
Краткое описание проекта (1-2 абзаца).

## 🚀 Быстрый старт
Пошаговая инструкция по установке и запуску.

## 📚 Пользовательская документация
- [Оглавление](./manual_docs/index.md)
- [Справочник](./manual_docs/reference/index.md)

## 🤝 Вклад в проект
Ссылка на [CONTRIBUTING.md](./CONTRIBUTING.md)

## 📄 Лицензия
Ссылка на [LICENSE.md](./LICENSE.md)
```

### Шаблон новой функции (`manual_docs/how-to/<name>.md`)

```markdown
# <Название задачи>

[Назад к оглавлению](../index.md)

## 🎯 Назначение
Какую задачу решает эта инструкция.

## 📖 Пошаговая инструкция
### Шаг 1: <действие>
<описание с реальной командой/кодом>

### Шаг 2: <действие>
<описание>

## 💡 Примеры
<реальный запускаемый пример>

## ⚠️ Известные ограничения
- <ограничение>

## 🔗 Связанные разделы
- [Связанный раздел](./related.md)
```

```markdown
### Добавлено

- <изменение>

### Исправлено
- <исправление>
```

## Чек-лист для разработчика

Перед отправкой PR проверьте:

- [ ] Обновлён `CHANGELOG.md` (раздел `Unreleased`).
- [ ] Обновлена документация в `manual_docs/`.
- [ ] Для нового/изменённого эндпоинта — отражение в справочнике (`manual_docs/reference/`).
- [ ] Добавлены или обновлены примеры кода/команд (реальные, проверенные).
- [ ] В начале обновлённых файлов есть ссылка на оглавление (`../index.md`).
- [ ] Документация проверена на орфографию и грамматику.
- [ ] Инструкции воспроизводимы (попробуйте выполнить как пользователь).
- [ ] `npm test -- docs.coverage` проходит локально (если `DOCS_COVERAGE_COMMAND` задана).

## Частые ошибки

| Ошибка | Исправление |
|--------|-------------|
| Дока «на потом» в отдельной задаче | Писать дока в том же PR, что и код |
| Абсолютные ссылки внутри доки | Только относительные (`./`, `../`) |
| Примеры-заглушки (`command --example`) | Реальные curl/JSON из `docs/spec.md` и кода |
| Дублирование текста из `docs/` | Ссылаться на `docs/`, не копировать |
| Технический жаргон без пояснений | Объяснять для конечного пользователя |
| Забыт `CHANGELOG.md` | Обновлять в каждом PR |
| Игнор coverage-гейта (`docs.coverage`) | PR не пройдёт (если `DOCS_COVERAGE_COMMAND` задана) |

## Красные флаги — остановитесь

- «Документирую после кода» → нарушает Docs-as-Code: дока должна попадать в тот же PR, что и код.
- «Это внутренняя сущность, дока не нужна» → добавьте в `.coverage-exemptions.json` с причиной.
- «Скопирую пример из старого туториала» → проверьте работоспособность.
- «Обновлю index.md потом» → проверка ссылок упадёт.
