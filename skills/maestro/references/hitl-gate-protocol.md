# HITL Gate Protocol (глава)

> Канон: hitl-gate-protocol. Грузится из `skills/maestro/SKILL.md` на каждый HITL-гейт (Overview, Pipeline).
> Читается оркестратором (имеющим SKILL.md в контексте); внутри главы
> допускаются ссылки «см. SKILL.md, <секция скелета>» и на другие главы.

## HITL Gate Protocol

**Правило вопросов (UX):**
- **Свободный текст** (описание фичи, разъяснения, произвольный ввод) — обычным
  текстовым вопросом, **не** вопрос-инструмент (панель/select) — инструмент
  возвращает метку вместо введённого текста.
- **Содержательные выборы** (нужно подумать: контент, дизайн-развилки) —
  варианты (a)/(b)/(c) **текстом в сообщении**, не панелью (пользователь может
  отклонить панель и ответить текстом).
- **Вопрос-инструмент (панель)** — только для быстрых формальных выборов из
  фиксированного набора (напр. гейт 10: Approve/Revise/Reject; гейт 17:
  Approve merge/Fix/отмена).

Decision gates (шаги 2, 7, 10, 12, 17) — явный вопрос с вариантами (a)/(b)/(c),
сопровождаемый рекомендуемым дефолтом (п. 3а). Остальные gates в pipeline
(шаги 0, 1, 1.5, 16 — нетекстовые артефакты D5, D2, D6, D7, а также плато и
особый случай на шаге 10 и security-гейты 8.6 / Security Review Точка 2)
следуют
тому же протоколу, но без дефолтов и с вариантами, специфичными для каждого
gate (см. inline-описание в pipeline). Оркестратор ОБЯЗАН следовать этому
протоколу для всех gates:

**Полный перечень gates в pipeline:**

Feature:
- Шаг 0 — загрузка Project Context (загрузить/создать/пропустить/отмена)
- Шаг 1 — выбор маршрута (feature/bugfix/spike/cancel)
- Шаг 1 — Spike (выбор): nod на план + финальный «принять/продолжить/отмена»
- Шаг 1.5 — выбор режима (efficient/interactive/cancel)
- Шаг 2 — подтверждение старта + pre-flight (да/отмена/skip в interactive)
- Шаг 7 — сложность фичи (сложная/простая/отмена) + **аппрув короткого дизайна (7b, Bounded)** + fast-track (d)/(e) + вариант B (внешний review)
- Шаг 8.6 — spec security review: при `FINDINGS_FOUND` (вычистить и продолжить /
  продолжить как есть (принять риск) / стоп)
- Шаг 10 — spec утверждён (approve/revise/reject)
- Шаг 10 — **Особый случай Revise** (правке/вопросу нужен confidential-контекст):
  (a) решает trusted `custodian` (Q/A-агрегат, без значений) / (b) follow-up /
  (c) отмена (см. шаг 10b, «Особый случай»)
- Шаг 10 — **Сходимость Revise** (fast-path: пустые C/I-бакеты контрольного
  ревью → дефолт (a) Approve, Minor → follow-up; плато: 2 раунда без новых
  Critical/Important при незакрытых повторах → (a) Approve / (b) продолжить /
  (c) follow-up оставшиеся) (см. шаг 10b)
- Шаг 12 — plan утверждён (approve/revise/cancel)
- Шаг 16 — нетекстовые (бинарные) артефакты в дифе (D5, #107):
  (a) ИИ-ревью текстовой части дифа, бинарные — ручное / (b) ИИ-ревью всего
  дифа по кодовому канону, бинарные игнорируются / (c) стоп — контентный;
  manual/auto-answer — HITL; auto-ai — решение ИИ с журналом решений,
  fallback (a) (контент — `references/artifact-review.md`)
- Шаг 17 — pre-PR (approve merge/fix/cancel)
- Security Review (Точка 2) — при находке sanitizer перед untrusted-диспатчем
  (вычистить и продолжить / продолжить как есть (принять риск) / стоп)

Bugfix:
- Шаг D2 — утвердить гипотезу (да/новая гипотеза)
- Шаг D6 — гипотеза подтверждена (да/нет)
- Шаг D7 — переход к фиксу (да/отмена)

0. **Язык HITL:** все вопросы, варианты и сообщения пользователю на HITL gates — ТОЛЬКО на русском языке

1. **Показать контекст:**
   - Шаг 10 (spec gate) — diff правок spec после review
   - Шаг 12 (plan gate) — список task-ов с краткими описаниями
   - Шаг 17 (pre-PR) — `git log --oneline`, test results, coverage status,
     список открытых issues (open + follow-up) с severity из шага 16

2. **Задать вопрос с вариантами (a)/(b)/(c):**
   - Никогда не спрашивать "Continue?" или "Утверждаешь?" — только structured options
   - Варианты: Approve / Revise (с указанием куда вернуться) / Reject (отмена фичи)

3. **Дождаться ответа:**
   - Не принимать молчание за approval
   - **«Continue» / «Proceed» / «Давай» не являются approval для последующих gates.**
     Ответ «continue» переводит pipeline ровно на один следующий шаг.
     Gate X+1 требует отдельного явного ответа.
     Оркестратор НЕ имеет права экстраполировать «continue» на всю цепочку gates.
    - Если ответа нет → STOP, pipeline на паузе

3а. **Дефолты в decision gates (P1.3):**
   - Для decision gates (шаги 2, 7, 10, 12, 17) оркестратор сопровождает вопрос
     рекомендуемым вариантом по умолчанию с кратким обоснованием:
     «рекомендую (a) X, потому что Y — подтвердите или выберите иное».
   - HITL подтверждает дефолт ТОЛЬКО явной буквой варианта (или явно выбирает
     иное); «continue»/«давай»/«ок» дефолт НЕ подтверждают (см. пункт 3).
   - Структурированные варианты (a)/(b)/(c) сохраняются — дефолт помечает
     рекомендованный вариант, не заменяет меню.
   - Дефолт предлагается ТОЛЬКО на этих пяти вопросах; все прочие HITL-вопросы —
     гейты 0, 1, 1.5 (предпочтения), D2/D6/D7 (контентные), плато и особый
     случай confidential на шаге 10, security-гейты (8.6, Security Review
     Точка 2) — дефолтов НЕ имеют.
   - Если условие-источник дефолта НЕ выполнено — дефолт НЕ предлагается,
     вопрос остаётся открытым, без рекомендации.
   - Источники дефолтов: шаг 2 — маршрут и режим только что выбраны (1/1.5);
     шаг 7 — категория по матрице сигналов; шаг 10 — вердикт ревью approve /
     fast-path (P1.2); шаг 12 — quality-проверки плана (шаг 11) пройдены;
     шаг 17 — только follow-up issues («не блокирует»), тесты зелёные,
     secret-scan (SEC-3) — 0 находок.

3в. **Режимы запуска (авто-режимы):**
   Режим задаётся флагом при вызове `@maestro-init`, per-run, не персистится
   в `maestro.json`. Флаг убирается из текста задачи.
   - **manual** (без флага / `--no-auto`) — протокол 0–4 + 3а без изменений.
   - **auto-answer** (`--auto-answer` / `-aa`) — **принцип полноты:** авто-принимаются
     только подтверждения рекомендаций, сама работа (шаги, pre-flight, baseline,
     Spec Review, task-review, docs, финальные проверки) выполняется в полном
     объёме. Любое сокращение процесса — вне auto-answer. Каждое авто-принятие
     выводится одной строкой в чат: `[auto-answer] шаг N: принята рекомендация
     (a) X — <краткое обоснование>`; молчаливое авто-принятие — anti-pattern.
   - **auto-ai** (`--auto-ai` / `-ai`) — ИИ сам принимает решения с доп. анализом
     (маршрут, project-context, контентные вопросы, Spec Review offer, docs-шаг).
     Механика — ralph loop. Жёсткий пол (никогда не пропускается): TDD, task-review,
     SEC-3, шаг 15 (тесты для гейта 17), security-гейты, инварианты ⚑1–4.
     Fallback неоднозначности: консервативный выбор (более полный путь).

   **Перечень авто-гейтов auto-answer** (авто-принятие при выполнении
   условия-источника; иначе — HITL как обычно):
   | Гейт | Авто-ответ | Условие-источник |
   |---|---|---|
   | 0 | (a) загрузить | `docs/project-context.md` существует; нет → HITL |
   | 1 | маршрут из текста задачи | однозначно; иначе HITL |
   | 1.5 | (a) efficient | сам флаг выражает предпочтение |
   | 2 | (a) да | P1.3 (маршрут и режим только что выбраны) |
   | 7 | категория по матрице | P1.3 |
   | 7d | (d) использовать внешний spec | однозначное соответствие задаче; иначе HITL |
   | 9 | (b) прогнать Spec Review | сложные фичи (рекомендован); архитектурные — обязателен |
   | 12 | (a) Approve | P1.3 (quality-проверки пройдены) **+ sensitivity guard (⚑4)** |

   **Sensitivity guard (гейт 12, ⚑4):** авто-принятие (a) на гейте 12 применяется
   только если план **и** spec **не затрагивают** внешние API-контракты интеграций
   (public API, межсервисные контракты, breaking changes) и основополагающие
   правила бизнес-логики. Если затрагивают — гейт 12 остаётся HITL даже в
   auto-answer (рекомендация показывается по P1.3, подтверждает человек).
   Классификация (гейт 7) под guard не подпадает.

   **Аппрув короткого дизайна (Bounded, шаг 7b):** утверждение короткого
   дизайна в чате — отдельная HITL-точка (approve/revise/cancel), контентный
   вопрос. НЕ гейт 12 (у простой фичи шаг 11 не выполняется →
   источник-условие P1.3 отсутствует) и не входит в авто-список: в
   manual/auto-answer — всегда HITL; в auto-ai — ИИ решает с доп. анализом
   (decision-диспатч). Авто-принятие по аналогии с гейтом 12 — анти-паттерн
   (расширение авто-зоны за пределы перечня 3в → дрейф в auto-ai-семантику).

   **Никогда не авто (все режимы, включая auto-ai):** гейты 10 (⚑2) и 17 (⚑1);
   плато и особый случай Revise (шаг 10); Tier 3 и
   упавшие команды (15/15a); docs-расхождения (14); reconciliation (13f);
   чувствительные изменения (⚑4); security-риск-принятие и стоп (см. ниже).

   **Ручное в manual / auto-answer** (в auto-ai решается иначе — см. ниже):
   контентные вопросы фичи (brainstorm Q/A, **аппрув короткого дизайна
   (Bounded, шаг 7b)** — см. выше, custodian-сходимость, имя ветки при
   неоднозначности, D2/D6/D7, spike-гейты); security-гейты (8.6 при
   `FINDINGS_FOUND`, включая HITL-заверение «sanitize пропустить» — P7; Точка 2;
   гейт плагина P5).
   В auto-ai: контентные вопросы — ИИ решает сам с доп. анализом; security-гейты —
   гибрид: безопасный дефолт («вычистить и продолжить» / «запретить доступ») ИИ
   применяет сам; принятие риска и стоп — HITL. Правило направления:
   автоматизируются только risk-reducing действия; risk-accepting — всегда HITL.
   В auto-ai гейты 10 и 17 — жёсткие паузы: ИИ ждёт человека, затем продолжает
   (ralph loop не форсирует проход инвариантных гейтов).
   Если условие-источник рекомендации не выполнено — вопрос остаётся HITL
   в любом режиме.

   **auto-ai: механика ralph loop.** Режим ведётся циклом ralph loop:
   - state-файл `.opencode/ralph-loop.local.md` (вводится при старте: `active: true`,
     `iteration`, `maxIterations`, текст задачи); `/cancel-ralph` — прерывание.
   - Итерации продолжают работу после idle до `<promise>DONE</promise>` (завершение
     pipeline до следующего инвариантного гейта или финал) либо до max-итераций.
   - **Паузы на гейтах 10/17:** цикл НЕ форсирует проход инвариантных гейтов — на
     гейте 10 (⚑2) и 17 (⚑1) ИИ останавливается и ждёт явного ответа человека;
     после ответа цикл продолжается. Возобновление: пауза на гейте 10/17 НЕ
     завершает цикл `<promise>DONE</promise>` — `active: true` сохраняется, ответ
     человека на гейте открывает следующую итерацию ralph loop (цикл ждёт, не
     завершается).
   - **Анти-тупик (R2):** отказ в доступе (нативный deny) не ретраится в цикле
     (>1 попытки) — оркестратор передаёт нужный контекст через санизированный
     промпт либо фиксирует деградацию в журнал решений.

   **auto-ai: журнал решений.** Каждое авто-решение (включая security-авто-действия
   и fallback) фиксируется записью: `решение + обоснование + confidence + источник`
   (для security — `R1: security-авто-действие`). Журнал хранится в orchestral-состоянии
   сессии; сводка по журналу показывается на следующем инвариантном гейте (10/17),
   чтобы человек видел, что было решено/сделано автоматически до принятия спеки/мержа.

   **auto-ai: security-усиления (R1–R4):**
   - **R1 Прозрачность:** каждое security-авто-действие (вычистить / deny) — в журнал
     решений + строка в сводке на гейтах 10/17.
   - **R2 Анти-тупик:** deny не ретраится в ralph loop (>1 попытки); контекст — через
     санизированный промпт или фиксация деградации.
   - **R3 Тревожная плотность:** аномально высокое число findings за прогон
     (эвристика оркестратора) → пауза с HITL даже для безопасного направления.
   - **R4 P5 — предпосылка режима:** без работающего плагина авто-режимы не стартуют
     (жёсткий стоп, fail-closed); это условие существования режима, не «гибрид».
   - **Механический пол:** Ур.1 маскирование task-промптов и confidential-deny
     исполняются плагином `maestro-bootstrap`; read-блоки нативного
     permission-слоя — ядром opencode; всё это действует безусловно —
     авто-режимы их не отключают.

4. **После ответа:**
   - (a) Approve → следующий шаг pipeline
   - (b) Revise → вернуться к указанному шагу, исправить, повторный gate
   - (c) Reject → STOP, pipeline завершён
