# Init Context — Схема `docs/project-context.md` (14 категорий)

Справочный файл скилла `maestro-init`. Перечисляет структуру и назначение
`docs/project-context.md`, который создаёт/обновляет `/maestro-init`. Читается
оркестратором в ходе интерактивного опроса. Формат секции `14. Commands`
совпадает с тем, что ожидает `skills/maestro/SKILL.md` (шаг 0, §14).

## Цель файла

`docs/project-context.md` — постоянный контекст проекта, который maestro
загружает на шаге 0 каждого pipeline. `/maestro-init` наполняет его для
**нового** проекта. Существующий файл обновляется только по явному решению
пользователя (пересоздание/расширение).

## 14 категорий

Ниже — проектируемый перечень. `/maestro-init` проходит категории поочерёдно,
задаёт вопрос, фиксирует ответ и в конце собирает файл.

### 1. Название и назначение

- Что делает проект (1-2 абзаца).
- Для кого (аудитория/пользователи).
- Тип проекта (сервис, приложение, библиотека, CLI, monorepo …).

### 2. Цели и метрики успеха

- Бизнес-цели и продуктовая ценность.
- Измеримые критерии успеха (метрики, North Star, KPI).
- Что НЕ входит в scope (non-goals) на данном этапе.

### 3. Стек технологий

- Языки, фреймворки, ключевые библиотеки.
- ORM/БД, кэш, очереди, внешние сервисы.
- Инструменты: менеджер пакетов, линтер, форматтер, тест-раннер.
- Это зеркалит артефакты, которые `stack-detection.md` использует для детекта команд.

### 4. Архитектура

- Слои и границы (endpoint → сервис → репозиторий и т.п.).
- Ключевые потоки данных.
- Ссылка на дизайн-документ из `docs/superpowers/specs/` (генерируется на шаге (a) `/maestro-init`), если он создан.

### 5. Домены / модули

- Ключевые подсистемы и их ответственность.
- Схема каталогов верхнего уровня.

### 6. Ограничения и допущения

- Неконфункциональные требования (latency, availability, scales).
- Compliance / regulatory ограничения.
- Допущения, принятые на старте.

### 7. Риски

- Технические и продуктовые риски.
- Митигации.
- Открытые вопросы.

### 8. Команда и процессы

- Git flow, конвенция веток (feature/fix/hotfix — см. SKILL.md maestro).
- Процесс code review и тестирования.
- CI/CD практики.

### 9. Критерии приёмки качества

- Определение done (DoD).
- Требования покрытия тестами.
- Gate-критерии перед merge.

### 10. Тестирование

- Стратегия unit / integration / e2e.
- Fixtures, тестовые БД, среды.
- Тестовые команды (дублируются/берутся из §14).

### 11. Развёртывание и окружения

- dev / staging / prod.
- Docker, оркестрация, CI-пайплайн.
- Миграции и seed-данные.

### 12. Безопасность

- Аутентификация/авторизация.
- Обработка секретов (`.env`, vault).
- Обработка чувствительных данных.

### 13. Мониторинг и observability

- Логи, метрики, алерты, трейсинг.
- Инструменты и дашборды.
- Observability-команды (зеркалятся в §14).

### 14. Commands

Подсекция в формате, который читает мастер (шаг 0/§14 в SKILL.md):

```yaml
## 14. Commands

### Default (root)
TEST_COMMAND: "npm run test:unit"
BUILD_COMMAND: "npm run build"
E2E_COMMAND: "npm run test:e2e"              # опц.
LINT_COMMAND: "npm run lint"
DOCS_COVERAGE_COMMAND: "npm run docs-coverage"   # опц.
OBSERVABILITY_COVERAGE_COMMAND: "npm run obs-coverage"  # опц.

### services/etl-go/
TEST_COMMAND: "go test ./..."
BUILD_COMMAND: "go build ./..."
```

Значения каждой переменной: явная команда | `auto` (авто-детект по
`stack-detection.md`) | `none` (пропуск шага в pipeline). Эти значения — 
**selectable-варианты** для вопросного инструмента (radio + «свой вариант»),
а не текст вопроса. Для архивных и долгоживущих разделов используется тот же
формат YAML с `### <service-path>/`.

## Готовый шаблон файла

Скилл собирает файл из ответов пользователя. Минимально обязательные секции:
1, 2, 3, 4, 9, 14. Остальные — заполняются по релевантности или помечаются
`_pending_` (не блокирует создание, обновляется позже).

## Вывод конфигурации из контекста

Задача 3 `/maestro-init` выводит секции `maestro.json` из 14 категорий. Правила вывода и
**полный JSON-канон** — в скилле `maestro-assistant` (`skills/maestro-assistant/SKILL.md`).
Задача 3 загружает `maestro-assistant` и следует его канону. Ниже — краткая сводка:

- **`trust`** — всегда `design: true`, `sanitizer: true` (trusted по роли). Остальные — untrusted.
- **`access_policy`** — `allow` из §3/§5 (src/test/packages + расширения языков), `ask` из
  docs/specs/manual_docs/config, `deny` — секреты (`*.env`, `*.{pem,key,cert,secret}`); `default: "ask"`.
- **`confidential`** — дефолт `paths: ["docs/confidential/**"]`, `trusted` read allow / write+edit deny.
- **`sanitizer_whitelist`** — `rules` дефолтные, `extra_fields`/`extra_uri_schemes` из §12/§3.

> Полный JSON-канон и детали — в `skills/maestro-assistant/SKILL.md` (единый источник; не
> дублировать здесь).

### `.opencode/opencode.json` (или global) → `agent.*` (модели, M1)

- tier-класс per агент (см. `skills/maestro-init/SKILL.md`, M1).
- Доступные модели — из `provider.<name>.models` по всем уровням конфигурации
  (D2), см. `skills/maestro-init/SKILL.md`.
- HITL per агент, плейсхолдеры запрещены.
- «Оставить текущую» — если агент настроен на любом уровне (global или project);
  при наследовании из global в project ничего не пишется (наследование через merge).
- `temperature` — дефолт по tier (см. таблицу в M1), не перезаписывать
  существующее значение; записывать вместе с `model` (не при `auto`); при записи
  новой модели в проект — наследовать из global, если задана.
