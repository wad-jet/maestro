# План: Fast-track — внешний spec для сложных фич (пропуск spec-цикла)

> Статус: **зафиксирован, реализация НЕ начата**.
> Дата: 2026-08-19. Репо: `maestro-agent` (authoring).
> Источник: `.maestro-feedback-18.09.md` (предложения 1 и 2).
> Решения: механизм — авто-детект spec в `docs/superpowers/specs/` + ручной путь
> (пользователь указывает путь); scope — пропуск только spec-цикла (шаги 8, 8.6,
> 9, 10), plan (11) пишется maestro из внешнего spec, plan-gate (12) обязателен.

## Постановка

При работе над фичей Trace Enrichment дизайн и план были уже обсуждены и
получили два ревью Opus **до** запуска `maestro`. Скил не знал об этом и
потребовал полный формальный цикл: spec → spec-review → gates (шаги 8–10).
Итог — правильно, но дорого: повторное ревью того же плана.

Скилу не хватает механизма «внешний spec уже отревьюен/утверждён», чтобы
упростить формальности без потери обязательных gates.

**Вторая проблема (закрывается этим же решением):** gate «continue» требует
явного ответа на каждый шаг, даже когда маршрут выбран и план подтверждён.
После fast-track лишние гейты spec-цикла не запускаются — жалоба снимается.
Отдельного изменения не требуется (закрыто через #1).

## Как определяется «внешний spec»

**Авто-детект + ручной путь** (на шаге 7, после выбора категории):

1. Оркестратор globs `docs/superpowers/specs/*.md` (конвенция:
   `YYYY-MM-DD-<feature-name>-design.md`).
2. Найден один или несколько → HITL: «Обнаружен spec `<path>`.
   (d) использовать — fast-track / (e) создать заново (шаг 8)».
   Несколько файлов → список на выбор.
3. Не найден → пользователь может явно указать путь вручную.
   Иначе — нормальный путь (шаг 8, design-сабагент).

**Применимо только к сложным/архитектурным фичам** (где шаги 8–10 запускаются).
Для простых фич шаги 8–10 уже пропущены (шаг 7b) — fast-track не релевантен.

## Что пропускается / остаётся

| Шаг | Обычный pipeline | Fast-track |
|---|---|---|
| 7 | категория фичи | категория фичи + предложение (d)/(e) |
| 8 | dispatch `design` → spec | **ПРОПУСК** (внешний spec) |
| 8.5 | оценка изменений контекста | **ОСТАЁТСЯ** — анализирует внешний spec |
| 8.6 | spec security review | **ПРОПУСК** (нет диспатча opus; spec читает только оркестратор) |
| 9 | spec review (opus) | **ПРОПУСК** |
| 10 | spec gate | **ПРОПУСК** |
| 11 | writing-plans | **ОСТАЁТСЯ** — plan пишется ИЗ внешнего spec |
| 12 | plan gate | **ОСТАЁТСЯ** — обязателен, пользователь подтверждает план |
| 13+ | SDD → review → pre-PR | без изменений |

**Почему 8.6 (security review) пропускается:** spec не отправляется в untrusted
сабагенты — plan (11) пишет сам оркестратор (trusted), implementer-промпты
санируются на Точке 2 (шаг 13d). Утечки чувствительных данных нет.

**Почему 8.5 остаётся:** это анализ spec на изменения проектного контекста
(новые категории, стек, команды) — нужен независимо от того, кто написал spec.
Работает с внешним spec файлом как с источником.

## Edge case: внешний spec невалидный

- Пустой / нечитаемый / не содержит требований → HITL:
  (a) создать заново через `design` (шаг 8) / (b) указать другой путь /
  (c) отмена. Добавить в таблицу «Обработка сбоев».

## Известные ограничения

- **Риск ложного «внешний spec»:** если spec некачественный, потери частично
  компенсируются обязательными gates (plan-gate 12, code-review 16, pre-PR 17)
  и отсутствием 8.6 (sanitizer не запускается). Пользователь сам объявляет
  spec готовым — ответственность на нём.
- **Формат внешнего spec не проверяется:** maestro полагается на читаемость.
  Если `design`-конвенция нарушена, шаг 11 может потребовать уточнений — это
  обрабатывается существующим plan-gate (12).
- **Реализация (#3, #5, #6, #7 из фидбека)** — отдельный план
  (`process-improvements-plan.md`), не смешивать.
