## Постановка

Четыре независимых улучшения SKILL.md, выявленных фидбеком. Каждое — локальная
правка в существующие секции, без изменения структуры pipeline.

## #3 Лимит размера задачи

**Проблема:** Task 8 (redact, 16 файлов) — самая большая задача вышла тяжёлой
для одного диспатча; субагент справился, но риск/нагрузка высоки.

**Решение:** в шаг 11 (проверки качества плана) добавить правило:
> **Размер задачи:** если задача затрагивает > ~8–10 файлов — разбить на
> подзадачи (отдельные диспатчи). Guidance, не жёсткий лимит: крупный
> рефакторинг с механическими правками может оставаться одной задачей
> по решению оркестратора с HITL-подтверждением при неоднозначности.

## #5 Spec+plan без дублирования

**Проблема:** `...-design.md` (spec) и `...-trace-enrichment.md` (plan) с почти
одинаковым содержимым — ручная работа по поддержке двух документов.

**Решение:** в шаг 11 (проверки качества плана) добавить правило:
> **Дублирование spec:** план ссылается на секции spec по имени (например,
> «см. spec §3.1»), не переписывает требования дословно. Полное дублирование
> содержимого spec в плане — дефект качества, исправить до plan-gate.

## #6 Cross-cutting прогноз

**Проблема:** перенос и удаление `trace.redact` затронули
`examples/*/maestro.config.yaml` (13 файлов) — не было предсказано в spec;
всплыло на review.

**Решение:** в шаг 8.5 (оценка изменений контекста) добавить:
> **Cross-cutting scan:** если spec меняет конфиг-схему/ключи (удаление,
> переименование, перенос ключа) — оркестратор выполняет grep по изменённым
> ключам в `examples/`, конфигах, доках и запоминает найденные файлы как
> pending cross-cutting changes (вместе с context changes). Они попадают в plan
> (шаг 11) как задачи на обновление затронутых файлов.

Замечание: scan на шаге 8.5 возможен только для фич со spec (сложные/арх),
т.к. 8.5 выполняется после шага 8. Для простых фич (без spec) cross-cutting
риск покрывается существующим regression-анализом на шаге 11.

## #7 Умный pre-PR gate

**Проблема:** на pre-PR gate вариант (b) «Fix → шаг 13» предлагался как
равноправный, хотя открытых замечаний не было (все issues исправлены и
перепроверены, остался только follow-up I2, не блокирующий merge). Это вводило
в заблуждение: пользователь спрашивал «что за шаг 13 и что чинить».

**Решение (две части):**

**Шаг 16 (requesting-code-review)** — документировать трекинг состояния issues:
> Оркестратор ведёт fix-loop после code review и трекает состояние каждого
> issue: `fixed` / `open (blocking)` / `follow-up (non-blocking)`.
> Follow-up фиксируется отдельно (не блокирует merge), не молчаливо.

**Шаг 17 (pre-PR gate)** — показывать состояние issues в gate:
> Оркестратор ПОКАЗЫВАЕТ: git log, test results, coverage status **и список
> открытых issues (open + follow-up) с severity** из шага 16.
> Если открытых issues нет — вариант (b) помечается:
> «(b) Fix — нет открытых замечаний (только follow-up, не блокирует)».
> Если открытые есть — их список прямо в gate, чтобы пользователь решал
> на основе фактов, а не гадал.

## Известные ограничения

- #3 — это guidance, не enforcement: порог файлов субъективен, финальное
  решение за оркестратором (+ HITL при неоднозначности).
- #6 — grep по ключам ловит только точные вхождения; переименованные ключи
  с разными суффиксами могут остаться незамеченными. Это acceptable overhead,
  покрывается code-review (шаг 16).
- #7 — требует от шага 16 дисциплины трекинга (fixed/open/follow-up). Если
  оркестратор не ведёт список, gate деградирует до текущего поведения.
- Вне scope: #4 (type-верификация тестов), #1/#2 (fast-track).

## Верификация

- Шаг 11: план с задачей >10 файлов и/или с дословным дублированием spec
  помечается до plan-gate.
- Шаг 17: при отсутствии открытых issues вариант (b) содержит пометку;
  при наличии — список issues отображается.
- Согласованность SKILL.md ↔ hitl-gates.md ↔ changelog.
- Тесты плагина не затронуты (63/63).
