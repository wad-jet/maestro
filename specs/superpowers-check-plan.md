## Постановка

`/maestro-init` (скилл `maestro-init`, `skills/maestro-init/SKILL.md`) должен проверять наличие
установленных скилов superpowers (`https://github.com/obra/superpowers`, папка
`skills`). Если скилы не установлены — предложить установку через HITL.

**Зачем:** pipeline maestro жёстко зависит от superpowers-скилов (REQUIRED
SUB-SKILLS в `skills/maestro/SKILL.md`: `writing-plans`,
`subagent-driven-development`, `test-driven-development` и др.). Если их нет —
SDD-шаги (план, исполнение, TDD) работать не будут. Сам init НЕ требует
superpowers runtime (`design-prompt.md` и `implementer-prompt.md` —
self-contained), но проверка на этапе init предупреждает пользователя
заблаговременно, чтобы после bootstrap не оказаться с неработающим pipeline.

## Как определяется «установлено»

**Runtime-пробник через `skill` tool** (не проверка конфигов):

1. Оркестратор вызывает `skill` tool с **bogus-именем** (например
   `__maestro_probe__`).
2. `skill` tool всегда возвращает ошибку для несуществующего имени, и в тексте
   ошибки содержит полный список доступных скилов:
   `Skill "__maestro_probe__" not found. Available skills: brainstorming, ...,
   writing-plans, ...`.
3. Оркестратор парсит список из ошибки и проверяет наличие **всех 7 REQUIRED
   SUB-SKILLS** maestro (см. `skills/maestro/SKILL.md`):
   - `writing-plans`
   - `subagent-driven-development`
   - `test-driven-development`
   - `using-git-worktrees`
   - `requesting-code-review`
   - `finishing-a-development-branch`
   - `systematic-debugging`
4. Все 7 в списке → superpowers **установлен**. Любой отсутствует →
   **не установлен** (фиксируем список недостающих).

**Почему bogus-name, а не загрузка самих скилов:** загрузка скила через `skill`
tool инжектит его полное содержимое в контекст (тысячи токенов). Bogus-name
возвращает ошибку с полным списком — **0 токенов контента**, 1 вызов, проверка
всех 7 скилов бесплатно.

**Почему пробник, а не `opencode.json`:** `skill` tool детектит **фактическую**
доступность, независимо от способа установки (плагин, ручное копирование,
зеркало `.opencode/`). Проверка конфигов обманывает в обе стороны (запись есть,
пакет сломан; скилы скопированы без записи).

**Зависимость:** подход опирается на формат ошибки `skill` tool (наличие
`Available skills:` в тексте). Это текущее поведение opencode; при изменении
формата — fallback на прямую загрузку одного канонического скила
(`test-driven-development`).

## Flow (новый pre-flight шаг в `skills/maestro-init/SKILL.md`)

Расположение: блок «Предусловия (pre-flight)», после «3. Git-состояние»
(независимо от контекста проекта).

1. **Пробник:** bogus-name вызов `skill` tool → парсинг списка доступных скилов
   → проверка всех 7 REQUIRED SUB-SKILLS.
2. **Все найдены** → пометить `superpowers: ok`, перейти к следующему шагу.
3. **Недостающие найдены** → HITL:

   Показать пользователю:
   - список недостающих скилов;
   - команду установки;
   - вопрос: «(a) установить глобально (`-g`) — (b) установить в проект — (c) пропустить».

   Рекомендация — (a) глобально: скил доступен во всех проектах.
   Примечание: `-g` модифицирует `~/.config/opencode/opencode.json` (глобальный
   конфиг пользователя); без `-g` — проектный `opencode.json`.

4. **Выбор (a)/(b):** оркестратор выполняет команду сам через `bash`
   (команда показывается и подтверждается HITL):

   ```
   opencode plugin -g superpowers@git+https://github.com/obra/superpowers.git   # (a)
   opencode plugin superpowers@git+https://github.com/obra/superpowers.git       # (b)
   ```

   После выполнения — **повторный пробник** для подтверждения.
   - Повторный пробник успешен → `superpowers: ok`.
   - Повторный пробник всё ещё не находит (C1: текущая сессия кэширует список
     скилов при старте; `opencode plugin` обновляет файлы/конфиг, но работающая
     сессия может не подхватить изменения без перезапуска) → сообщить:
     «Установка выполнена. **Перезапустите opencode** для активации скилов,
     затем повторно запустите `/maestro-init`.» Пометить
     `superpowers: installed (restart required)`. Не блокировать init.

5. **Выбор (c) (пропустить):** init **продолжается**, в `.maestro/last-run.md`
   и финальном своде — явная пометка: «superpowers НЕ установлен — SDD-шаги
   pipeline maestro (план, исполнение, TDD, ревью) работать не будут»
   (fail-open с предупреждением, без блокировки init).

## Поведение при сбое

| Ситуация | Действие |
|---|---|
| Команда установки упала (сеть, git) | HITL: повторить / показать команду пользователю для ручного запуска / пропустить |
| Пробник после установки всё ещё не находит (C1: сессия не перезагрузилась) | Сообщить «перезапустите opencode», пометка `installed (restart required)`, продолжить |
| Отказ (c) | Продолжить, пометка в last-run.md + своде |

## Известные ограничения

- **Init не требует superpowers runtime** (I2): `design-prompt.md` и
  `implementer-prompt.md` — self-contained (не загружают скилы через `skill`
  tool). Проверка — это **readiness-предупреждение** для последующего pipeline
  maestro, а не хард-зависимость самого init. Поэтому отказ (c) не блокирует
  init.
- **Идемпотентность** (I1): повторный запуск `/maestro-init` повторяет пробник.
  Если скилы уже установлены — HITL не показывается, `superpowers: ok`.
- **Зависимость от формата ошибки** `skill` tool: подход опирается на наличие
  `Available skills:` в тексте ошибки bogus-name вызова. При изменении формата —
  fallback на прямую загрузку `test-driven-development`.
- **C1 — перезапуск после установки:** `opencode plugin` обновляет файлы/конфиг,
  но работающая сессия кэширует список скилов при старте. Повторный пробник в той
  же сессии может не увидеть свежеустановленные скилы. Fallback — рекомендация
  перезапустить opencode.
- Ограничение HITL-gate: «Запустить pre-flight диагностику?» (.TODO.md п.6) —
  вне скоупа этого плана.
