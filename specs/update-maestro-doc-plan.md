# План: документ «Обновление maestro» (how-to) + короткая секция в README

**Goal:** Документировать процесс обновления maestro (скиллы/команды/агенты + плагин)
в целевом проекте до версии, включая контроль версии через `/maestro-version` и
`.maestro/plugin-version`. Подробно — в `manual_docs/`, коротко со ссылкой — в `README.md`.

**Spec:** автономный spec-файл не создаётся — правка чисто документационная
(соглашение authoring-репо: для правок только доков `manual_docs/` отдельный spec
не требуется; все факты зафиксированы в разделе «Контекст» ниже).

**Решения по «контролю версии» (согласованы в ревью):**
- Версия плагина и скилов — **единая**, живущая в корневом `package.json → version`
  (сейчас `1.1.0`). Другие маркеры/механизмы версии не рассматриваются.
- Рантайм-контроль всей сборки = команда `/maestro-version` (читает
  `.maestro/plugin-version`, тот пишется из `package.json` при `init`).
- Изменение кода плагина НЕ требуется (плагин уже читает `package.json`) → скоуп —
  только документация.
- `VERSION.md` НЕ создаётся: `package.json` — единственный источник версии.

## Контекст (факты из репо)

Обновление maestro в целевом проекте состоит из **двух независимых частей** с разными
механизмами доставки и контроля версии:

1. **Скиллы/команды/агенты** (`.opencode/`) — доставляются штатным механизмом: вручную
   из удалённого репозитория или через `agpack` (AGENTS.md; `manual_docs/how-to/customize-maestro.md`).
   Отдельного механизма версии скиллов нет.
2. **Плагин `maestro-bootstrap`** — ставится из git: `maestro-bootstrap@git+https://github.com/wad-jet/maestro.git`
   (публикация в npm не используется). Единственный источник версии — **корневой** `package.json`
   репозитория (сейчас `1.1.0`). `readPluginVersion()` резолвит его относительно `core.js`
   (`plugins/maestro-bootstrap/` → `../../package.json`). При `init` версия пишется в
   `<project>/.maestro/plugin-version` (`writePluginVersionFile`, fail-soft). Читается командой
   `/maestro-version` (команда сообщает «не инициализирован», если файла нет).
   При необходимости версию/коммит плагина можно зафиксировать через fragment
   `#<commit-sha>` (см. `plugins/maestro-bootstrap/README.md`, строки 301–308).
3. **Версия и плагина, и скилов — единая, из корневого `package.json → version`
   (сейчас `1.1.0`).** Скилы отдельной версии не имеют; их версия = версия дистрибутива
   maestro. Это правило фиксируется в документации (не вводит новых маркеров/файлов).
4. **Рантайм-контроль всей сборки — `/maestro-version`**: плагин при каждом `init`
   перезаписывает `.maestro/plugin-version` из `package.json`, команда его читает.
   До перезапуска OpenCode файл содержит старую версию (контроль — после рестарта).

## Задачи

### Task 1: Создать `manual_docs/how-to/update-maestro.md`

New how-to «Обновление maestro до версии». Структура:

- `## 🎯 Назначение` — как обновить maestro (skills + plugin) в целевом проекте до новой
  версии authoring-репо; два пути доставки; контроль версии.
- `## 🧩 Две части и их контроль версии` — таблица:
  | Часть | Механизм доставки | Контроль версии |
  |---|---|---|
  | Скиллы/команды/агенты | agpack sync / вручную | нет отдельной версии; версия = версия дистрибутива из `package.json` |
  | Плагин maestro-bootstrap | git (`@git+...`), опционально `#<commit-sha>` | `.maestro/plugin-version` + `/maestro-version` |
- `## 🔍 Единая версия и как её узнать` — версия плагина и скилов — одна: корневой
  `package.json → version`. Рантайм-контроль — `/maestro-version` (читает
  `.maestro/plugin-version`). Если файла нет — команда сообщает «не инициализирован»
  (признак сбоя init). Число-пример: `1.1.0` «на момент написания», актуальное —
  всегда из `package.json`.
- `## Шаг 1: Обновление скиллов/команд/агентов`
  - Вариант A (agpack): `agpack sync` (обновляет зависимости из `agpack.yml`). Отметить:
    agpack не покрывает плагин и конфиги (`maestro.json`, `opencode.json`, `.gitignore`, `regression/`).
  - Вариант B (вручную): скопировать `skills/`, `commands/`, `agents/` (и `.opencode/` при необходимости).
- `## Шаг 2: Обновление плагина`
  - По умолчанию (`@git+...` без fragment) — OpenCode получает последнюю версию из ветки
    репозитория при старте.
  - Зафиксировать конкретную версию/коммит: fragment `maestro-bootstrap@git+https://github.com/wad-jet/maestro.git#<commit-sha>`.
  - Примечание: не копировать папку плагина отдельно от репозитория — версия не определится.
- `## Шаг 3: Контроль обновления` (порядок обязателен: обновить → **перезапустить** → проверить):
  1. перезапустить OpenCode — иначе `.maestro/plugin-version` держит старую версию;
  2. `/maestro-version` → версия из `.maestro/plugin-version`;
  3. сверка с ожидаемой версией из `package.json` (== версия скилов и плагина);
     расхождение → скилы/плагин не той версии;
  4. если «не инициализирован или версия неизвестна» — плагин не загрузился / init сбоя.
- `## ⚠️ Известные ограничения` — версия скилов = версия дистрибутива (нет отдельной
  версии скила); `agpack` не пинит скилы по версии (только ветка); гарантия версии
  сборки — пинить плагин на тот же коммит `#<commit-sha>`, что и источник скилов;
  плагин версию резолвит только при целостной установке из репо.
