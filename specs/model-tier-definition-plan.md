# План: развернуть ответственности тиров и определить «свою модель» sanitizer в docs

> Статус: **утверждено, реализация не начата**.
> Репо: `maestro-agent` (authoring). Дата: 2026-08-24.

## Постановка

Текущая формулировка в `manual_docs/tutorials/setup-project.md:118` и
`README.md` определяет Tier как «мощность модели (выбор провайдера)». Это
неточно: Tier — **класс ответственности агента** (тип задачи × модальность ×
требование к reasoning × доверие), а «мощность» — лишь одна компонента (контекст
задаёт конкретная модель, не тир).

Контрпримеры тому, что Tier ≠ мощность:
- **fable** — модальность (примеры/метафоры), не мощность;
- **sanitizer** — «своя» модель, определяется **доверием** (trusted) и
  **точностью** security-задачи, не мощностью.

Термин «своя модель» (для sanitizer) нигде в docs не определён — надо дать
внятное определение.

## Решение

1. **Развести понятия.** Tier = класс ответственности; «мощность» — лишь
   косвенное следствие (opus ≥ sonnet ≥ haiku по способности к **рассуждению**);
   **контекст задаёт конкретная модель, а не тир**. Мощность — не единственный
   критерий (R3).
2. **Определить «свою модель» sanitizer** как: модель **вне четырёх тиров**
   (особый случай, не пятый тир), индивидуально подобранная под security-задачу
   (точность распознавания чувствительных данных, надёжность); по типу операции —
   детерминированная классификация, но **не обязана быть лёгкой/дешёвой**;
   задаётся в `agent.sanitizer.model` через M1/D2 по общим правилам;
   по умолчанию `temperature 0.0` (стабильность классификации), поправимо — как
   в `maestro-init/SKILL.md` M1 (`sanitizer→своя | 0.0`) (M1); trusted (доступ к
   confidential) — доверие, не мощность.

### 2. `manual_docs/tutorials/setup-project.md`

- **Строка 118** — заменить на развёрнутое определение Tier (класс
  ответственности, не мощность; контрпримеры fable/sanitizer).
- **После таблицы «Агенты: tier и trust»** (после строки ~133) — добавить таблицу
  «Tier → тип задач / ответственность → требуемое → сабагент» (из
  `model-selection.md:13-18`):

  | Tier | Тип задач / ответственность | Требуемое | Сабагент |
  |---|---|---|---|
  | haiku | механические: 1-2 файла, трансляция, юнит-тесты | низкий reasoning, следование spec | `haiku` |
  | sonnet | интеграционные: multi-file, отладка, pattern matching | средний reasoning + контекст | `sonnet` |
  | opus | архитектура, spec, дизайн-решения, ревью | высокий reasoning/дизайн-суждение | `design` (spec, **trusted**), `opus`-агент (spec review, untrusted), `code-reviewer` (code review, untrusted) |
  | fable | примеры, метафоры, пояснения | модальность, не мощность | `fable` |
  | своя (sanitizer) | security-пометка: поиск/маркировка чувствительных данных | **вне tier-класса**: точность + доверие (trusted), не мощность | `sanitizer` |

- **C1 (примечание о совпадении имён):** под таблицей — тир `opus` и агент `opus`
  — совпадение имён: тир = класс задач, агент `opus` = конкретный сабагент этого
  тира (spec review). Не путать.
- Краткое примечание под таблицей: определение «своей модели» — в
  [Выборе моделей](../reference/model-selection.md).
- Краткое примечание про экономику выбора (из `model-selection.md:35-37`): без
  явного tier агент наследует дорогую модель сессии — разрушает экономику.

мощность — косвенное следствие (по способности к рассуждению), не единственный
критерий (fable — модальность, sanitizer — доверие); контекст задаёт конкретная
модель, не тир». Таблицу tier→задача в README не дублируем.

**M2:** в README добавить однострочное определение «своей модели» (для sanitizer):
«"своя" — модель вне четырёх тиров, подбирается под security-задачу (точность,
надёжность), не обязана быть мощной/лёгкой; temperature 0.0 по умолчанию. Подробно —
в Выборе моделей». Чтобы README не расходился с `model-selection.md`.

### 4. Уточнение «ближе к haiku» (sanitizer)

Не привязываем sanitizer к haiku-цене/мощности. Формулировка: «по типу операции —
детерминированная классификация, но модель **не обязана быть лёгкой/дешёвой**;
выбор из требований точности/надёжности, **вне tier-карты**».
