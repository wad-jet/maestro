# План: поддержка пользовательской документации в процессе maestro

> Статус: план для разработки. Дата: 2026-08-24.
> Репо: `maestro-agent` (authoring). Масштаб: скиллы + документация (не код приложения).
> Связанный spec: `docs-alignment.md` (реализован ранее) — выровнял структуру `manual_docs/`.
> Связанное ревью: результаты углублённого ревью плана учтены в секции «Решения» и «Задачи».

## Цель

Обеспечить, чтобы разработка через maestro по мере изменений **сопровождалась
пользовательской документацией**: усилить enforcement на шаге 14 пайплайна,
сделать скилл `manual-docs` стек-агностичным и зафиксировать факт обязательной
поддержки документации в документации процесса maestro (`manual_docs/`).

## Проблема (контекст)

1. **Шаг 14 слабо принуждается.** `skills/maestro/SKILL.md:463` — одна строка
   «🟢 14. [agent] manual-docs -> обновление пользовательской документации».
   Нет acceptance criteria, нет сверки diff'а кода с докой, нет связи с
   coverage-гейтом. Провал шага 14 не блокирует merge так, как падающий тест.
2. **Скилл `manual-docs` хардкодит стек.** `skills/manual-docs/SKILL.md`
   описывает NestJS-специфику (`@Get/@Post/...`, `src/<module>/`,
   `docs.coverage.spec.ts`, `Saga`/`ETL`) и API-центричный пример
   `api-endpoints.md`, а maestro стек-агностичен.
3. **Документация процесса не отражает обязанность.** `manual_docs/`
   описывает шаг 14 одной строкой; не отражено, что maestro **обязательно**
   сопровождает разработку пользовательской документацией.

## Решения (утверждены, включая итоги ревью)

- **Усилить шаг 14**: оставить после SDD (шаг 13), добавить acceptance criteria
  и diff-сверку кода с `manual_docs/`. HITL поднимается **только при
  расхождении** (a/b/c); в efficient-режиме diff-сверка выполняется молча —
  без расхождений гейта нет (учитывает известный pain-point «gate fatigue»,
  см. changelog).
- **Coverage-гейт остаётся на шаге 15**: `DOCS_COVERAGE_COMMAND` уже выполняется
  на шаге 15 (`SKILL.md:471`). Шаг 14 **не** дублирует coverage — делает только
  diff-сверку. Единая точка проверки coverage — шаг 15.
- **Механика шага 14 — скилл, load оркестратором**: оркестратор загружает скилл
  `manual-docs` через skill-инструмент (по аналогии с `maestro-assistant`,
  `SKILL.md:745-751`). Не субагент; `step_to_tier` не затрагивается. Подпись
  `[agent] manual-docs` → `[skill] manual-docs`.
- **Стек-агностичность скилла `manual-docs`**: абстрактные правила + NestJS
  только как пример (не обязательное требование). Пример файла-структуры
  `api-endpoints.md` → нейтральный `reference/configuration.md` (без API-перекоса).
- **Enforcement**: если `DOCS_COVERAGE_COMMAND` задана и не `none` — coverage-гейт
  на шаге 15 обязателен; если не задана — **diff-сверка как fallback** на шаге 14
  (работает в любом проекте без coverage-теста).
- **Масштаб diff-сверки**: единый полный для всех категорий фич (простая /
  сложная / архитектурная). Шаг 14 выполняется для всех категорий: для простой
  фичи пропускаются только шаги 8-10 (`SKILL.md:235`), шаг 14 не исключается.
- **Отражение факта** поддержки документации в `manual_docs/` (обязательность шага 14).

## Задачи

### Задача 1: Скилл `manual-docs` → стек-агностичный

**Файл:** `skills/manual-docs/SKILL.md`

- Убрать NestJS-хардкод из «Когда применять»: `@Get/@Post/@Put/@Delete/@Patch`
  → «новый/изменённый API-эндпоинт»; `src/<module>/` → «новый/переименованный
  модуль/подсистема»; «статусы узлов, Saga-флоу, ETL-пайплайн» →
  «изменение пользовательского поведения».
- «Структура `manual_docs/`»: оставить Diátaxis-структуру (универсальна);
  `api-endpoints.md` → `reference/configuration.md` как нейтральный пример
  (без API-перекоса).
- «Правило 1» (Docs-as-Code): снять конфликт с пайплайном — пояснить, что в
  maestro дока обновляется на шаге 14 после реализации; «дока до кода» — для
  крупных изменений на уровне спецификации.
- «Правило 2» (Один PR): `api-endpoints.md` → `reference/configuration.md`;
  пункт «иначе падает `docs.coverage.spec.ts`» → «иначе блокирует merge
  (coverage на шаге 15 или diff-сверка на шаге 14)».
- «Тест покрытия `docs.coverage.spec.ts`»: переписать как **опциональный**
  механизм (выполняется на шаге 15, если `DOCS_COVERAGE_COMMAND` задана и не
  `none`); упомянуть diff-сверку maestro на шаге 14 как fallback.
- «Шаблоны», «Чек-лист», «Частые ошибки»: убрать NestJS/coverage-специфику.
- **Добавить** секцию «Роль в maestro»: скилл — generic user-docs для **целевого
  приложения**, загружается оркестратором на шаге 14 через skill-инструмент;
  это **отдельно** от правила синхронизации `manual_docs/` самого maestro
  (см. `manual_docs/how-to/keep-docs-up-to-date.md`).

### Задача 2: Усилить шаг 14 пайплайна maestro

**Файл:** `skills/maestro/SKILL.md`

- **L463** — расширить шаг 14 с одной строки до полного описания:
  - Оркестратор загружает скилл `manual-docs` через skill-инструмент
    (подпись `[skill] manual-docs`, не субагент; `step_to_tier` не меняется).
  - **Acceptance criteria:** каждое пользовательское изменение кода имеет
    отражение в `manual_docs/` (новый/изменённый эндпоинт → строка в
    reference; новый модуль/конфиг → how-to/reference; изменённое поведение →
    обновлённая страница).
  - **Diff-сверка:** оркестратор сверяет diff кода с изменениями в `manual_docs/`.
    В efficient-режиме — молча; в interactive — комментирует находки.
  - **HITL только при расхождении:** (a) дополнить доку → (b) документировать
    как follow-up → (c) skip с подтверждением. Без расхождений — гейта нет.
  - **Coverage НЕ выполняется на шаге 14** — он остаётся на шаге 15 (не дублировать).
- **L77** (REQUIRED SUB-SKILLS): уточнить «manual-docs (локальный скил
  репозитория) — обязательное обновление пользовательской документации целевого
  приложения (шаг 14, diff-сверка)».
- **L741** (таблица интеграции): «Документация | manual-docs (локальный скил
  репозитория) — обязательный шаг 14, diff-сверка; coverage на шаге 15».
- **Примеры L1561, L1622** и `manual_docs/examples/example-feature.md`: шаг 14 →
  «[skill] manual-docs → diff-сверка OK». В L1622 заменить
  `manual_docs/reference/api-endpoints.md` на нейтральный пример
  (см. Задачу 1) — например `manual_docs/reference/configuration.md`.

### Задача 3: `DOCS_COVERAGE_COMMAND` — diff-сверка как fallback

**Файл:** `skills/maestro/stack-detection.md` (секция `DOCS_COVERAGE_COMMAND`)

- Добавить: если команда не задана/`none`/не детектится → **не** молчаливый skip,
  а **diff-сверка** оркестратора на шаге 14 (правила acceptance criteria) +
  HITL только при расхождении. Это fallback, работает в любом проекте без
  coverage-теста. Если команда задана — coverage-гейт выполняется на шаге 15.

- `skills/manual-docs/SKILL.md` не содержит NestJS/`docs.coverage.spec.ts` как
  обязательного требования (только опциональный механизм + пример);
  пример файла-структуры нейтрален (`reference/configuration.md`), без
  API-перекоса (`api-endpoints.md` не встречается как обязательный/примерный).

  diff-сверка, HITL только при расхождении, coverage НЕ дублируется (остаётся
  на шаге 15).

  пользовательской документацией для всех категорий фич; короткие маршруты
  помечены, что шаг 14 обязателен.
- `manual_docs/` синхронизированы с SKILL.md (по правилу AGENTS.md);
  maestro-assistant canon синхронизирован; changelog обновлён.
- Нет битых ссылок; grep по NestJS-специфике в скилле `manual-docs` не находит её
