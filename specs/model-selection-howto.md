# Спецификация: how-to по подбору моделей LLM для ролей агентов maestro

## Проблема

В `manual_docs/` есть справочник `reference/model-selection.md`, который отвечает
на вопрос **«какой tier/сабагент нужен для какого шага»** (маппинг
tier→роль→шаг, механика конфигурации, дефолтные temperature). Но отсутствует
практическое руководство, отвечающее на вопрос **«как подобрать конкретную
модель под роль агента»** — по каким критериям думать (скорость, качество/
глубина анализа, стоимость/токены, контекстное окно, стабильность вывода), и
когда предпочитать локальные модели, а когда внешние и почему.

Пользователь сталкивается с необходимостью вручную выбрать модель (через
`/maestro-init` M1, либо в `.opencode/opencode.json`/global) и не имеет готовой
методики, на какие оси смотреть и как учитывать trust-ось (локальные для
trusted-агентов).

## Цели

1. Дать пользователю понятную, полную, но не перегруженную инструкцию по
   подбору моделей для ролей агентов maestro.
2. Явно описать критерии выбора: скорость, качество/глубина анализа,
   стоимость (токены), контекстное окно, стабильность вывода.
3. Дать рекомендацию по локальным vs внешним моделям: когда и какие, и почему
   (trust-ось: confidential-данные).
4. Не дублировать `reference/model-selection.md`, а дополнять его практическими
   рассуждениями и ссылаться на него как на справочник tier→роль→шаг.

## Вне области

- Изменение существующих таблиц/контента `reference/model-selection.md` и
  `tutorials/setup-project.md` — не трогаем, только связываем ссылками.
- Жёсткие карты «роль → конкретная модель» (поставщик-специфичные, устаревают).
  Даём только классы/примеры-ориентиры, не контракт.
- Изменение механики конфигурации (D2/M1) — она уже описана в reference.

## Подход

Новый how-to-раздел в Diátaxis-стиле (как существующие `how-to/*.md`):
задача-ориентированный документ «как думать при выборе модели», с чек-листом и
примерами-ориентирами. Размещается в `manual_docs/how-to/choose-models.md`,
регистрируется в `manual_docs/index.md` и отражается в `overview/changelog.md`.

## Архитектура документа

### 1. Заголовок и навигация

- `# Подбор моделей для агентов`
- `[Назад к оглавлению](../index.md)`
- `## 🎯 Назначение` — кратко: как подбирать конкретную модель под роль агента;
  критерии; связь со справочником `reference/model-selection.md` (tier→роль→шаг
  там, дублировать не будем).

### 2. Критерии выбора модели (`## 📖 Критерии`)

Таблица осей с описанием, кто к какой оси критичен. Здесь и далее «opus»
читается как **tier** (мощность), охватывающий агентов `opus`, `custodian`,
`code-reviewer`; конкретный сабагент для шага — см. `reference/model-selection.md`.

| Ось | Что это | Кому критична |
|---|---|---|
| **Скорость** | Латентность / токенов в секунду; число циклов фиксов | `haiku` (механические task-и, частые циклы), `sonnet` (multi-file) |
| **Качество и глубина анализа** | Способность к архитектурным рассуждениям, нахождению ошибок | `opus`, `custodian` (Q/A по confidential), `code-reviewer` (финальное ревью) |
| **Точность классификации** | Надёжность распознавания/маркировки чувствительных данных | `sanitizer` (детерминированная задача: точность, не мощность рассуждений) |
| **Стоимость (токены)** | Цена за вход/выход; экономика mass-задач vs точечных | `haiku`/`sonnet` (масса task-ов), дорогой `opus` — точечно (spec/revise/финальное ревью) |
| **Контекстное окно** | Устойчивость к большим диффам/спекам | `code-reviewer` (финальное ревью ветки), `sonnet` (multi-file), `opus` (spec review) |
| **Стабильность вывода** | Предсказуемость формата, отсутствие «галлюцинаций» в структуре | `haiku`/`sanitizer` (temperature 0.0); агенты со стабильным форматом — при temperature ≤ 0.2 (`sonnet`/`opus`/`custodian`/`code-reviewer`); `fable` — исключение (0.7) |

Ключевая идея: **выбор — это баланс осей под роль**, а не «самая мощная
модель». Для механических задач избыточная мощность → лишняя цена и задержки.

### 3. Локальные vs внешние модели (`## 📖 Локальные или внешние`)

Правило по trust-оси (не мощность):

- **Локальные/изолированные** — для **trusted**-агентов (`custodian`, `sanitizer`):
  confidential-данные не покидают контур (согласуется с `SECURITY.md` P4 и
  `reference/model-selection.md`). Одна локальная модель может обслуживать обоих.
  Минусы: зависит от качества/скорости локального железа, требует настройки.
- **Внешние** — для **untrusted**-агентов (`haiku`, `sonnet`, `opus`,
  `code-reviewer`, `fable`): не работают с confidential-данными, допустимо
  облако; шире выбор мощности. Локальные тоже допустимы, если хватает качества/
  скорости.
- Это **предпочтение, не жёсткое требование** — выбор за пользователем
  (соответствует reference и SECURITY P4: «trusted → изолированная модель»).

### 4. Практический чек-лист (`## 📖 Чек-лист подбора`)

Пошагово:
1. Определить tier/роль по `reference/model-selection.md` (шаг → tier → сабагент).
2. **Задать модель явно** — не оставлять `auto`/наследование: без явного
   `model` сабагент наследует модель сессии (часто самую дорогую), что
   разрушает экономику tier-выбора. `auto` — только осознанное решение.
3. Выбрать ось-приоритет для роли (скорость/качество/цена — из таблицы критериев).
4. Определить локальная или внешняя (trust-ось: trusted → локальная).
5. Проверить доступность кандидатов (D2: `opencode models <provider>`, fallback —
   `provider.<name>.models` в merge-конфиге).
6. Задать `temperature` — **дефолты брать из таблицы `reference/model-selection.md`**
   (единственный источник; не пересказывать в how-to, чтобы не рассинхронизировать
   при правках дефолтов).
7. Проверить реальным диспатчем (`/test-agents` — каждая модель диспатчится и
   доступна).

### 5. Примерные ориентиры (`## 📖 Примерные ориентиры`)

Иллюстративная таблица «роль → приоритетные критерии → пример класса модели»
(без жёсткой привязки к конкретным поставщик-специфичным ID, чтобы не устаревала;
**это ориентир, не контракт**):

| Роль | Приоритет | Класс модели |
|---|---|---|
| `haiku` | скорость + цена | лёгкая/быстрая |
| `sonnet` | баланс (multi-file) | средняя/сбалансированная |
| `opus` / `code-reviewer` | качество анализа | мощная (архитектурные рассуждения) |
| `custodian` | качество анализа | мощная, желательно локальная (trusted) |
| `sanitizer` | точность классификации | точная/надёжная, желательно локальная (trusted) |
| `fable` | креативность | креативная (высокий temperature — параметр конфига) |

## Обработка ошибок / рисков

- **Устаревание примеров моделей** → в разделе «Ориентиры» даём классы, а не
  конкретные ID; явно помечаем как иллюстрацию.
- **Дублирование с reference** → все tier-таблицы остаются в reference; how-to
  только ссылается, не переписывает.
- **Перегруженность** → критерии — сжатой таблицей, без лишних деталей;
  акцент на осях и trust, а не на каталоге моделей.
- **Известный корпус-долг (follow-up, НЕ в области этой фичи):** существующие
  файлы (`reference/model-selection.md:139`, `reference/config.md:51,615`,
  `explanation/agents-and-trust.md:30,40,114,278`) используют `../../../SECURITY.md`
  с глубины `manual_docs/*/`, что выводит за пределы репо (корректно —
  `../../SECURITY.md`). Зафиксировать как отдельный follow-up; новый файл пишет
  корректный путь и **не** «гармонизируется» под корпусный баг.
